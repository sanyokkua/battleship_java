# Near-Realtime Web Game Updates: Technology-Neutral Research and Architecture Recommendation

## Executive conclusion and factual constraints

For this exact system—a **two-player, turn-based browser game, no registration, no database, one in-memory backend instance, 15-minute session retention, potentially one packaged JAR on a constrained free tier**—the strongest design is not merely “use SSE” or “use WebSockets.” The more durable, technology-neutral architecture is:

> **Authoritative, versioned server state + idempotent HTTP commands + a server-push subscription carrying authoritative state snapshots + conditional snapshot retrieval as the recovery path.**

For browsers under the stated constraints, the preferred concrete transport for that subscription is **Server-Sent Events (SSE)**. Commands remain ordinary HTTPS `POST` requests. The normal update path is therefore server push, **not REST polling**. Adaptive conditional polling exists only as a degraded fallback when streaming cannot remain healthy.

The recommended stack-independent contract is:

```text
Client command
    |
    | POST commandId + expectedVersion
    v
Authoritative in-memory game
    |
    | serialize command
    | validate expected version
    | mutate once
    | version++
    v
Canonical snapshot(version=N)
    |
    +------ HTTP command response ------> commanding player
    |
    +------ SSE snapshot event ---------> player A
    |
    +------ SSE snapshot event ---------> player B
```

The decisive reason is the **shape of the workload**. A turn-based game needs many server-to-client notifications but only occasional client-to-server actions. SSE was expressly designed for server-to-browser events over HTTP; `EventSource` automatically reconnects, supports application event IDs, and sends `Last-Event-ID` while reestablishing a connection. The HTML Standard also defines `204 No Content` as a way to tell an `EventSource` to stop reconnecting. [WHATWG Server-Sent Events](https://html.spec.whatwg.org/multipage/server-sent-events.html) documents all of these behaviors. citeturn12search0turn14view2

WebSockets are an excellent general-purpose alternative and become preferable if the game evolves toward frequent bidirectional traffic. RFC 6455 gives WebSockets persistent full-duplex messaging, ordered message fragments, close semantics, and Ping/Pong control frames that can serve as keepalives. But those capabilities are more than this game needs, while reconnect, replay/resume, application IDs, and synchronization semantics still have to be designed at the application layer. [RFC 6455](https://datatracker.ietf.org/doc/html/rfc6455) specifies the protocol. citeturn12search1turn16view3

WebTransport is no longer merely theoretical in browsers, but it is still a poor fit here. As of **August 18, 2026**, the W3C WebTransport specification published on **July 30, 2026** is a **Candidate Recommendation Snapshot** and is scheduled to remain at that stage at least until October 30, 2026. WebTransport exposes HTTP/3-based reliable streams and unreliable datagrams—useful capabilities for latency-sensitive, high-frequency, multiplexed applications, but unnecessary for an ordered, low-rate turn game. MDN labels WebTransport “Baseline 2026” while warning that older browsers and portions of the API can still vary in support. [W3C WebTransport](https://www.w3.org/TR/webtransport/) and [MDN WebTransport](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API) are the relevant current sources. citeturn12search3turn13search2turn13search22

A critical architectural constraint is that **persistent connections must be treated as disposable**. Hosting infrastructure can impose timeouts independent of the application. For example, Google Cloud Run treats WebSockets as long-running HTTP requests subject to a configured request timeout, currently up to 60 minutes, while Render's free web services spin down after 15 minutes without inbound traffic. These are examples rather than universal limits, but they demonstrate why correctness cannot depend on a socket living forever. [Cloud Run WebSockets](https://docs.cloud.google.com/run/docs/triggering/websockets) and [Render Free Services](https://render.com/docs/free) document those behaviors. citeturn15search1turn15search2

The resulting recommendation is therefore:

**SSE is the normal notification transport; HTTPS commands are the mutation transport; full versioned snapshots are the synchronization unit; reconnect and snapshot recovery are normal protocol operations rather than exceptional failure handling.**

## Comparison matrix and trade-offs

The following matrix separates the transport properties from the application-level synchronization properties. No transport by itself solves duplicate commands, conflicting turns, server restarts, or authoritative game-state reconciliation.

| Approach | Connections / game while waiting | Near-realtime latency | Idle request churn | Reconnect / resume | Ordering and event identity | Backpressure / slow client | Proxy / browser characteristics | Fit here |
|---|---:|---|---|---|---|---|---|---|
| **Fixed polling** | 0 persistent | Up to polling interval; expected wait ≈ interval/2 under uniform event arrival | **High** | Trivial: next poll | Application version required | Naturally bounded request/response | Maximum HTTP compatibility | **Poor primary choice** |
| **Adaptive polling** | 0 persistent | Fast while active, increasingly stale while idle | Medium to low | Trivial | Application version required | Naturally bounded | Maximum HTTP compatibility | **Good fallback** |
| **Long polling** | Up to 2 pending | Usually near one network transit after event | Low-to-medium; each event/timeout causes another HTTP exchange | Entirely application-designed | Application IDs/version needed | One response at a time limits accumulation, but pending-request resources remain | Generally proxy-friendly, but timeout-sensitive | **Viable, not optimal** |
| **SSE / EventSource** | **2 logical streams** | Push / near network latency | Almost none except heartbeat bytes | **Native reconnect + `Last-Event-ID`** | Native `id:` plus app version | Server must bound pending writes; snapshots can be coalesced | Mature browser API; HTTP streaming can encounter buffering/timeouts | **Best fit** |
| **WebSocket** | **2 sockets** | Push / near network latency | Almost none except optional Ping/Pong | Application-designed | Reliable ordered connection, but application resume/version still required | Classic browser API has no receive-side backpressure control | Mature and widely supported; upgrade/persistent-connection support required | **Strong runner-up** |
| **WebTransport** | **2 sessions** | Excellent; supports multiple streams/datagrams | Low | Application-designed | Multiple reliable streams and unreliable datagrams available | Stream APIs provide richer flow-control model | Requires newer browser/server HTTP/3 ecosystem | **Overkill / premature here** |
| **Fetch response streaming** | 2 streams | Similar to HTTP streaming/SSE | Low | Manual | Manual parser, event IDs and retry logic | `ReadableStream` supports explicit stream consumption | Standard HTTP/fetch; same intermediary buffering class as streaming | **Useful SSE adapter, not first choice** |

The polling distinction matters at scale. RFC 6202 notes that continual polling spends bandwidth on complete HTTP request/response round trips when no event exists and necessarily delays an event until the next poll. Long polling removes most of that latency but sends a complete HTTP request and response for every event or timeout, meaning repeated HTTP header overhead even when messages themselves are tiny. The RFC also observes that most proxies handle long polling reasonably well because each event or timeout produces a complete HTTP response. [RFC 6202](https://www.rfc-editor.org/info/rfc6202/) remains the IETF's key analysis of these trade-offs. citeturn17view0turn17view1

SSE avoids the request-reopen cycle: multiple application events occupy one HTTP response. Its chief operational weakness is therefore not semantics but **intermediary behavior**. The WHATWG specification notes that some proxy servers can drop long-lived connections and suggests sending a comment line roughly every 15 seconds where necessary. Separately, NGINX's official documentation shows that proxy response buffering can be disabled and that the `X-Accel-Buffering: no` response header can control it when NGINX is the intermediary. [WHATWG SSE authoring notes](https://html.spec.whatwg.org/multipage/server-sent-events.html) and [NGINX proxy documentation](https://nginx.org/en/docs/http/ngx_http_proxy_module.html) support those deployment considerations. citeturn14view1turn15search0

There is an HTTP/1.x browser caveat: MDN documents a six-SSE-connection limit per browser and domain when SSE is not running over HTTP/2; with HTTP/2, simultaneous streams are negotiated between endpoints, with 100 given as the default example. One stream per game tab normally fits comfortably, but opening many game tabs against the same HTTP/1.1 origin can hit this limit. [MDN: Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) documents the browser behavior. citeturn14view0

This browser-side multiplexing should not be confused with backend capacity. At the **application level**, 1,000 concurrent games still imply up to 2,000 active player subscriptions. HTTP/2 can multiplex requests from a given client over fewer physical TCP connections, but the server still maintains 2,000 logical subscriber contexts.

WebSocket's main advantage is genuine bidirectionality. Its primary disadvantage for this workload is that the additional channel does not remove the difficult application problems. A WebSocket message stream is ordered while the connection exists, and Ping/Pong is standardized, but after a disconnect the application must determine which state the client has already seen and which command results it might have missed. RFC 6455 provides no game-specific replay/version model. citeturn12search1turn16view3

There is also a browser-side backpressure distinction. MDN explicitly notes that the traditional browser `WebSocket` interface has no mechanism to apply backpressure when application messages arrive faster than they are processed. `WebSocketStream` addresses that through the Streams API, but MDN describes it as non-standard and not broadly portable. This is unlikely to hurt a low-rate turn game, but it removes one supposed advantage of choosing WebSocket preemptively. [MDN WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API) and [WebSocketStream](https://developer.mozilla.org/en-US/docs/Web/API/WebSocketStream) describe the distinction. citeturn13search11turn13search1

Fetch response streaming is the main relevant “other” approach. A fetch response body is a `ReadableStream` and can be consumed incrementally, so it can implement the same server-streaming protocol while retaining normal Fetch request configuration. The cost is that the application—not `EventSource`—must implement frame parsing, reconnect timing, event-ID persistence, and resume behavior. [MDN Fetch streaming](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch) documents incremental response consumption. citeturn19search0turn19search8

**Trade-off conclusion:** the best primary transport is SSE, but the **protocol must be transport-independent enough that the same snapshot/version/command model could later be carried over WebSocket without redesigning game semantics**.

## Recommended architecture and protocol contract

The protocol should make the in-memory game object authoritative and make the network transport merely a way to disseminate versions of that object.

A minimal API contract could be:

```text
POST /api/games
POST /api/games/{gameId}/join

GET  /api/games/{gameId}/snapshot
GET  /api/games/{gameId}/events
POST /api/games/{gameId}/commands
```

This is deliberately a small interface. The frontend does not know whether game state is stored in a Java object, an actor, a map, or something else. The backend does not depend on frontend framework code. The same API can therefore survive replacement of either side.

**Canonical state.** Each game has a monotonically increasing unsigned or positive 64-bit logical `version`, starting at a defined value such as `1`. Every accepted state-changing command increments it exactly once. Commands are serialized per game, so there is only one authoritative state for version `N`.

An illustrative snapshot is:

```json
{
  "gameId": "g_...",
  "version": 42,
  "phase": "PLAYING",
  "you": "PLAYER_A",
  "state": {
    "turn": "PLAYER_B",
    "board": "...",
    "winner": null
  },
  "expiresAt": "2026-08-18T19:42:00Z"
}
```

The `version` is more important than transport ordering. It provides a common synchronization primitive across SSE delivery, command responses, retries, fallback GETs, browser suspension, and reconnects.

**Snapshot endpoint.**

```http
GET /api/games/{id}/snapshot
```

returns the full authoritative representation and an entity tag associated with its version, for example:

```http
ETag: "game-g_abc-v42"
Cache-Control: no-store
```

The degraded fallback may issue:

```http
If-None-Match: "game-g_abc-v42"
```

and receive `304 Not Modified` when appropriate. The application can retain the ETag itself even when shared/intermediary caching is disabled.

**Command endpoint.** A command should contain both an operation identity and the state revision against which the player made the decision:

```http
POST /api/games/g_abc/commands
If-Match: "game-g_abc-v42"
Content-Type: application/json
```

```json
{
  "commandId": "random-client-generated-id",
  "type": "MAKE_MOVE",
  "payload": {
    "position": 7
  }
}
```

`If-Match` is especially appropriate here. RFC 9110 explicitly describes `If-Match` on state-changing methods such as POST, PUT, and DELETE as a mechanism for preventing the **lost update** problem, and allows `412 Precondition Failed` when the client's representation is no longer current. [RFC 9110 §13.1.1](https://datatracker.ietf.org/doc/html/rfc9110#section-13.1.1) defines this behavior. citeturn14view3

Using an `expectedVersion` JSON field instead is also valid. `If-Match` is preferable because it exposes the concurrency rule through standard HTTP semantics, while `version` remains in the JSON model. The contract could require both to agree if explicitness is valued more than minimality.

A critical subtlety is that **`commandId` deduplication must be checked before the stale-version precondition on a retry**. Consider:

1. Player sends command `C17` against version 42.
2. Server commits it, creating version 43.
3. HTTP response disappears.
4. Another move creates version 44.
5. Player retries `C17`, still carrying `If-Match: ...v42`.

If the server checks version first, it returns a misleading conflict even though `C17` already succeeded. If it first recognizes `C17` as a previously committed command, it can return its remembered outcome without applying the command again.

That makes the application-level command semantics retry-safe even though HTTP `POST` is not inherently idempotent. RFC 9110 says clients generally should not automatically retry a non-idempotent method unless they know its application semantics are idempotent or can determine whether the operation was applied. A `commandId` deduplication record supplies exactly that missing property. [RFC 9110 §9.2.2](https://datatracker.ietf.org/doc/html/rfc9110#section-9.2.2). citeturn14view4

Because storage is deliberately in memory, there is no need for an unlimited idempotency history. Keep a bounded recent-command ring—say **32 or 64 command IDs per game**—for at least the game's remaining lifetime. That number is a design recommendation, not a standard requirement. Since a two-player turn game will normally issue very few commands during a network-retry interval, even a small ring provides ample duplicate protection.

**SSE subscription.**

```http
GET /api/games/{id}/events
Accept: text/event-stream
```

On establishment, the server should register the subscriber and capture the initial state **atomically with respect to game mutation**. Otherwise there is a classic race:

```text
read snapshot v42
                      <- opponent changes game to v43
register subscriber
```

and the client can permanently miss v43. Instead:

```text
under per-game serialization:
    register subscriber
    queue current snapshot
release serialization
```

or use an equivalent actor/event-loop operation.

The stream then begins with an authoritative snapshot:

```text
retry: 2000
event: snapshot
id: 42
data: {"version":42,"state":{...}}

:hb

event: snapshot
id: 43
data: {"version":43,"state":{...}}
```

The WHATWG format gives `id:` direct semantics: receiving it updates `EventSource`'s last event ID, and a reconnect includes that value in the `Last-Event-ID` request header. The `retry:` field changes the browser's reconnection time. [WHATWG SSE parsing and reconnect rules](https://html.spec.whatwg.org/multipage/server-sent-events.html) specify both fields. citeturn14view2

For this game, **`id` should equal the authoritative game version**. There is no benefit in maintaining a separate event sequence for ordinary state updates.

**Resume strategy.** Do not make correctness depend on a durable event log, because this application deliberately has neither a database nor long-term persistence. When a browser reconnects with:

```http
Last-Event-ID: 40
```

and the current game is at version 43, the server can simply send snapshot version 43.

That is stronger and simpler than replaying 41, 42, and 43. Because each snapshot describes the entire authoritative game, v43 subsumes the earlier state versions.

The server may optionally keep a tiny recent event ring for debugging or non-state notices, but **replay history is not required for convergence**.

The application rules become:

```text
event.version < local.version   -> stale: discard
event.version = local.version   -> duplicate: discard
event.version > local.version   -> apply full snapshot
```

A jump from 40 directly to 43 is safe because events are snapshots.

If the protocol later introduces **deltas**, the rule must change:

```text
delta.version == local.version + 1 -> apply
anything else                      -> fetch full snapshot
```

That distinction is important. Deltas make lost-event handling substantially harder and tie correctness to replay availability.

**Snapshot versus delta recommendation.** For a small turn-based game, send a complete state snapshot after each accepted state-changing command. The extra bytes are normally insignificant compared with the simplicity gained from making every update self-healing. Move to deltas only if measurement shows that state representations are large enough or update rates high enough for snapshots to dominate the bandwidth budget. There is no evidence in the supplied scenario that this threshold has been reached.

The command response should also contain the resulting authoritative snapshot:

```json
{
  "accepted": true,
  "commandId": "...",
  "snapshot": {
    "version": 43,
    "state": { }
  }
}
```

The commanding browser may therefore advance immediately even if its SSE stream has just failed. It may subsequently receive the same v43 snapshot over SSE; the version comparison discards the duplicate. That duplication deliberately buys robustness at very low complexity and bandwidth cost.

**Heartbeat.** Use SSE comment frames rather than synthetic game-state events:

```text
:hb

```

A starting interval of roughly **15 seconds** follows the WHATWG authoring note intended to mitigate legacy proxy connection timeouts. The exact value should be tuned for the actual host; if the provider guarantees a longer idle timeout, 20–30 seconds may save bandwidth. citeturn14view1

A server heartbeat is **not game activity** and must not advance `version`.

**Session expiration.** There is an ambiguity in “sessions only in memory for 15 minutes after the last client access.” The recommended operational interpretation is:

> A game is active while at least one authenticated player subscription is connected. Once both subscriptions are gone, retain the session for 15 minutes after the most recent authenticated access or command.

This avoids an absurd case where two users stare at an active game for 15 minutes and the game disappears merely because SSE is server-to-client and generates no browser request during that period. Heartbeat writes themselves should not extend retention.

If the intended product rule is instead a **hard 15-minute inactivity timeout even while both clients remain connected**, the server should expire at that deadline, send:

```text
event: expired
data: {"reason":"idle-timeout"}

```

and close the response. Since closing an SSE response normally causes reconnection, the next `/events` request should return `204 No Content`; the HTML Standard specifies that `204` tells EventSource not to reconnect. citeturn12search0

A fallback `GET /snapshot` can return `410 Gone` for an expired known game or `404 Not Found` if the implementation deliberately makes expiration indistinguishable from a nonexistent ID.

**Disconnect.** On deliberate page teardown the client calls:

```javascript
eventSource.close();
```

The EventSource standard defines `close()` as aborting the fetch and putting the EventSource into `CLOSED`. The backend removes the subscriber when the async response/socket closes. citeturn16view1

Do not require a separate “disconnect REST call” for correctness: mobile browsers, crashes, killed tabs, and network loss cannot guarantee that such a call is delivered.

**Backpressure.** Never allocate an unbounded FIFO of snapshots per browser. For each subscriber keep at most:

```text
currently-being-written frame
latest not-yet-written snapshot
small bounded control-event queue
```

If snapshot 44 is waiting and 45 becomes available before 44 is sent, replace 44 with 45. Because a full state snapshot supersedes the older snapshot, coalescing cannot lose authoritative state.

If a subscriber remains unwritable beyond a configured threshold, close it and let reconnect recover from the current snapshot. In a Java/JAR implementation, the transport must use asynchronous/non-blocking response I/O rather than holding one blocked worker thread for every SSE stream. The Jakarta Servlet specification specifically ties scalable non-blocking I/O to asynchronous processing. [Jakarta Servlet specification](https://jakarta.ee/specifications/servlet/5.0/jakarta-servlet-spec-5.0) documents the model. citeturn15search3

**Proxy behavior.** The SSE response should be flushed after event frames, disable inappropriate intermediary caching, and—when the deployment actually uses NGINX—disable response buffering, including `X-Accel-Buffering: no` where supported. NGINX documents that disabling proxy buffering causes data to be passed to the client as it is received. citeturn15search0

Do not blindly encode proxy-specific headers as part of the frontend/backend API contract. They are deployment details.

**Authentication without registration.** “No registration” should not mean “no authorization.” Create two anonymous **seat capabilities**, one for each player. After creation/join, exchange the capability for a short-lived same-origin session cookie scoped to the game/application.

For the same-origin packaged deployment, a good cookie profile is approximately:

```text
Secure
HttpOnly
SameSite=Strict   # or Lax if invite/navigation UX requires it
Path=/
```

MDN documents that `Secure` restricts cookies to HTTPS, `HttpOnly` prevents JavaScript access to the cookie, and `SameSite` restricts cross-site transmission and provides some CSRF defense. [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie). citeturn18search1

Cookies are particularly convenient for native SSE because the standardized `EventSource` constructor accepts a URL and only one option, `withCredentials`; it does **not expose an arbitrary custom-header parameter** analogous to Fetch's request configuration. [WHATWG `EventSource`](https://html.spec.whatwg.org/multipage/server-sent-events.html) shows the constructor's full `EventSourceInit` dictionary. citeturn16view0turn16view1

Therefore, do **not** make a permanent bearer secret in the SSE query string the default authentication architecture. For this packaged same-origin application, an HttpOnly capability/session cookie is simpler.

If frontend and backend are later deployed to separate origins, the API still remains replaceable, but the authentication adapter needs an explicit choice: credentialed CORS cookies, a short-lived stream ticket, or Fetch-based response streaming if arbitrary authorization headers are essential. Fetch can consume response bodies incrementally as `ReadableStream`s, though reconnect and `Last-Event-ID` semantics then become application code. citeturn19search0

For cookie-authenticated mutation requests, add CSRF protection beyond relying solely on SameSite—such as checking the expected `Origin` plus a CSRF token/custom request header. For WebSocket deployments, RFC 6455 explicitly says the server can and should use the browser-supplied `Origin` header to reject unauthorized cross-origin use. citeturn16view2

The server should additionally impose small limits on request bodies, game creation, join attempts, commands per seat, and simultaneous streams. For the stated model, enforce **one current subscription per player seat**: if the same seat reconnects while an old stream has not yet been detected as dead, the new stream replaces the old one. That keeps the intended maximum at **two active subscriber contexts per game** and prevents trivial connection multiplication.

## Client and server synchronization pseudocode

The pseudocode below describes protocol semantics rather than a JavaScript or Java framework.

The important invariant is:

> **The client renders only authoritative state carrying the greatest accepted server version.**

A client can safely receive the same version from a command response, SSE, and fallback snapshot without applying it multiple times.

```text
client fields:

    appliedVersion = -1
    snapshot       = null
    etag           = null

    eventSource    = null
    streamHealthy  = false
    fallbackActive = false

    reconnectFailureSince = null
```

Initial loading:

```text
function startGame():

    result = GET /games/{id}/snapshot

    if result is 401 or 403:
        enter AUTH_FAILED
        return

    if result is 404 or 410:
        enter EXPIRED_OR_MISSING
        return

    applySnapshot(result.snapshot, result.etag)

    openEventStream()
```

Applying state:

```text
function applySnapshot(incoming, incomingEtag = null):

    validate schema(incoming)

    if incoming.gameId != expectedGameId:
        triggerAuthoritativeResync()
        return

    if incoming.version < appliedVersion:
        # stale delivery
        return

    if incoming.version == appliedVersion:
        # duplicate delivery
        if incomingEtag != null:
            etag = incomingEtag
        return

    # Full snapshots permit a jump:
    # local v40 -> incoming v43 is valid.
    snapshot = incoming
    appliedVersion = incoming.version

    if incomingEtag != null:
        etag = incomingEtag
    else:
        etag = etagFor(incoming.version)

    render(snapshot)
```

Opening the native SSE stream:

```text
function openEventStream():

    eventSource =
        EventSource("/games/{id}/events",
                    withCredentials = true)

    eventSource.onopen:
        streamHealthy = true
        reconnectFailureSince = null
        stopFallbackPolling()

    eventSource.on("snapshot", event):

        incoming = parseAndValidate(event.data)

        # Optional invariant:
        if parseVersion(event.lastEventId) != incoming.version:
            triggerAuthoritativeResync()
            return

        applySnapshot(incoming)

    eventSource.on("expired", event):
        eventSource.close()
        stopFallbackPolling()
        enter EXPIRED

    eventSource.onerror:

        streamHealthy = false

        if reconnectFailureSince == null:
            reconnectFailureSince = now()

        # EventSource itself is allowed to reconnect.
        # Do not create a new EventSource on every error.

        if now() - reconnectFailureSince > STREAM_GRACE_PERIOD:
            startFallbackPolling()
```

One useful implementation detail is that `EventSource.onerror` is deliberately not your detailed HTTP error-reporting interface. Keep the ordinary snapshot endpoint as the diagnostic/recovery channel; it can distinguish authorization failure, expiration, and a normal current state while SSE continues trying to reconnect.

Command submission:

```text
function sendCommand(type, payload):

    commandId = cryptographicallyRandomId()
    commandVersion = appliedVersion
    commandEtag = etagFor(commandVersion)

    request = {
        commandId: commandId,
        type: type,
        payload: payload
    }

    repeat only using SAME commandId:

        response =
            POST /games/{id}/commands
            If-Match: commandEtag
            body: request

        if network failure / response unknown:
            # Safe only because commandId makes the
            # application operation deduplicatable.
            retry with bounded backoff
            continue

        if response == 401 or 403:
            enter AUTH_FAILED
            return

        if response == 404 or 410:
            enter EXPIRED
            return

        if response == 412:
            # The move was built against stale state.
            applySnapshot(response.currentSnapshot)
            show "state changed; action was not applied"
            return

        if response is success:
            applySnapshot(response.snapshot)
            return
```

A command should **not automatically be reconstructed and resubmitted after a 412**. The player selected the move against an older state; after the opponent's action, the same command can have a different meaning or become illegal. Resynchronize and require the UI/game logic to reconsider it.

The server command handler:

```text
function handleCommand(gameId, player, request, ifMatch):

    game = findGame(gameId)

    if game absent:
        return 404/410

    authenticate player capability
    validate Origin/CSRF
    validate body size and schema
    rateLimit(player, game)

    atomically serialize on game:

        touchGameAccess(game)

        previous = game.commandResults.get(request.commandId)

        if previous exists:
            # This check occurs BEFORE expectedVersion validation.
            return previous

        if ifMatch != etagFor(game.version):
            return 412 with currentSnapshot(game)

        if player is not allowed to move:
            return 409 or domain-specific illegal-command result

        if command is illegal against game.state:
            return domain-specific validation result

        nextState = applyDomainCommand(
            game.state,
            player,
            request.type,
            request.payload
        )

        game.state = nextState
        game.version = game.version + 1

        snapshot = immutableSnapshot(game)

        result = {
            accepted: true,
            commandId: request.commandId,
            snapshot: snapshot
        }

        game.commandResults.putBounded(
            request.commandId,
            result
        )

        # Queue while still serialized so event order cannot
        # be reversed by two simultaneous command handlers.
        for subscriber in game.subscribers:
            subscriber.offerLatest(snapshot)

    return result
```

Subscription must likewise avoid the registration race:

```text
function subscribe(gameId, player, lastEventId, response):

    authenticate player

    game = findGame(gameId)

    if game absent or expired:
        return HTTP 204
        # EventSource must stop reconnecting.

    initialize text/event-stream response
    initialize async / nonblocking writer

    atomically serialize on game:

        touchGameAccess(game)

        oldSubscriber = game.subscriberFor(player)

        if oldSubscriber exists:
            close oldSubscriber

        subscriber = createBoundedSubscriber(response)

        game.setSubscriber(player, subscriber)

        current = immutableSnapshot(game)

        # Because snapshots supersede history, current state
        # is sufficient even when Last-Event-ID is far behind.
        subscriber.offerLatest(current)
```

Subscriber write handling:

```text
function onWritable(subscriber):

    while transport is writable:

        item = subscriber.nextPendingItem()

        if item absent:
            return

        write:
            event: snapshot
            id: item.version
            data: serialize(item)
            blank-line

        flush according to server/container semantics

    # If not writable, return to the async event loop.
    # Do NOT block a worker thread.
```

Snapshot coalescing:

```text
function offerLatest(snapshot):

    if no state snapshot is currently waiting:
        pendingSnapshot = snapshot
    else:
        pendingSnapshot = snapshot
        # replacement, not append

    if queuedBytes > HARD_LIMIT
       or no progress for SLOW_CLIENT_TIMEOUT:
        close connection
```

Fallback behavior:

```text
function startFallbackPolling():

    if fallbackActive:
        return

    fallbackActive = true

    while fallbackActive:

        response =
            GET /games/{id}/snapshot
            If-None-Match: etag

        if response == 200:
            applySnapshot(response.snapshot,
                          response.ETag)

        else if response == 304:
            # already current
            pass

        else if response == 401 or 403:
            stop everything
            enter AUTH_FAILED

        else if response == 404 or 410:
            stop everything
            enter EXPIRED

        periodically attempt / allow SSE recovery

        sleep adaptiveInterval()
```

An example fallback schedule—not a standard—is:

```text
first ~10 seconds degraded:   2-second snapshot interval
next ~50 seconds:             5-second interval
long degraded state:         15-second interval
hidden/background tab:       30-second interval
```

SSE re-probes can use capped exponential backoff with random jitter, for example approximately 2, 4, 8, 15, and 30 seconds. As soon as an SSE stream becomes healthy, stop fallback polling.

This ensures that polling is a **failure mode**, not the normal architecture.

## Resource budget and scale envelope

A useful resource analysis must distinguish **protocol-derived counts**, which can be calculated, from **JVM/server/provider memory**, which cannot be predicted accurately without measuring the actual implementation.

The following model uses deliberately explicit engineering assumptions:

| Budget item | Working assumption |
|---|---:|
| Players per game | 2 |
| Active SSE subscriptions per game | 2 maximum |
| SSE heartbeat interval | 15 s |
| Nominal heartbeat application payload | 20 bytes |
| Canonical serialized game snapshot | ~2 KiB average |
| Game state + basic metadata | ~4 KiB/game |
| Recent command-deduplication storage | ~4 KiB/game |
| Maximum app-level pending output | ~8 KiB/subscriber |
| App-controlled total used for model | ~24 KiB/game |
| Fixed-poll comparison interval | 2 s |
| Adaptive idle-poll comparison interval | 15 s |
| Long-poll timeout comparison | 30 s |

The 15-second heartbeat choice is derived from the WHATWG SSE authoring guidance; the byte size, snapshot size, buffers, and memory figures above are **budget assumptions**, not standards or measured JVM figures. citeturn14view1

With `G` games:

```text
players / subscriber streams = 2G

fixed polling at 2 s:
    requests/sec = 2G / 2 = G

adaptive idle polling at 15 s:
    requests/sec = 2G / 15

30-s long polling with no game events:
    timeout/reopen exchanges/sec ≈ 2G / 30

SSE:
    held logical streams = 2G
    steady-state request churn ≈ 0
    plus heartbeats
```

That produces:

| Concurrent games | Browser players / SSE streams | Fixed poll at 2 s | Adaptive idle poll at 15 s | 30-s long-poll idle reopens | SSE heartbeat payload/day* | App-controlled heap assumption* |
|---:|---:|---:|---:|---:|---:|---:|
| **100** | 200 | 100 req/s | 13.3 req/s | 6.7 req/s | ~23 MB | ~2.3 MiB |
| **1,000** | 2,000 | 1,000 req/s | 133 req/s | 66.7 req/s | ~230 MB | ~23.4 MiB |
| **10,000** | 20,000 | 10,000 req/s | 1,333 req/s | 666.7 req/s | ~2.30 GB | ~234 MiB |

\*The heartbeat figures count only the assumed 20-byte application comment and omit HTTP/TCP/TLS framing and acknowledgements. The heap column counts only the artificial 24-KiB/game application budget and **does not include JVM baseline memory, framework objects, TLS state, HTTP connection state, direct buffers, kernel socket buffers, file descriptors, logging, GC overhead, or temporary serialization allocations**.

Those omissions are crucial. At 10,000 games, the naïve application map alone is not the main concern: there are **20,000 live subscriber contexts**. Even if each game's own state is tiny, runtime and operating-system connection structures can dwarf the state objects.

Long polling does **not** solve that concurrent-connection problem. While idle, it still holds approximately one pending request per player—therefore roughly the same 2G concurrency as SSE—and additionally completes/reopens those requests on timeouts and every event. RFC 6202 specifically notes that asynchronous servers are much better suited than synchronous request-per-thread models for this kind of workload. citeturn17view1turn17view2

Fixed polling removes held streams, but converts them into CPU/request pressure. At a two-second period, 10,000 games become 10,000 HTTP requests per second even when nobody makes a move. RFC 6202 identifies precisely this inefficiency: polling consumes request/response bandwidth while no data is available and delays updates until another poll arrives. citeturn17view1

The SSE heartbeat model above yields about:

```text
20 bytes × 2 clients × 86,400 / 15
= 230,400 application bytes per game per day
```

before network framing. This means that reducing heartbeat frequency, where the hosting proxy permits it, becomes significant at very high connection counts.

### Practical scale interpretation

**100 concurrent games / 200 subscribers:** this is a sensible target for the proposed architecture on a small single service, assuming nonblocking I/O and modest state. The actual hosting tier still needs a connection test because provider limits are not standardized.

**1,000 concurrent games / 2,000 subscribers:** the application-level state remains small under the assumptions, but the hosting environment becomes the dominant uncertainty: logical connection limits, file descriptors, container memory, TLS buffers, bandwidth quotas, and runtime implementation all need measurement. This may or may not fit a particular free tier.

**10,000 concurrent games / 20,000 subscribers:** the synchronization protocol itself remains valid, but **a generic constrained free-tier single instance should not be treated as a credible capacity target**. Under the sample budget, application-controlled memory is already roughly 234 MiB before JVM/framework/socket/TLS overhead, and heartbeats alone produce about 2.3 GB/day of application payload. This conclusion is an engineering capacity assessment, not a universal provider-imposed limit.

This is an important boundary: the requirement says not to recommend a database or multiple backend instances. The correct response is therefore **not** to invent horizontal scaling. It is to state that the architecture remains logically valid at 10,000 games, while the assumed free-host resource envelope probably does not.

The server must therefore expose and load-test at least:

```text
active games
active subscriber streams
heap used
direct/native memory if visible
open file descriptors / sockets
pending subscriber bytes
slow subscriber count
events emitted/sec
commands/sec
bytes sent/sec
GC pause / CPU utilization
p50/p95/p99 update-delivery latency
stream reconnect rate
fallback-polling rate
```

For a packaged Java service, the implementation should use asynchronous/nonblocking writes. Jakarta Servlet explicitly says non-blocking I/O is intended to improve the number of simultaneously handled connections and requires asynchronous processing. citeturn15search3

Provider behavior must be tested rather than inferred. Render's free service documentation, for example, says a free service spins down after 15 minutes without **inbound** HTTP traffic or WebSocket messages. An SSE comment is outbound, so one should not assume that merely emitting SSE heartbeats keeps that provider's service active. That inference follows directly from Render's documented definition of inbound traffic. citeturn15search2

This particular behavior is actually compatible with a game that intentionally expires after 15 minutes of genuine inactivity, provided active player behavior causes inbound commands/access and the chosen retention interpretation is documented.

## Failure handling, security, and proving tests

The rendered failure-state diagram accompanying this report implements the following state machine:

```text
                    +-----------------+
                    |   CONNECTING    |
                    +--------+--------+
                             |
                    snapshot + SSE
                             v
                    +-----------------+
       +----------->|      LIVE       |<--------------+
       |            +---+---------+---+               |
       |                |         |                   |
       |        stream error      | invalid/ambiguous |
       |                |         | state             |
       |                v         v                   |
       |        +------------+  +--------+            |
       |        |RECONNECTING|  | RESYNC |------------+
       |        +------+-----+  +--------+
       |               |
       |        SSE unavailable
       |               v
       |        +-----------------+
       +--------| FALLBACK POLL   |
        SSE OK  +------+----------+
                       |
                404/410/204
                       v
                 +-----------+
                 |  EXPIRED  |
                 +-----------+
```

The key property is that **every recoverable arrow ultimately obtains an authoritative snapshot**. No recovery path says “hope the missing event was unimportant.”

An SSE connection can fail after any byte boundary. The server can commit v43 and lose the connection before the browser sees it; the browser can receive v43 and disconnect before updating its own persistent UI state; or a reverse proxy can disappear while both endpoints initially believe they are connected. Native EventSource reconnection plus `Last-Event-ID` gives useful context, but the current snapshot, rather than perfect replay, supplies correctness. citeturn14view2

A process restart is qualitatively different. Because the requirements explicitly forbid a database and retain all sessions only in memory, restarting the single process **destroys the authoritative game**. No network protocol can recover that state. After restart, reconnect should resolve to expired/missing rather than fabricate game continuity.

That limitation should be reflected honestly in the UI:

```text
"This game session is no longer available."
```

rather than silently creating a new state under the old identifier.

### Slow-client behavior

A slow or suspended browser must never force unbounded server memory growth. The server maintains a bounded/coalescing subscriber buffer. Since full snapshots supersede earlier snapshots:

```text
pending v43
new v44 arrives
new v45 arrives

send v45
```

is semantically correct.

The client needs no knowledge that v44 was skipped.

If the output transport remains blocked beyond a configured limit, disconnect it. Reconnection retrieves the current state.

This is superior to a delta protocol where missing v44 could make v45 uninterpretable.

### Security and abuse model

There is no user account, but each seat must still be protected by an unguessable anonymous capability. Separate player A and player B capabilities so possession of one does not authorize the other seat.

All production communication should use HTTPS, with the seat/session credential carried in an appropriately scoped `Secure`, `HttpOnly`, `SameSite` cookie in the same-origin deployment. Those browser cookie controls are documented by MDN. citeturn18search1

State-changing commands require:

```text
authenticated seat
expected Origin
CSRF defense
valid commandId
expected game version
valid schema
legal player turn
legal game command
body-size ceiling
per-seat/game/IP rate limit
```

The `expectedVersion`/`If-Match` rule prevents a stale browser from overwriting a newer move, while `commandId` prevents retransmission from applying one move twice. RFC 9110's conditional-request semantics directly support the concurrency part of this model. citeturn14view3turn14view4

A malicious client must never be trusted merely because the official frontend would not send a certain operation. All turn legality and state transitions remain server-authoritative.

For SSE, cap one current stream per seat. A reconnect races naturally with dead-connection detection, so atomically install the new subscriber and close/supersede the old one. Without such a limit, a valid capability could intentionally create hundreds of subscriptions and multiply memory/bandwidth consumption.

For WebSocket if it were substituted, validate the browser `Origin`; RFC 6455 explicitly describes `Origin` as the mechanism by which the server can reject unauthorized cross-origin browser use. citeturn16view2

Rate limiting is necessarily in-memory under the project rules. It therefore resets on process restart; this is acceptable for lightweight abuse protection but should not be mistaken for durable anti-abuse accounting.

### Proving-test matrix

The protocol should be considered proven only when the following tests work under forced failures, not merely during a normal two-browser demonstration.

| Test | Fault / stimulus | Required invariant | Expected observable result |
|---|---|---|---|
| **Simultaneous turns** | Both players submit against v42 at almost the same instant | At most one conflicting mutation commits against v42 | Winner produces v43; loser receives 412/conflict and v43 |
| **Lost command response** | Server commits command, response is dropped | Command applied exactly once | Retry with same `commandId` returns remembered result |
| **Duplicate command** | Same command sent 2–10 times | One mutation / one version increment | All retries converge on same committed outcome |
| **Stale command** | Player acts on v40 after opponent has created v41 | No lost update | 412; client applies current snapshot |
| **SSE loss before event** | Commit v43, terminate stream before delivery | Eventually converge | Reconnect receives current v43+ snapshot |
| **SSE loss after delivery** | Deliver v43 then disconnect immediately | Duplicate safe | Reconnect may resend v43; client ignores equal version |
| **Miss multiple events** | Suppress v41 and v42, allow v43 snapshot | Replay not required | Client jumps directly to v43 |
| **Outdated event injection** | Deliver v40 after client has v43 | State never regresses | v40 discarded |
| **Malformed event** | Corrupt SSE JSON or ID/version mismatch | Never apply uncertain state | Trigger authoritative snapshot resync |
| **Proxy buffering** | Configure intermediary to accumulate stream bytes | Streaming failure detected | Client enters fallback polling; deployment test fails until buffering fixed |
| **Proxy idle timeout** | Drop stream at 10/30/60 s | Disconnect not fatal | Auto-reconnect or fallback converges |
| **Network offline** | Disconnect browser for 30–120 s | No duplicate state transition | Online recovery obtains latest snapshot |
| **Browser suspension** | Background/suspend mobile tab | No server queue growth | Old snapshots coalesce; resume receives latest |
| **Very slow reader** | Throttle browser/network severely | Bounded server memory | Subscriber queue stays under cap or stream closes |
| **Reload race** | New stream opens while old socket appears alive | One stream per seat | New stream supersedes old |
| **Session TTL** | Disconnect both users >15 min | Memory released | Snapshot says expired/missing; stream no longer reconnects |
| **Live expiration variant** | Hard TTL fires with open stream | Explicit terminal state | `expired` event; reconnect gets 204 |
| **Server process restart** | Kill process and restart | Never invent lost in-memory session | Existing IDs resolve to missing/expired |
| **Bad player capability** | Steal/alter game ID without seat secret | No state disclosure | 401/403 |
| **Cross-site mutation** | Foreign site attempts command with browser credentials | No CSRF mutation | Origin/CSRF validation rejects |
| **Oversized command** | Send large body | Memory bounded | Early 413/rejection |
| **Command flood** | Valid seat floods endpoint | Turn service remains usable | Rate limiter throttles |
| **Stream flood** | Same credential opens many subscriptions | ≤1 active subscription per seat | Older connections replaced/rejected |
| **100 games** | 200 streams under realistic moves | Establish baseline | Stable heap and latency |
| **1,000 games** | 2,000 streams | Determine actual hosting boundary | No monotonic heap growth; provider limit recorded |
| **10,000 games** | 20,000 attempted streams | Prove or falsify free-tier feasibility | Clean refusal/measurement rather than OOM |
| **Reconnect storm** | Drop every active stream simultaneously | Recovery remains bounded | Jitter prevents synchronized reconnect spike |
| **Fallback recovery** | Break SSE then restore it | Polling remains exceptional | Client stops polling immediately after stream recovery |

For load tests, correctness metrics matter more than raw socket count. Recommended acceptance criteria should include:

```text
zero duplicate committed commands
zero state-version regressions
zero unbounded per-subscriber queue growth
zero leaked subscriber entries after disconnect
all recoverable failures converge to current snapshot
steady heap returns near baseline after sessions expire
```

A latency target such as “95% of accepted moves visible to the other connected browser in under 500 ms under intended capacity” is a reasonable **product SLO**, not a property guaranteed by SSE or any other transport.

A reconnect-storm test is especially important. If 2,000 clients simultaneously detect a hosting restart and all immediately reconnect, the recovery load can be much worse than ordinary gameplay. Random jitter in application fallback probes and reliance on browser reconnect behavior reduce synchronization of those retries.

## Reasons for rejecting alternatives and remaining uncertainty

**Fixed polling as the normal mechanism is rejected** because it spends HTTP requests, CPU, and bandwidth in direct proportion to the number of connected players even when the state is unchanged. At a two-second period, the model produces 100, 1,000, and 10,000 requests per second at 100, 1,000, and 10,000 games respectively. It also imposes up to a full interval of detection latency. RFC 6202 identifies both unnecessary idle round trips and reduced responsiveness as core polling drawbacks. citeturn17view1

Fixed polling remains useful diagnostically because it has the broadest possible HTTP compatibility.

**Adaptive polling as the primary mechanism is rejected** because it trades wasted traffic for unpredictable latency. Backing off to 15 or 30 seconds saves requests while simultaneously allowing an opponent's move to remain invisible for that long. It is, however, the **recommended degraded mode**, because that exact latency/resource trade-off is appropriate after streaming has failed.

**Long polling as the primary mechanism is rejected** because it retains most of the persistent-resource cost of SSE—one outstanding request per player—while adding repeated complete HTTP exchanges after each event and each timeout. RFC 6202 explicitly calls out HTTP header overhead and the need to choose timeouts around infrastructure behavior; it notes that a timeout set too high can encounter server/proxy timeouts and historically regarded around 30 seconds as a safer interoperable value. citeturn17view0turn17view2

Long polling is still a credible compatibility fallback if a particular host reliably supports held requests but demonstrably buffers SSE streams. It is not the default fallback proposed here because conditional adaptive snapshots are simpler and the expected game rate is low.

**WebSocket as the primary mechanism is not rejected as technically inadequate.** It is rejected on **fit and complexity**. Full duplex does not confer much value when player-to-server messages are occasional commands that already map cleanly to HTTP requests. The application would still need versions, idempotent command IDs, reconnect handling, stale-state detection, and snapshot recovery. Browser WebSocket also lacks the automatic `Last-Event-ID` resume mechanism EventSource supplies, and the classic API lacks backpressure support. citeturn13search11turn14view2

WebSocket should replace SSE as the first choice if future requirements become substantially different—for example:

```text
many client-to-server events per second
continuous interaction rather than turns
bidirectional ephemeral messages
real-time cursor/aim/control streams
transport-specific binary protocol
hosting environment with excellent WebSocket support but broken HTTP streaming
```

The application model should remain unchanged:

```text
commandId
expectedVersion
authoritative version
full recovery snapshot
bounded subscriber queues
```

so that such a transport migration does not require rewriting game correctness.

**WebTransport is rejected for the current game** because it introduces HTTP/3/QUIC-specific infrastructure and a substantially richer API to solve problems the game does not have. WebTransport supports multiple reliable uni- and bidirectional streams and unreliable datagrams, but an ordered turn game needs neither independent stream scheduling nor unreliable delivery. Its W3C specification is also still a Candidate Recommendation as of August 18, 2026. citeturn12search3turn13search2

It should be reconsidered only if future gameplay needs capabilities such as independently prioritized streams, unreliable low-latency datagrams, or transport behavior that is measurably impossible to achieve with SSE/WebSocket.

**WebSocketStream is rejected** because its backpressure model is attractive but it is not yet an appropriate interoperability baseline. MDN describes the traditional WebSocket API as stable while noting that `WebSocketStream` is not standardized/broadly implemented. citeturn13search11turn13search1

**Raw Fetch streaming is rejected as the first-choice browser API** because it recreates functionality that EventSource already standardizes: parsing event boundaries, reconnect timing, event IDs, and resume behavior. It becomes attractive if a future authentication contract absolutely requires request headers that native EventSource cannot configure. Fetch response bodies are standard `ReadableStream`s and can be processed incrementally. citeturn19search0turn16view0

There are several genuine uncertainties that cannot responsibly be resolved at the technology-neutral research stage.

First, **the actual simultaneous-connection ceiling is hosting-provider and runtime specific**. The protocol math can say that 1,000 games mean 2,000 player subscriptions, but it cannot say that an unspecified free host will accept exactly 2,000 streams. Cloud Run, Render, reverse proxies, JVM HTTP servers, and other platforms impose different concurrency, timeout, memory, and network policies. The Cloud Run 60-minute WebSocket timeout and Render 15-minute free-service idle behavior illustrate why these limits must be verified against the chosen deployment rather than assumed. citeturn15search1turn15search2

Second, **per-connection memory cannot be estimated accurately from Java alone**. The chosen servlet/reactive container, TLS implementation, direct buffers, HTTP version, operating system, socket buffer sizing, framework callbacks, and GC behavior matter. The 24-KiB/game figure in this report is intentionally an application-owned budget, not an estimate of process resident memory.

Third, **proxy buffering must be tested end-to-end**. HTTP streaming standards cannot force every deployment intermediary to deliver tiny chunks at the desired cadence. RFC 6202 documents the historic intermediary buffering problem, and NGINX exposes explicit buffering controls. citeturn17view1turn15search0

Fourth, **the definition of “last client access” must be part of the product contract**. The technically clean interpretation for SSE is that an authenticated connected player counts as active presence and the 15-minute retention clock begins after the last player disconnects. If the intended business rule instead means “15 minutes after the last browser-originated HTTP request regardless of an open stream,” the application must explicitly expire connected games or introduce a client presence/touch mechanism. That decision cannot be inferred from network standards.

Finally, the absence of a database makes **process loss equivalent to session loss by design**. No choice among polling, SSE, WebSockets, or WebTransport changes that. The strongest architecture is therefore one that does not pretend to offer durable delivery: it makes reconnection cheap, makes missed transient events harmless, makes commands idempotently retryable, and treats the current in-memory snapshot as the only source of truth.

The resulting decision can be summarized as:

| Design decision | Recommendation |
|---|---|
| Authority | Single in-memory server game object |
| Mutation path | HTTPS `POST` commands |
| Concurrency protection | `If-Match` / `expectedVersion` |
| Retry protection | Client-generated `commandId` + bounded dedupe history |
| Normal update path | **SSE `EventSource`** |
| Streams per game | **2 maximum, one per player** |
| State event | **Full authoritative snapshot** |
| Event ID | Same value as game `version` |
| Delivery guarantee required | At-least-available/current-state convergence, not durable event replay |
| Duplicate handling | Ignore `version <= appliedVersion` |
| Missed updates | Accept newest full snapshot |
| Resume | Native `Last-Event-ID`; server sends current snapshot |
| Heartbeat | SSE comment, initially around 15 s, tune to host |
| Slow client | Coalesce snapshots; bounded queue; disconnect if persistently blocked |
| Normal polling | **None** |
| Degraded fallback | Adaptive conditional `GET snapshot` |
| Authentication | Anonymous player capability exchanged into secure same-origin cookie |
| Session end | Remove after chosen 15-minute inactivity semantics |
| Process restart | Session is lost, explicitly reported |
| 100 games | Plausible target; load-test |
| 1,000 games | Host-specific; prove with 2,000-stream test |
| 10,000 games | Protocol-valid, but not a credible generic free-tier assumption |
| Primary alternative | WebSocket if workload becomes genuinely bidirectional |
| Rejected emerging transport | WebTransport for current requirements |

In other words, **SSE is recommended because it minimizes transport machinery, while full versioned snapshots and idempotent commands minimize distributed-state machinery**. The latter is more important. Even if SSE is eventually replaced, a client that understands `commandId`, `expectedVersion`, authoritative snapshots, and deterministic resynchronization will remain correct across disconnects, duplicate delivery, stale actions, proxy timeouts, and temporary fallback—all without introducing a database or a second backend instance.
