# Responsive Battleship Frontend UX Research

## Recommended interaction architecture

A robust Battleship frontend should treat **dragging as an enhancement, not as the only way to play**. The primary interaction model should be coordinate-based: choose a ship or action, navigate/select a board cell, preview the result, and confirm. Pointer dragging can accelerate that workflow for mouse, touch, and pen users, but the same operation must remain possible through tap/click and keyboard controls. This directly aligns with WCAG 2.2’s Dragging Movements requirement, which says functionality that uses dragging should also be achievable with a single pointer without dragging unless dragging is essential. Direct source: https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html citeturn3search0

The recommended frontend model is therefore:

**canonical game state → interaction state → derived visual preview → command → authoritative server state**

Do not make CSS positions or DOM locations authoritative. Ships should live in application state as board coordinates such as `{shipId, row, col, orientation}`. Dragging, tapping, keyboard navigation, CSS transforms, and responsive layout then become different views/controllers over the same coordinate model. This makes snapping, rotation, conflict resolution, reconnects, and responsive resizing substantially easier to reason about.

The browser-facing input layer should use **Pointer Events** for mouse/touch/pen gestures. Pointer Events provide one event model across those pointing devices, including pointer IDs and pointer capture. Direct sources: https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events and https://www.w3.org/TR/pointerevents3/ citeturn0search0turn15view4 Native keyboard activation and semantic HTML should remain separate rather than synthesizing fake pointer events for keyboard users.

A practical interaction hierarchy is:

| Task | Preferred universal interaction | Pointer enhancement |
|---|---|---|
| Place ship | Select ship → select board cell → confirm/place | Drag ship onto board |
| Move ship | Select placed ship → Move → select new origin → confirm | Drag placed ship |
| Rotate ship | Explicit **Rotate** button | Tap/click Rotate while ship selected |
| Remove ship | Explicit **Remove** button | Same button/action menu |
| Fire | Navigate/select enemy cell → Enter/Space or click/tap | Direct tap/click |
| Cancel edit | Cancel button and Escape | Release invalid drag / Cancel |
| Inspect board | Arrow-key navigation; pointer hover/tap where appropriate | Pointer movement |

This avoids gesture-only features such as long-press menus, two-finger rotation, or “drag in exactly this way” interactions. WCAG also requires general functionality to be keyboard operable, and pointer actions cannot substitute for that requirement. Direct sources: https://www.w3.org/WAI/WCAG21/Understanding/keyboard.html and https://www.w3.org/WAI/WCAG22/quickref/ citeturn14search3turn14search18

**UX recommendation.** Keep placement forgiving and reversible until the player explicitly commits or becomes “Ready,” assuming the game rules support such a phase. A ship dropped over an illegal location should visually return to its previous position rather than silently snapping somewhere else. A click/tap attempt on an invalid origin should leave the ship selected, state why the placement is invalid, and let the player try another cell.

**Backend-independence recommendation.** Put a single domain API between UI code and any HTTP/WebSocket/SSE/polling implementation. UI components should dispatch domain commands rather than constructing URLs or interpreting transport status codes themselves. A useful transport-neutral boundary is conceptually:

```ts
type GameCommand =
  | { type: "PLACE_SHIP"; shipId: string; row: number; col: number; orientation: "H" | "V" }
  | { type: "MOVE_SHIP"; shipId: string; row: number; col: number }
  | { type: "ROTATE_SHIP"; shipId: string }
  | { type: "REMOVE_SHIP"; shipId: string }
  | { type: "FIRE"; row: number; col: number };

interface CommandEnvelope {
  commandId: string;
  expectedRevision: number;
  command: GameCommand;
}

interface GameSnapshot {
  revision: number;
  phase: string;
  turn: string | null;
  expiresAt: string;
  // Only information this player is permitted to know.
  ownBoard: unknown;
  opponentBoard: unknown;
}
```

The important architectural properties are a **stable command vocabulary**, an idempotency/request identifier, a monotonic server revision or equivalent ordering mechanism, and a canonical snapshot that can be re-fetched after reconnect or conflict. If HTTP is used underneath, `409 Conflict` is explicitly intended for a request conflicting with current resource state, `412 Precondition Failed` can support version/precondition semantics, and `410 Gone` is a plausible transport mapping for a permanently expired session; these should remain adapter details rather than leaking throughout UI components. Direct sources: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/409, https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/412, and https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/410 citeturn7search3turn7search33turn7search7

A particularly important security/API boundary is that the client should receive **only opponent information the current player is allowed to know**. Hidden ship positions should not merely be hidden with CSS or `aria-hidden`; they should not be present in the player-visible payload at all. `aria-hidden` only affects the accessibility tree—it is not an information-security mechanism. Direct source for what `aria-hidden` actually does: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-hidden citeturn14search25


## Browser and web-platform facts

**Pointer Events.** A single Pointer Events implementation can handle mouse, touch, and pen input and exposes properties such as `pointerId` and `pointerType`. Use `pointerdown`, `pointermove`, `pointerup`, and `pointercancel` as the core drag stream rather than maintaining independent mouse and touch implementations. Direct sources: https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent and https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events citeturn0search4turn0search0

For dragging, call `setPointerCapture(pointerId)` on a stable drag owner after the drag starts. Pointer capture causes subsequent events for that pointer to be targeted to the capture element even when the pointer leaves its bounds, which is exactly what a ship drag needs when a finger moves outside the ship or board. Capture can be explicitly released with `releasePointerCapture()`, and `pointerup`/`pointercancel` cause implicit release. `lostpointercapture` is therefore a normal part of the lifecycle, not an obscure error condition. Direct sources: https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture and https://www.w3.org/TR/pointerevents/ citeturn0search16turn10search0

That has one easily missed consequence: **during capture, `event.target` is not a reliable indication of the board cell geometrically underneath the pointer.** The pointer stream continues to target the capture element. Derive the hovered cell from pointer coordinates and board geometry instead. This follows directly from pointer-capture retargeting semantics. Direct source: https://www.w3.org/TR/pointerevents3/ citeturn15view4

`pointercancel` can occur when the browser takes control of the gesture—for example, for panning/zooming or other suppression conditions—and the Pointer Events specification defines cancellation and subsequent stream termination. The UI must therefore have the equivalent of a transaction rollback for every drag. Direct sources: https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event and https://www.w3.org/TR/pointerevents/ citeturn0search20turn10search0

**`touch-action` is declarative.** This is one of the most important implementation facts for the mobile board. The browser determines whether a direct-manipulation gesture may pan or zoom using `touch-action`, and changing `touch-action` after the gesture begins is too late to change the behavior of that gesture. The Pointer Events specification also explains why browser panning/zooming is not something applications should attempt to control merely by canceling pointer events. Direct source: https://www.w3.org/TR/pointerevents3/ citeturn15view4

Consequently, do **not** apply:

```css
.board {
  touch-action: none;
}
```

to the entire game board unless preventing all direct browser pan/zoom from that region is genuinely intended.

A better pattern is:

```css
/* Ordinary cells remain friendly to tap and browser gestures. */
.board-cell {
  touch-action: manipulation;
}

/* Only an element that genuinely starts a drag opts out. */
.ship-drag-handle {
  touch-action: none;
}
```

`touch-action: manipulation` permits panning and continuous zooming while removing some gesture ambiguity; `none` disables browser panning/zooming for gestures begun on that element. Direct sources: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/touch-action and https://www.w3.org/TR/pointerevents3/ citeturn2search0turn15view4

This architecture also avoids needing to disable browser zoom globally. The viewport declaration should not contain `user-scalable=no`; MDN explicitly warns that disabling user zoom creates accessibility problems. Direct source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport citeturn13view1

Use:

```html
<meta
  name="viewport"
  content="width=device-width, initial-scale=1, viewport-fit=cover"
/>
```

when the UI intentionally extends into edge-to-edge device areas, and compensate using CSS safe-area environment variables. `viewport-fit=cover` and `safe-area-inset-*` are the platform mechanisms for such layouts. Direct sources: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport and https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env citeturn13view0turn12view1

**Pointer completion should happen on the up-event whenever practical.** WCAG’s Pointer Cancellation guidance specifically favors up-event activation because it permits a user to move away before release and avoid an accidental activation. Do not fire a shot, permanently remove a ship, or finalize placement merely on `pointerdown`. Direct source: https://www.w3.org/WAI/WCAG21/Understanding/pointer-cancellation.html citeturn4search0

A drag recognizer should therefore distinguish press from actual drag:

```text
pointerdown
    │
    ├── small movement → still a possible tap
    │
    └── movement exceeds threshold → dragging
                                      │
pointerup ─────────────────────────────┘
```

The threshold should be a modest internal UX constant rather than something users need to hit precisely. Once dragging begins, record exactly one `activePointerId`; do not let a second finger unexpectedly rotate, commit, or take ownership of the ship. Pointer Events explicitly represent simultaneous pointers independently, and browsers can cancel a stream in circumstances including excessive simultaneous pointer activity or gesture takeover. Direct sources: https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events/Multi-touch_interaction and https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event citeturn0search12turn0search20

**Snapping should use board coordinates.** At drag start:

```text
pointerCell = cellFrom(clientX, clientY)
grabOffset = pointerCell - originalShipOrigin
```

During movement:

```text
candidatePointerCell = cellFrom(clientX, clientY)
candidateOrigin = candidatePointerCell - grabOffset
candidate = validate(ship, candidateOrigin, orientation, boardState)
```

Keeping `grabOffset` prevents a multi-cell ship from jumping so that its bow suddenly sits under the user’s finger. Validity should come from a pure rules function—bounds, overlap, fleet rules, and any ship-adjacency rule—not from DOM collision testing. Render the preview from that candidate model. A visual preview layer can use `pointer-events: none` so it does not become a pointer target itself. Direct source for CSS `pointer-events`: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/pointer-events citeturn2search19

The board rectangle can be cached for an active gesture, but it must be recomputed when geometry changes, such as responsive reflow or viewport rotation. Pixel measurements are ephemeral; row/column coordinates remain canonical.

**Responsive viewport facts.** Modern viewport units include dynamic viewport variants such as `dvh`, intended to respond to the changing visual viewport on mobile rather than assuming the classic fixed `vh` behavior. Direct source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length citeturn1search5 Do not lock the game to landscape just because it is board-heavy: WCAG’s Orientation criterion requires content not to restrict operation to one display orientation unless a specific orientation is essential. Direct source: https://www.w3.org/WAI/WCAG22/Understanding/orientation.html citeturn1search12


## Interaction state machines

The following machines deliberately separate **interaction state** from **authoritative game state**. They also make cancellation, pending network work, and reconciliation explicit rather than encoding those cases as incidental booleans such as `isDragging` plus `loading`.

**Placement**

```text
UNPLACED
   │ select ship
   ▼
SHIP_SELECTED
   │
   ├── hover/focus/tap candidate
   ▼
PREVIEW_VALID  ◄──────────────► PREVIEW_INVALID
   │ confirm / pointerup              │ retry elsewhere
   ▼                                  │
PENDING_PLACE                         └────► SHIP_SELECTED
   │
   ├── accepted ───────────────► PLACED
   │
   ├── rejected/conflict ──────► SHIP_SELECTED + error announcement
   │
   └── connection outcome unknown ──► RECONCILING
```

For drag placement, `pointercancel`, `lostpointercapture`, Escape, or an invalid final coordinate should return to `SHIP_SELECTED` or `UNPLACED` according to the product’s selection model. Do not treat loss of capture as implicit success. Pointer Events explicitly define capture loss and cancellation as lifecycle events. Direct sources: https://www.w3.org/TR/pointerevents/ and https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event citeturn10search0turn0search20

For non-drag placement, the equivalent sequence is simply **Select ship → move board focus → Enter/Space**, satisfying the requirement for a non-drag single-pointer alternative and keyboard operation. Direct sources: https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html and https://www.w3.org/WAI/WCAG21/Understanding/keyboard.html citeturn3search0turn14search3

**Movement**

```text
PLACED
   │ select ship
   ▼
PLACED_SELECTED
   │ Move
   ▼
MOVE_ARMED
   │ choose/drag toward candidate
   ▼
MOVE_PREVIEW_VALID ◄──────────► MOVE_PREVIEW_INVALID
   │ confirm
   ▼
PENDING_MOVE
   │
   ├── accepted ───────────────► PLACED_AT_NEW_ORIGIN
   └── failure/cancel ─────────► PLACED_AT_ORIGINAL_ORIGIN
```

Keep the original placement immutable for the duration of a move transaction. Visually moving the real ship and then attempting to reconstruct where it used to be after an error is fragile. Instead, keep `{original, candidate}` until the server accepts the candidate.

Keyboard movement should not overload ordinary grid arrow keys. The APG grid pattern expects arrows to navigate within a grid. A clearer keyboard workflow is **select ship → activate Move → navigate board → Enter to preview/confirm**, while **Rotate**, **Remove**, and **Cancel** remain explicit buttons. APG documents arrow-key navigation as the defining interaction of a grid. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/grid/ citeturn15view1

**Rotation**

```text
PLACED_SELECTED
   │ Rotate
   ▼
ROTATION_PREVIEW
   │
   ├── valid + confirm ────────► PENDING_ROTATE
   │                              │
   │                              ├── accepted → PLACED_ROTATED
   │                              └── failure  → PLACED_SELECTED
   │
   └── invalid ────────────────► INVALID_ROTATION_PREVIEW
                                    │
                                    └── Cancel / new action
```

For uncommitted setup, a single Rotate activation can reasonably both preview and apply locally if the placement remains valid; if every adjustment is persisted immediately, retaining a `PENDING_ROTATE` state is safer. A dedicated button is preferable to requiring a single-letter shortcut or a twist gesture. Native `<button>` elements already have platform keyboard activation behavior; adding `role="button"` to a generic element does not provide that behavior automatically. Direct source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/button_role citeturn14search9

**Removal**

```text
PLACED_SELECTED
   │ Remove
   ▼
REMOVE_REQUESTED
   │
   ├── reversible setup edit ──► PENDING_REMOVE
   │                               │
   │                               ├── accepted → UNPLACED
   │                               └── failed   → PLACED_SELECTED
   │
   └── irreversible action ────► CONFIRM_DIALOG
                                   │ Confirm
                                   ▼
                                PENDING_REMOVE
```

Do not insert confirmation dialogs for every reversible pre-game edit. Confirmation becomes appropriate when removal is destructive, commits a state other players depend upon, or cannot easily be undone. When a modal contains a consequential irreversible operation, APG recommends considering initial focus on the least destructive action. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/ citeturn15view3

**Shooting**

```text
WAITING_FOR_TURN
   │ server says your turn
   ▼
TARGETING
   │ select available cell
   ▼
TARGET_SELECTED
   │ click/tap/Enter/Space
   ▼
PENDING_SHOT
   │
   ├── authoritative MISS ─────► RESULT_MISS ──► WAITING_FOR_TURN
   ├── authoritative HIT ──────► RESULT_HIT  ──► next phase per rules
   ├── authoritative SUNK ─────► RESULT_SUNK ──► next phase per rules
   ├── rejected/conflict ──────► TARGETING after resync
   └── outcome unknown ────────► RECONCILING_SHOT
```

A shot is the operation for which optimistic rendering is least appropriate. Do not change the cell to “hit” or “miss” before receiving authoritative information. While submission is pending, show a neutral “Shot pending” state and block another shot unless the API explicitly supports concurrent commands.

If the connection fails after the request left the browser, the frontend cannot safely infer that the shot failed. Reconcile using `commandId`, revision, and a snapshot or command-status mechanism. Blindly resending a shot risks duplicating a non-idempotent command.

Already-fired or otherwise unavailable cells should remain perceivable when navigating the board. `aria-disabled="true"` can communicate that an element remains perceivable but is not operable; unlike a native disabled form control, applying `aria-disabled` alone does not implement the disabled behavior, so application logic must still prevent the action. Direct source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-disabled citeturn14search1

**Reconnect**

```text
CONNECTED
   │ transport/request failure
   ▼
RECONNECTING
   │
   ├── connection restored
   │       ▼
   │    RESYNCING_SNAPSHOT
   │       │
   │       ├── revision valid/current → CONNECTED
   │       ├── local pending command  → RECONCILING_COMMAND
   │       └── session expired        → EXPIRED
   │
   └── retries continue → RECONNECTING
```

While reconnecting, display the last canonical snapshot but make game-changing actions unavailable. A persistent message such as **“Reconnecting… last known game state is shown”** is clearer than blanking the board.

Do not let `navigator.onLine` be the authority for this state. MDN explicitly describes the property as inherently unreliable for determining whether a particular site or service is reachable and recommends using it only as a hint. Direct source: https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine citeturn7search0

On restoration, synchronize with the server before re-enabling commands. A WebSocket is one possible near-realtime transport, but it should remain behind the API adapter; the browser WebSocket API is only a transport facility and does not define your domain ordering, replay, or conflict rules. Direct source: https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API citeturn7search5

**Expiry**

```text
ACTIVE
   │ inactivity deadline approaches
   ▼
EXPIRY_WARNING
   │
   ├── server-recognized activity → ACTIVE with new authoritative deadline
   ├── deadline reached           → VERIFYING / server response
   └── session declared expired   → EXPIRED

EXPIRED
   │
   ├── game UI becomes non-operable
   ├── announce expiration
   └── New game / Return action
```

For a 15-minute inactivity expiry, tell players the duration early instead of surprising them at minute fifteen. WCAG 2.2’s AAA Timeout criterion specifically addresses warning users about inactivity that can cause loss of data; while AAA may not be your conformance target, its guidance is directly applicable to this game. Direct source: https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html citeturn3search1

The **server must own the deadline**. The client may render a countdown from an authoritative `expiresAt`, but it should not silently decide that random mouse movement, pointer movement, heartbeat traffic, tab focus, or reconnect constitutes activity unless the API contract says it does. Clock drift and background-tab throttling make a purely client-maintained 15-minute timer unsuitable as the canonical expiry mechanism.

For an impending expiry warning, a time-sensitive announcement can use an alert or alert-dialog depending on whether immediate action is required. MDN explicitly lists session-expiration warnings as a suitable use of alert semantics, while warning that alerts should be used sparingly. Direct source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/alert_role citeturn2search16


## Semantic HTML, keyboard model, and accessible game states

The most defensible Battleship board semantics are a **semantic HTML table enhanced with the ARIA `grid` pattern**, because the game is intrinsically row/column-based and interactive.

WAI-ARIA APG says a `grid` is a composite widget in which directional navigation is handled inside the component and only one focusable item normally participates in the page Tab sequence. It also explicitly identifies interactive tabular information with row/column labels as a use case. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/grid/ citeturn15view1

APG's date-picker example demonstrates an especially relevant implementation: a native `<table role="grid">`, with ordinary `<tr>`, `<th>`, and `<td>` providing implied row, column-header, and grid-cell roles; one `<td>` has `tabindex="0"` and the others `tabindex="-1"`. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/ citeturn15view0

A recommended skeleton is:

```html
<html lang="en">
  <body>
    <header>
      <h1>Battleship</h1>

      <p id="session-status">
        Session expires after 15 minutes of inactivity.
      </p>

      <nav aria-label="Language">
        <button type="button" lang="en" aria-pressed="true">English</button>
        <button type="button" lang="uk" aria-pressed="false">Українська</button>
      </nav>
    </header>

    <main>
      <section aria-labelledby="enemy-board-title">
        <h2 id="enemy-board-title">Opponent board</h2>

        <p id="enemy-board-help">
          Use the arrow keys to move between cells.
          Press Enter or Space to fire at an available cell.
        </p>

        <table
          class="board"
          role="grid"
          aria-labelledby="enemy-board-title"
          aria-describedby="enemy-board-help"
        >
          <caption class="visually-hidden">
            Opponent targeting board
          </caption>

          <thead>
            <tr>
              <th aria-hidden="true"></th>
              <th scope="col">A</th>
              <th scope="col">B</th>
              <!-- C–J -->
            </tr>
          </thead>

          <tbody>
            <tr>
              <th scope="row">1</th>

              <td
                tabindex="0"
                aria-label="A1, available"
              ></td>

              <td
                tabindex="-1"
                aria-label="B1, miss"
                aria-disabled="true"
              ></td>

              <!-- remaining cells -->
            </tr>
          </tbody>
        </table>
      </section>

      <section aria-labelledby="fleet-title">
        <h2 id="fleet-title">Your fleet</h2>

        <ul>
          <li>
            <button type="button">
              Cruiser, three cells, not placed
            </button>
          </li>
        </ul>

        <div aria-label="Selected ship actions">
          <button type="button">Move</button>
          <button type="button">Rotate</button>
          <button type="button">Remove</button>
        </div>
      </section>

      <div
        id="game-status"
        role="status"
        aria-live="polite"
        aria-atomic="true"
      ></div>

      <div id="urgent-status" role="alert"></div>

      <ol
        id="game-log"
        role="log"
        aria-label="Game events"
      ></ol>
    </main>

    <dialog id="session-expired-dialog" aria-labelledby="expired-title">
      <h2 id="expired-title">Session expired</h2>
      <p>Your game expired after 15 minutes of inactivity.</p>
      <button type="button">Start a new game</button>
    </dialog>
  </body>
</html>
```

The exact `aria-label` text should be localized and generated from state; the sample is illustrative.

The document's `lang` attribute should switch between `en` and `uk` with the interface language. The HTML `lang` global attribute identifies the content language using a language tag, which assists language-sensitive processing such as screen-reader pronunciation. Direct source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/lang citeturn5search1

**Keyboard contract for a board**

| Key | Battleship behavior |
|---|---|
| `Tab` | Enter the board at its remembered/current cell; subsequent Tab leaves the board |
| `Shift+Tab` | Leave toward the previous page control |
| `ArrowRight` | One column right |
| `ArrowLeft` | One column left |
| `ArrowDown` | One row down |
| `ArrowUp` | One row up |
| `Home` | First cell of current row |
| `End` | Last cell of current row |
| `Ctrl+Home` | A1 |
| `Ctrl+End` | J10 |
| `Enter` / `Space` | Activate current cell for the current mode |
| `Escape` | Cancel placement/move preview or dismiss a dismissible overlay |

This follows the APG grid model rather than creating 100 Tab stops. APG specifically says only one focusable element inside a grid is normally included in the page Tab sequence and that the author manages directional focus. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/grid/ citeturn15view1 The APG date picker likewise places only one grid cell in the Tab sequence at a time. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/ citeturn15view0

Do not wrap arrow movement at edges unless user testing clearly favors it. Battleship is spatial: pressing Right on J5 and unexpectedly landing on A6 weakens the geometric model. `Home`/`End` already provide fast row navigation.

**Mode handling.** Grid arrows should mean **navigation consistently**. Do not have Right Arrow sometimes move focus and sometimes slide a ship without a strong, announced mode transition. Recommended keyboard placement is:

```text
Choose "Cruiser"
→ focus enters board
→ arrows choose origin
→ Enter previews/places
→ Rotate button changes orientation
```

Moving a placed ship becomes:

```text
Select Cruiser
→ Move button
→ board receives focus
→ arrows choose new origin
→ Enter confirms
→ Escape cancels
```

This reduces hidden keyboard modality.

**Accessible cell states.** A cell should convey coordinate and relevant known state. For example:

```text
"A1, available. Press Enter to fire."
"B4, miss."
"C7, hit."
"D7, hit, sunk cruiser."
"E2, unavailable, already fired."
"F6, selected placement origin; cruiser fits horizontally."
"G10, invalid placement; cruiser would extend outside the board."
```

Do not expose an opponent ship's type or location until game rules reveal it.

Keep **focus**, **selection**, and **game result** visually distinct:

- keyboard focus means “where input will act”;
- selection means “which cell/ship is chosen”;
- hit/miss/sunk is persistent game data;
- invalid preview is temporary validation feedback;
- unavailable means activation is currently prohibited.

`aria-selected` is appropriate only where there is actual selection semantics; APG's grid example applies it to the currently selected grid cell rather than treating focus itself as selection. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/ citeturn15view0

**Visual state must not be color-only.** WCAG requires color not to be the sole visual means of conveying information or distinguishing state. Use, for example, a dot/ring for a miss, cross or impact icon for hit, ship outline/pattern for sunk, hatch/stripe plus warning icon for invalid placement, and a distinct focus outline for keyboard focus. Direct sources: https://www.w3.org/WAI/WCAG21/Understanding/use-of-color.html and https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html citeturn14search2turn14search22

**Announcements should be event-oriented, not DOM-change-oriented.** `role="status"` is suitable for advisory updates such as:

```text
"Cruiser placed at C4 horizontally."
"Shot at F7: miss."
"Opponent's cruiser sunk."
"Reconnected. Game state updated."
```

Status-message guidance says such changes should be programmatically determinable without unnecessarily moving focus. Direct source: https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html citeturn3search2

Use `role="alert"` for truly urgent states such as imminent expiry or a significant connection failure, not every invalid hover. Use a `log` for sequential game history if the UI offers one; the ARIA `log` role is intended for sequentially appended information and includes game-like or conversational event histories among its uses. Direct sources: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/alert_role and https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/log_role citeturn2search16turn2search20

Do **not** place `aria-live` on the entire board. A single shot can change several nodes—cell visual, turn label, ship health, status, log—and a broad live region can produce repetitive announcements. Update a deliberately small live-status element with one synthesized outcome sentence.

A concise accessibility acceptance checklist is:

| Requirement | Acceptance condition |
|---|---|
| Keyboard-only operation | Place, move, rotate, remove, shoot, open/close overlays, reconnect/retry and restart without pointer |
| Grid navigation | Board is one Tab stop, arrows navigate cells, focus remains visible |
| Pointer alternatives | Every drag has click/tap alternative |
| Coordinate awareness | Screen reader receives row/column coordinate plus state |
| Focus versus selection | Independently perceivable |
| Hit/miss/sunk | Not represented by color alone |
| Invalid placement | Both visual indicator and text/status |
| Pending actions | Programmatically announced |
| Reconnect | Last state identified as stale/read-only |
| Expiry | Warning and terminal state announced |
| Dialog | Initial focus, contained Tab order, Escape policy, visible close/cancel, focus return |
| Zoom | Browser zoom remains enabled |
| Orientation | Portrait and landscape both usable |
| Motion | Nonessential movement reduced with OS preference |
| Localization | Correct document `lang`; no clipped English/Ukrainian content |


## CSS layout, viewport strategy, and localization

A 10×10 Battleship board has a fundamental small-screen constraint: even before row/column labels, ten 44 CSS-pixel cells require 440 CSS pixels of playable width. WCAG 2.2’s Level AA Target Size (Minimum) criterion uses **24×24 CSS pixels** subject to defined exceptions; 44×44 is associated with the larger enhanced target guidance rather than being the universal AA floor. Direct sources: https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html and https://www.w3.org/WAI/WCAG22/quickref/ citeturn1search1turn1search4

That means a narrow phone cannot simultaneously have a full-width 10×10 board, axis labels, margins, and 44-pixel cells. The correct design response is not horizontal scrolling by default; it is to make **individual board cells as large as the viewport allows while ensuring larger controls such as Rotate, Remove, Ready, Retry, and language controls remain generously sized**.

A good structural layout uses CSS Grid for the page while preserving the semantic table internally. CSS Grid is specifically designed for two-dimensional row/column layout. Direct source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Grid_layout citeturn5search2

For example:

```css
:root {
  --page-gap: clamp(0.5rem, 2vw, 1.25rem);
  --board-max: 38rem;
}

*,
*::before,
*::after {
  box-sizing: border-box;
}

html,
body {
  margin: 0;
  min-inline-size: 0;
}

body {
  min-block-size: 100dvh;
}

.game {
  min-block-size: 100dvh;
  display: grid;
  grid-template-rows: auto minmax(0, 1fr) auto;
  gap: var(--page-gap);

  padding-block-start:
    max(0.75rem, env(safe-area-inset-top));
  padding-block-end:
    max(0.75rem, env(safe-area-inset-bottom));
  padding-inline-start:
    max(0.75rem, env(safe-area-inset-left));
  padding-inline-end:
    max(0.75rem, env(safe-area-inset-right));
}

.boards {
  min-inline-size: 0;
  display: grid;
  gap: var(--page-gap);
}

.board {
  inline-size: min(100%, var(--board-max));
  table-layout: fixed;
  border-collapse: collapse;
}

.board td {
  padding: 0;
}

.board td::before {
  /* Use only if needed by the chosen table sizing strategy. */
  content: "";
}

.board [role="gridcell"],
.board td {
  /* Do not impose fixed text heights elsewhere in the UI. */
}

.ship-preview {
  pointer-events: none;
}

.ship-drag-handle {
  touch-action: none;
}

@media (min-width: 60rem) {
  .boards {
    grid-template-columns: minmax(0, 1fr) minmax(0, 1fr);
  }
}

@media (prefers-reduced-motion: reduce) {
  .ship,
  .board-cell,
  dialog {
    animation: none;
    transition-duration: 0.001ms;
  }
}
```

The `prefers-reduced-motion` media feature reflects a user preference to minimize nonessential motion. Direct source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion citeturn14search0 The intent should be to remove or simplify movement—not to suppress useful state feedback entirely. A hit can still change icon, label, and contrast instantly without a scale burst, shake, explosion, or long animated ship movement.

For an actual square-cell implementation, test the chosen table sizing across supported engines. A semantic table's axis column means “make the entire table `aspect-ratio:1`” does not precisely make the 10×10 playable interior square. A dependable implementation can calculate the playable cell size once from its containing board shell and expose it as a CSS custom property, while keeping all authoritative state in logical coordinates:

```js
const cellSize = Math.floor(
  Math.min(availablePlayfieldWidth, availablePlayfieldHeight) / 10
);
```

That geometry is a rendering calculation, not game logic.

**Recommended responsive viewport matrix**

The cell sizes below are design targets, not browser guarantees; final values depend on axis labels, safe areas, browser chrome, text scaling, and control layout.

| Test viewport | Orientation | Board strategy | Approximate useful cell goal | Surrounding UI |
|---|---|---|---:|---|
| 320×568 | Portrait phone | One primary board at a time | 24–28 px | Fleet/actions below or sheet; no two-board squeeze |
| 360×640 | Portrait phone | One primary board | 28–32 px | Sticky actions outside board |
| 390×844 | Portrait phone | One primary board | 30–35 px | Comfortable controls; secondary board below/toggle |
| 430×932 | Large portrait phone | One board dominant | 34–38 px | Can expose more fleet/status beside/below |
| 568×320 | Short landscape phone | Board left, controls right | 24–27 px, height-limited | Compact status; no orientation lock |
| 667×375 | Landscape phone | Board + side controls | 27–31 px | Account for notch/safe area |
| 844×390 | Large landscape phone | Board + side panel | 29–34 px | Fleet/action stack right |
| 768×1024 | Tablet portrait | Large board; second board stacked | 44+ px often attainable | Fleet adjacent if space permits |
| 1024×768 | Tablet landscape | Two boards or board + fleet | roughly 36–44 px each | Avoid over-dense third column |
| 1280×720 | Laptop | Two boards side by side | 44+ px feasible | Status/fleet around them |
| 1440×900+ | Desktop | Two bounded boards | 44–52 px | Do not endlessly enlarge board |

During **placement**, there is only one board that needs to dominate; use the extra space for the fleet list, Rotate/Move/Remove controls, instructions, and readiness state.

During **battle**, two boards are semantically useful but not equally interactive. On mobile, prioritize the opponent targeting board and make the player's own board readily reachable through a labelled toggle or stacked section. Do not shrink both into unusably small 10×10 thumbnails merely to preserve desktop symmetry.

For short landscape viewports, a two-column shell is more useful:

```css
@media (orientation: landscape) and (max-height: 30rem) {
  .placement-layout {
    grid-template-columns: minmax(0, 1fr) minmax(14rem, 0.7fr);
    align-items: start;
  }

  .placement-controls {
    overflow: auto;
    max-block-size: calc(100dvh - 1rem);
  }
}
```

Do not infer from this that landscape should be forced. WCAG’s Orientation criterion explicitly discourages that except where orientation is essential. Direct source: https://www.w3.org/WAI/WCAG22/Understanding/orientation.html citeturn1search12

**Safe areas.** Sticky controls, dialog buttons, bottom sheets, and the board should use `env(safe-area-inset-bottom)`, `-top`, `-left`, and `-right` when edge-to-edge presentation is enabled so they do not sit beneath cutouts or device UI regions. Direct source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env citeturn12view1

**English/Ukrainian localization.** Design for content expansion, not for the current English labels.

Avoid:

```css
.action-button {
  width: 96px;
  height: 36px;
  white-space: nowrap;
}
```

Prefer:

```css
.action-button {
  min-block-size: 2.75rem;
  padding: 0.65rem 0.9rem;
  max-inline-size: 100%;
  white-space: normal;
}

.action-row {
  display: flex;
  flex-wrap: wrap;
  gap: 0.5rem;
}

.message,
.session-code {
  min-inline-size: 0;
}
```

Ordinary Ukrainian prose should be allowed to wrap naturally. `overflow-wrap` exists to permit otherwise unbreakable strings to break when they would overflow; it is especially useful for IDs, session tokens, or URLs, not as a reason to arbitrarily fracture normal words. Direct source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-wrap citeturn6search0 CSS also provides `hyphens` when automatic/manual hyphenation is appropriate. Direct source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/hyphens citeturn6search1

Recommended localization engineering rules are to translate whole messages rather than concatenating fragments, avoid assumptions such as “label + number” having identical grammar in both locales, allow button labels to occupy multiple lines where necessary, test actual Ukrainian rather than relying only on pseudo-localization, and keep board coordinates such as “A1” separate from translated explanatory wording.

The document should change to `<html lang="uk">` when Ukrainian is active, with individual opposite-language fragments given their own `lang` where needed. Direct source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/lang citeturn5search1


## Dialog, popup, bottom-sheet, and focus contract

Use the platform's **native `<dialog>` element for true modal UI** instead of hand-building a fixed-position `<div>` plus custom focus trap whenever the product requirements fit the native primitive. Calling `showModal()` creates a modal dialog in the top layer with modal behavior; MDN documents keyboard dismissal and native dialog semantics. Direct source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog citeturn8search5

APG defines the expected modal behavior: focus moves inside when the dialog opens; Tab and Shift+Tab remain within the modal; Escape closes it; and focus normally returns to the element that invoked it. APG also strongly recommends a visible close/cancel control. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/ citeturn15view3

The Battleship dialog contract should be:

| Concern | Required behavior |
|---|---|
| Semantics | Native `<dialog>` for modal interaction where supported by target browsers |
| Accessible name | Visible heading referenced by `aria-labelledby` |
| Opening focus | Move focus inside |
| Long structured content | Focus heading/intro with `tabindex="-1"` rather than forcing a distant action into view |
| Short confirmation | Usually focus safest/default logical action |
| Tab | Cycles only through modal controls |
| Shift+Tab | Reverse cycle |
| Escape | Closes when cancellation is permitted |
| Visible dismissal | Close or Cancel button always available when dismissal is permitted |
| Outside click | Never the only dismissal mechanism |
| Destructive/critical flow | Do not light-dismiss by accidental outside click |
| Close return | Return to invoker, unless it no longer exists or workflow has a clearer next target |
| Stacked dialogs | Avoid where possible |
| Mobile Back | Treat browser close/cancel semantics consistently with Escape where platform behavior provides it |

APG explicitly says initial focus can vary with content complexity and recommends least-destructive focus for difficult-to-reverse final actions. It also specifies focus return to the invoker or a logical workflow destination. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/ citeturn15view3

Use a blocking modal for cases such as an irreversible “Leave game?” confirmation, a pre-game commit if “Ready” becomes irreversible, or a terminal expired-session action where continued interaction with the old game is meaningless.

Do **not** use a modal for ordinary “not your turn,” “ship overlaps,” “reconnecting,” or “shot was a miss” messages. These should stay in context.

For transient non-modal controls such as a compact ship-action menu, help panel, or responsive auxiliary menu, the **Popover API** can provide native popover behavior. Auto popovers support light dismissal, including interaction outside them and Escape. Direct sources: https://developer.mozilla.org/en-US/docs/Web/API/Popover_API/Using and https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/popover citeturn8search0turn8search4

This yields a useful rule:

```text
Requires interaction before returning to game?
    yes → dialog/modal
    no
     │
     ├─ transient action/help surface → popover
     └─ persistent information → ordinary semantic page content
```

**Outside-click behavior should depend on consequence.**

A noncritical ship action popover may light-dismiss when the user taps the board. A destructive confirmation should not vanish because the user accidentally touched the backdrop. Native dialog mechanisms increasingly expose explicit close-request/light-dismiss controls, but the product should define the policy independently of those APIs. WHATWG defines light dismissal as closing an applicable dialog when a user interacts outside it. Direct source: https://html.spec.whatwg.org/dev/interactive-elements.html citeturn8search2

**A bottom sheet is a visual layout, not an accessibility role.** On a phone, the fleet selector may visually rise from the bottom, but its semantic choice still depends on interaction:

```text
Modal placement chooser
→ <dialog> styled as bottom sheet

Non-modal transient ship actions
→ popover styled as bottom sheet

Persistent fleet/status information
→ ordinary <section>/<aside>, responsive CSS
```

On short landscape screens, a “bottom” sheet may become a side sheet or near-full-screen dialog without changing its semantic contract. This is a CSS presentation decision.

For modal sheets, do not “fake” inertness by putting `aria-hidden="true"` on arbitrary background ancestors while leaving focusable descendants operable. APG requires the experience described as modal to actually prevent outside interaction, and warns of severe accessibility problems when `aria-modal` says one thing while behavior says another. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/ citeturn15view3

Use `:focus-visible` for a conspicuous keyboard focus treatment without trying to erase all pointer-focus styling manually. The selector allows browsers to apply focus indication according to focus modality heuristics. Direct source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/%3Afocus-visible citeturn8search17

A sample policy:

```css
.board td:focus-visible,
button:focus-visible {
  outline: 3px solid currentColor;
  outline-offset: 2px;
}
```

Do not allow sticky headers, action bars, or bottom sheets to cover the currently focused board cell. WCAG 2.2 includes a Focus Not Obscured criterion specifically addressing this problem. Direct source: https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html citeturn1search9


## Realtime states and UX failure-state catalog

The frontend should distinguish **domain failures**, **transport failures**, and **uncertain command outcomes**. Treating all three as a generic red “Something went wrong” toast is particularly dangerous in a turn-based game because the player needs to know whether an action happened.

A recommended catalog is:

| State/failure | Visible UX | Interaction | Accessible announcement | Recovery |
|---|---|---|---|---|
| Initial loading | “Loading game…” with stable page structure | Game controls unavailable | Polite status | Render canonical snapshot |
| Placement pending | Ship preview remains; “Saving…” | Prevent duplicate edit of same ship | Polite status | Accept or rollback |
| Move/rotate pending | Candidate remains visibly pending | Disable conflicting ship action | Polite status | Accept or rollback |
| Shot pending | Neutral pending mark, not hit/miss | Prevent next shot | “Shot at F7 pending” | Await/reconcile |
| Local invalid placement | Invalid outline/pattern + reason | Retry immediately | Polite, only after intentional selection/drop | No network required |
| Server placement rejection | Restore previous valid state | Retry | “Placement rejected: …” | Canonical server state |
| Not player's turn | Turn indicator near board | Target cells non-operable | Status when turn changes | Wait for server event |
| Already fired | Existing result retained | No duplicate shot | Cell state says unavailable | Select another |
| Conflict/new revision | “Game changed; refreshing state” | Pause affected action | Polite status | Fetch snapshot/reconcile |
| Connection lost | Persistent reconnect banner | Read-only last-known state | Alert once, not every retry | Backoff/reconnect |
| Reconnecting | Spinner/text without blocking whole app visually | Game-changing commands paused | Polite status | Resync |
| Reconnected | Fresh snapshot replaces stale state | Re-enable valid commands | “Reconnected. Game updated.” | Continue |
| Unknown command outcome | “Checking result…” | Block conflicting retry | Polite status | Lookup/revision resync |
| Server unavailable | Explain temporary failure | Retry button where safe | Alert/status depending severity | Retry without duplication |
| Session nearly expired | Explicit countdown/warning | Continue according to server activity rules | Time-sensitive alert | Server-recognized activity |
| Session expired | Terminal game state/dialog | Old game non-operable | Immediate announcement | Start new session |
| Opponent unavailable | Domain-specific waiting status | Depends on game rules | Polite status | Backend-defined |
| Localization failure | Fallback copy rather than blank UI | Remains usable | No special announcement | Telemetry/fallback |
| Stale browser tab resumed | “Refreshing game…” | Temporarily pause commands | Polite status | Canonical resync |

`role="status"` is appropriate for informational result/progress updates that do not require focus movement, while `role="alert"` is intended for important time-sensitive messages. Direct sources: https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html, https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/status_role, and https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/alert_role citeturn3search2turn2search6turn2search16

**Loading.** Avoid rendering an apparently actionable empty 10×10 grid before knowing the actual phase and permissions. A stable heading and loading status are sufficient. Once state arrives, render the board with the correct turn and availability.

**Pending placement/movement/rotation.** These operations can be optimistically previewed because their local geometry is known, but whether to optimistically commit them depends on API semantics. Keep a pending visual treatment separate from “accepted.” On rejection, restore the exact previous canonical position.

**Pending shooting.** Keep it pessimistic. A shot result is server-owned information. The pending cell can display a spinner/dot and label such as “F7, shot pending,” but it should not become hit/miss until resolved.

**Conflict.** With revision-aware commands, a command made against revision `42` can be rejected if the server is already at `43`. At the HTTP layer, `409 Conflict` is explicitly defined for a conflict with the current state of the target resource; conditional request designs can alternatively use preconditions and `412`. Direct sources: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/409 and https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/412 citeturn7search3turn7search33

The UX response should normally be:

```text
pause affected action
→ retrieve canonical snapshot
→ apply newer revision
→ preserve selection if still meaningful
→ otherwise clear it
→ announce "Game state updated"
```

Do not show a generic fatal error for a routine synchronization conflict.

**Reconnect.** Keep the board visible so players do not lose context, but label it as last-known/stale and prevent commands that could have uncertain ordering. The UI should attempt connection recovery through the transport layer, then perform a snapshot/revision reconciliation before declaring success.

`navigator.onLine` must not decide whether the game is reachable. MDN notes that the browser's notion of online connectivity is inherently unreliable for this purpose. Direct source: https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine citeturn7search0

**Unknown outcome is different from rejected.** For example:

```text
POST FIRE F7
→ server accepts and changes state
→ response is lost
→ browser sees network error
```

The safe UX is “Checking shot result…”, not “Shot failed, try again.” Retrying blindly could duplicate the command. This is why `commandId` or equivalent idempotency/reconciliation support belongs in the API contract.

**Expiry.** Once the server reports the anonymous session has expired, stop reconnecting the old session indefinitely. Switch to a terminal state that explains exactly what happened: **“This game expired after 15 minutes of inactivity.”** If the transport maps this to HTTP, `410 Gone` semantically represents a resource that is no longer available and is intended to remain unavailable. Direct source: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/410 citeturn7search7

**Do not rely on `beforeunload` to preserve game state or tell the server the player left.** MDN notes limitations and unreliability around this event, especially in mobile/browser lifecycle scenarios. Direct source: https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event citeturn7search8 Durable game state must be server-side.

A compact transport adapter interface could be:

```ts
interface GameGateway {
  getSnapshot(): Promise<GameSnapshot>;

  send(
    envelope: CommandEnvelope,
    options?: { signal?: AbortSignal }
  ): Promise<CommandResult>;

  subscribe(
    onEvent: (event: GameEvent) => void,
    onConnectionState: (state: ConnectionState) => void
  ): () => void;
}
```

`fetch()` operations can be canceled using `AbortController`, which is useful when a page-level request becomes obsolete; cancellation is not the same thing as proving that a mutating command never reached the server. Direct source: https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch citeturn7search10


## Testing strategy and common implementation pitfalls

Accessibility testing must combine automation with manual and assistive-technology testing. W3C explicitly states that no evaluation tool can determine accessibility by itself and recommends evaluation throughout development. Direct sources: https://www.w3.org/WAI/test-evaluate/ and https://www.w3.org/WAI/test-evaluate/tools/selecting/ citeturn9search14turn9search8 web.dev similarly recommends hands-on keyboard and assistive-technology testing. Direct sources: https://web.dev/learn/accessibility/test-manual and https://web.dev/learn/accessibility/test-assistive-technology citeturn9search1turn9search9

**Pointer test suite**

Test mouse, touchscreen, and pen where the browser/device support matrix includes them. At minimum exercise:

| Scenario | Expected result |
|---|---|
| Pointer down/up without movement | Selection/tap behavior, not accidental drag |
| Move beyond drag threshold | Drag starts |
| Drag ship inside board | Candidate tracks snapped cells |
| Drag outside board | Preview becomes invalid; capture continues |
| Re-enter board before release | Valid preview resumes |
| Release outside | Cancel/revert |
| `pointercancel` | Cancel/revert |
| `lostpointercapture` before normal completion | Cancel/reconcile; never silently commit |
| Release over invalid placement | Revert and explain |
| Second finger added | Does not steal or rotate active ship |
| Browser scroll gesture outside drag handle | Page can still scroll |
| Pinch zoom away from drag handle | Browser zoom remains available |
| Orientation change during interaction | Drag cancels safely or geometry recomputes |
| Resize during drag | No pixel/cell corruption |
| Pointer leaves browser window | No stuck `dragging=true` state |
| Rapid successive taps | No duplicated placement/shot |
| Touch tap on same cell after drag | No “ghost” second action |

Pointer Events explicitly provide cancellation, capture, and independent pointer identity, so these are tests of normal platform semantics rather than artificial edge cases. Direct sources: https://www.w3.org/TR/pointerevents3/ and https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events/Multi-touch_interaction citeturn15view4turn0search12

**Keyboard test suite**

Complete an entire game setup and at least a representative battle sequence with the mouse/touchscreen untouched.

Verify that Tab reaches each major region without visiting all 100 cells; arrow keys reach all 100 coordinates; edge behavior is consistent; Home/End work; Enter/Space perform the currently described cell action; Move, Rotate, Remove and Ready are reachable native controls; Escape cancels edit modes and dismissible overlays; dialogs contain focus while open; focus returns logically when closed; expired-session UI does not strand focus in the old board; and no custom widget creates an accidental keyboard trap. WCAG requires keyboard operation, while APG defines the grid and modal navigation expectations. Direct sources: https://www.w3.org/WAI/WCAG21/Understanding/keyboard.html, https://www.w3.org/WAI/ARIA/apg/patterns/grid/, and https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/ citeturn14search3turn15view1turn15view3

**Screen-reader tests**

The exact support matrix is a product decision, but it should include representative browser/assistive-technology combinations from the browsers actually supported. APG itself warns that support gaps can exist across browser/assistive-technology combinations, including mobile/touch, and says testing APG-based code with assistive technologies is essential before production use. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/grid/examples/layout-grids/ citeturn15view2

Verify:

- board title, dimensions, row and column context;
- coordinate and state of every focused cell;
- `available`, `hit`, `miss`, `sunk`, `selected`, and `unavailable`;
- ship selection and orientation;
- invalid-placement reason;
- successful placement/movement/rotation/removal;
- whose turn it is;
- shot result exactly once;
- reconnect/lost-connection state;
- conflict refresh;
- timeout warning;
- final expiry;
- dialog title and focus placement;
- no hidden opponent fleet information in accessibility output.

Do not assume that an automated ARIA tree assertion proves the screen-reader experience is usable.

**Visual and responsive tests**

Run the viewport matrix above and add browser zoom/text scaling. Specifically test mobile browser chrome expanding/collapsing, safe-area devices, portrait-to-landscape rotation, 200% browser zoom, narrow viewport reflow, Ukrainian text, deliberately long pseudo-localized strings, forced/high-contrast modes where supported, and reduced motion.

Focus indicators and game-state icons require sufficient visibility, and the UI cannot depend on color alone. Direct sources: https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html and https://www.w3.org/WAI/WCAG21/Understanding/use-of-color.html citeturn14search22turn14search2

`prefers-reduced-motion: reduce` should be tested as a functional mode rather than just inspecting CSS. Direct source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion citeturn14search0

For browser automation, an implementation may use a tool such as Playwright to emulate viewport, touch, locale and related environment conditions. That is a tooling option rather than an application dependency, and emulation should complement rather than replace physical-device and assistive-technology tests. Direct source: https://playwright.dev/docs/emulation citeturn9search2

**Pure logic tests** should be especially extensive because board rules can be tested without browsers:

Useful invariants include: every horizontal/vertical ship occupies exactly its declared number of cells; no valid placement contains a coordinate outside `0..9`; two ships cannot occupy the same coordinate; canceling any edit produces the exact pre-edit model; rendering dimensions never affect legal placement; the same authoritative snapshot always produces the same board state; and an event with an already-applied `eventId` cannot apply twice.

**Common implementation pitfalls**

| Pitfall | Why it fails | Better approach |
|---|---|---|
| Implementing only drag-and-drop | Excludes non-drag pointer workflows and violates drag-alternative expectations | Select + cell + confirm path |
| Finalizing on `pointerdown` | Accidental actions cannot easily be canceled | Complete on `pointerup`/explicit confirm |
| Treating `pointercancel` as impossible | Browser can cancel gestures | Explicit cancel transition |
| Ignoring `lostpointercapture` | Can leave UI stuck in drag state | Terminal cleanup/reconciliation path |
| Applying `touch-action:none` to entire board/page | Needlessly suppresses browser gestures | Restrict it to true drag starters |
| Calling `preventDefault()` after pointerdown to “fix” scrolling | Gesture policy may already be decided | Declarative `touch-action` |
| Disabling pinch zoom in viewport meta | Accessibility regression | Keep browser zoom enabled |
| Using `event.target` to find cell during capture | Capture retargets pointer events | Map `clientX/Y` to board coordinates |
| Storing ship state as `left/top` pixels | Breaks on resize/responsive layout | Store row/column/orientation |
| DOM collision tests for legality | Couples rules to layout | Pure board-coordinate validation |
| Moving the authoritative ship during a preview | Rollback becomes error-prone | Keep original + candidate states |
| Two-finger rotation | Hidden gesture and multitouch complexity | Explicit Rotate action |
| Long-press-only menu | Poor discoverability and no obvious keyboard equivalent | Visible/contextual controls |
| All 100 cells in Tab order | Extremely inefficient keyboard navigation | Roving tabindex grid |
| Arrow keys both navigate and move ship silently | Mode ambiguity | Explicit Move mode |
| Removing unavailable cells from navigation | Makes prior results hard to inspect | Keep state perceivable |
| Color-only red/blue/green states | Excludes users who cannot distinguish them | Shape/icon/pattern + text |
| Live region on entire board | Excessive/repeated announcements | One deliberate status region |
| Toast-only critical errors | Easy to miss and may vanish | Persistent contextual state |
| Custom focus trap for every overlay | More brittle code | Native dialog/popover when appropriate |
| Outside-click closing destructive dialog | Easy accidental cancellation | Explicit confirm/cancel |
| Treating bottom sheet as its own semantic role | Visual form has no such accessibility semantics | Dialog, popover, or section based on behavior |
| `height:100vh` everywhere on mobile | Poor fit with dynamic browser UI | Consider `dvh` and flexible rows |
| Fixed button widths for English | Ukrainian/text zoom clips | Intrinsic sizing and wrapping |
| `overflow:hidden` to hide localization problems | Silently removes content | Flexible layout |
| Trusting `navigator.onLine` | Does not establish server reachability | Actual transport/request state |
| Optimistically marking a shot as hit/miss | Client does not own outcome | Pending → authoritative result |
| Retrying unknown shots blindly | Duplicate action risk | Command ID + resync |
| Multiple components calling backend independently | Ordering/conflict logic fragments | One gateway/API contract |
| Client-only expiry timer | Drift/background throttling/server disagreement | Server-authoritative deadline |
| Treating reconnect as “connected = current” | Messages may have been missed | Snapshot/revision resync |
| Hiding opponent ships only with CSS/ARIA | Data remains in client | Never send unrevealed data |
| Depending on `beforeunload` | Browser lifecycle is unreliable | Persistent server state |

The relevant standards behind the highest-risk pitfalls are Pointer Events capture/cancellation, WCAG dragging and pointer cancellation, the APG grid pattern, native dialog behavior, and the viewport/touch-action platform rules. ## Implementation trade-offs and unresolved product questions

**Semantic table grid versus `div`-based ARIA grid.** A CSS `div` grid gives extremely convenient exact 11×11 visual sizing, but it requires more hand-authored roles and relationships. A native `<table role="grid">` expresses Battleship's row/column structure in HTML, and APG provides a direct precedent where `tr`, `th`, and `td` imply the required row/header/gridcell roles. Direct source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/ citeturn15view0 **Recommendation:** start with semantic `<table role="grid">` and roving focus. Change only if real browser/assistive-technology testing demonstrates a material issue.

There is a second choice between focusing each `<td>` directly and placing a `<button>` inside every grid cell. APG permits either a focusable gridcell or a focusable widget contained by a cell, and its layout-grid examples explicitly use buttons and links inside cells. Direct sources: https://www.w3.org/WAI/ARIA/apg/patterns/grid/ and https://www.w3.org/WAI/ARIA/apg/patterns/grid/examples/layout-grids/ citeturn15view1turn15view2 **Recommendation:** focus the gridcells themselves for a uniform Battleship board unless production AT testing shows that native buttons materially improve interaction. The cell needs to remain navigable even after it becomes a non-actionable hit/miss result.

**Pointer capture owner.** Capturing on the ship itself is straightforward but can become awkward if the element is removed/reparented during the drag. Capturing on a stable board/interaction surface reduces lifecycle surprises. **Recommendation:** keep the actual DOM ship stable during an active pointer transaction and render a separate preview; whichever element owns capture should persist until completion.

**Drag quality versus browser manipulation.** `touch-action:none` over the entire board gives the application maximal gesture control but competes with normal browser pan/zoom. Restricting it to draggable ship handles preserves more native behavior but requires users to begin a drag precisely enough on a ship. **Recommendation:** use `touch-action:none` only on generous ship drag targets and make select-then-place the equally visible fallback. The standards basis for the trade-off is the declarative `touch-action` model. Direct source: https://www.w3.org/TR/pointerevents3/ citeturn15view4

**Optimistic setup versus server-confirmed setup.** Optimistic placement/movement feels immediate but requires rollback and revision handling. A stronger architectural option is to maintain setup as a local draft and submit the whole fleet atomically when the player chooses **Ready**, but that changes the backend contract and cannot be assumed from the current requirements. If the backend persists every edit, preserve pending/rollback states. If it supports atomic readiness, a local draft is likely simpler UX.

**Both boards on mobile versus board switching.** Showing both preserves situational awareness but makes cells smaller. Showing one dominant board keeps targeting usable but creates a navigation step to inspect the player's board. **Recommendation:** during battle, make the opponent board primary on narrow portrait screens and keep “Your board” immediately accessible as a labelled switch/section—not hidden behind a long press or obscure icon.

**Popup versus visible ship actions.** Hiding Move/Rotate/Remove in a contextual menu saves space but reduces discoverability. **Recommendation:** after a ship is selected, expose at least Rotate and Move/Remove in an obvious action strip or bottom sheet. A popover is reasonable for secondary actions, but no core action should exist solely behind a pointer-specific gesture.

**Motion versus feedback.** Ship snapping, hits, and sinking animations can make the game legible, but users may request reduced motion. **Recommendation:** let visual feedback primarily come from persistent state changes, with animation as enhancement. Honor `prefers-reduced-motion`. Direct source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion citeturn14search0

The following questions should be resolved in the product/API contract before implementation, because they directly change the frontend state machines:

| Unresolved question | Why it matters |
|---|---|
| What fleet composition and ship lengths are used? | Determines fleet controls, labels, validation and keyboard announcements |
| May ships touch diagonally or orthogonally? | Changes placement validator and invalid-reason messaging |
| Is there a final **Ready** step? | Determines whether setup is a local draft or a series of committed network edits |
| Can a Ready player become unready/edit again? | Determines whether Rotate/Move/Remove remain available |
| What exactly counts as “activity” for the 15-minute timeout? | Defines expiry timer reset behavior |
| Is activity based on browser input or accepted server requests? | Prevents client/server deadline disagreement |
| Does merely receiving opponent activity reset the local player's timeout? | Changes visible timer semantics |
| Is `expiresAt` supplied by the server? | Needed for an authoritative countdown |
| Can an anonymous session survive page refresh? | Determines token/session storage behavior |
| Can it be resumed on another tab/device? | Affects revision conflicts and session identity |
| Can one player have multiple active tabs? | Requires conflict policy |
| What happens when the opponent disconnects? | Pause, forfeit, continue waiting, or separate expiry rules |
| Does a lost connection pause the 15-minute timer? | Changes reconnect and expiry interaction |
| What happens when a shot was accepted but its response was lost? | Requires idempotency/status/revision reconciliation |
| What event ordering guarantee does near-realtime transport provide? | Determines event deduplication and gap detection |
| Are events replayable after reconnect? | Determines snapshot-versus-replay strategy |
| What revision/version primitive exists? | Determines safe concurrency handling |
| Which opponent ship details become visible on a hit? | Controls API privacy and accessible cell names |
| When a ship sinks, are all of its cells revealed immediately? | Changes result states and announcements |
| Is shooting an already-shot cell rejected locally, server-side, or both? | Determines unavailable-state behavior |
| What minimum browser versions are supported? | Determines whether newer dialog/popover features need progressive enhancement |
| Which browser/AT combinations are release targets? | Required because APG notes support differences across combinations citeturn15view2 |
| Must two boards always be simultaneously visible? | Major mobile layout constraint |
| May the game use audio or haptic feedback? | Requires non-audio equivalents and preference behavior |
| Is the language switch available during a live game? | Determines focus preservation and live re-localization |
| Are Ukrainian ship names fixed product terminology? | Needed before accessible labels and localization tests stabilize |

The strongest overall architecture is therefore a **semantic HTML application with a table-based ARIA grid; roving keyboard focus; Pointer Events plus pointer capture for optional drag; declarative, narrowly scoped `touch-action`; coordinate-based ship models; explicit non-drag alternatives; native `<dialog>`/Popover primitives where their behavior matches the UX; server-authoritative revisions, outcomes, and expiry; and a transport-independent game gateway**. That combination follows the platform instead of fighting it, while still providing the direct-manipulation behavior expected of a modern Battleship game. Its key standards foundations are Pointer Events, WCAG 2.2 Dragging Movements and Target Size, APG Grid and Dialog patterns, native dialog/popover behavior, responsive viewport/safe-area primitives, and reduced-motion preferences.
