# Deterministic Battleship Engine Testing Without a Database

## Recommended architecture and testing pyramid

The central testing decision should be architectural: **make the Battleship rules a pure state-transition component, and keep clocks, identifiers, session TTL, in-memory storage, concurrency control, HTTP/WebSocket transport, and Spring outside it**. That gives the rules engine a test surface that can run as ordinary JVM tests with no Spring context, server, database, network, scheduler, or wall clock.

A useful target shape is:

```text
                         ┌──────────────────────────┐
                         │ Browser / full-system    │
                         │ very few critical flows  │
                     ┌───┴──────────────────────────┴───┐
                     │ Contract + realtime integration │
                     │ API shapes, views, WS recovery  │
                 ┌───┴──────────────────────────────────┴───┐
                 │ Application tests                       │
                 │ sessions, TTL, idempotency, concurrency │
             ┌───┴──────────────────────────────────────────┴───┐
             │ DOMAIN TESTS — the large majority                │
             │ transitions, invariants, properties, models,     │
             │ editions, generators, mutation testing           │
             └───────────────────────────────────────────────────┘

                 Separate operational/stress lane:
                 capacity • heap • churn • concurrency stress
```

This follows the useful part of the test-pyramid heuristic: most assertions should live in small tests close to the logic, while progressively fewer tests should exercise broader stacks. Google likewise recommends keeping end-to-end tests relatively scarce because smaller tests are generally faster and more specific, while its later guidance emphasizes choosing test size according to reliability, fidelity and cost rather than treating a fixed ratio as a law. citeturn8search0turn8search3

For this system, I would divide responsibility as follows.

| Test family | What it owns | What it should **not** test |
|---|---|---|
| **Domain tests** | Battleship rules, fleet validity, shots, hits, misses, sinking, victory, phases, edition-specific behavior, hidden-information projection if that projection is a domain policy | Spring, HTTP, threads, TTL, real clocks |
| **Application tests** | Session creation/joining, in-memory repository behavior, TTL, deterministic IDs, idempotency, atomic application of commands, expiry races | Ship-placement geometry duplicated from domain tests |
| **Contract tests** | HTTP/JSON/WebSocket message schemas, status/error mapping, player-specific views, frontend assumptions | Reimplementation of the game rules in JavaScript |
| **Browser tests** | Rendering, interactions, reconnect UX, two-browser smoke flows | Exhaustive gameplay combinations |
| **Operational tests** | Heap/capacity bounds, session churn, leak detection, race stress, constrained-resource behavior | Fine-grained rule permutations |

Google's hermetic-testing guidance is particularly relevant here: tests become more repeatable when external services and networks are removed, and even broader server tests can be run hermetically where useful. citeturn8search2

The pure core can be as small conceptually as:

```java
public interface GameEngine {
    TransitionResult apply(
        GameState state,
        GameCommand command,
        RuleSet rules
    );
}

public record TransitionResult(
    GameState state,
    List<GameEvent> events
) {}
```

`GameEngine.apply()` should not call `Instant.now()`, `UUID.randomUUID()`, a repository, Spring, WebSocket code, or an uncontrolled RNG. The strongest domain-level determinism property then becomes:

\[
(state,\ command,\ rules) \rightarrow (newState,\ events)
\]

with identical inputs producing structurally identical outputs.

Clocks and session IDs belong one layer above:

```java
public final class SessionService {
    private final Clock clock;
    private final SessionIdSource ids;
    private final GameRepository games;
    private final GameEngine engine;

    // ...
}
```

Java explicitly provides `Clock.fixed(...)` for testing code that depends on current time, and `InstantSource` was designed to permit fixed or offset alternatives during tests. citeturn3search0turn3search12 For TTL boundary tests, a tiny mutable test clock is even more useful than `Clock.fixed`, because the test can advance time without sleeping.

Immutable state fits this architecture well, but Java records alone are insufficient for deep immutability. A Java record is only **shallowly immutable**; if a record contains a mutable `List`, its contents can still change. Oracle documents both this limitation and `List.copyOf`/`Map.copyOf`/`Set.copyOf` as ways to isolate collections from later mutation of their source containers. citeturn3search1turn10search0turn10search1turn10search2

Consequently, do not test immutability merely with `record` syntax. Test the actual aliasing boundary: mutate input collections after constructing `GameState`, attempt mutation through exposed collections, and retain a reference to the old state across a transition and prove its structural value has not changed.

## Deterministic fixtures, clocks, identifiers, and randomness

The most maintainable strategy is to **separate deterministic rule fixtures from random fleet-generation tests**. Most engine tests should use fully explicit fleet layouts. Only the fleet-generator test suite should depend directly on seeded pseudorandom generation.

### Canonical fixture set

Maintain named fixtures as code or small JSON/YAML resources, for example:

| Fixture | Purpose |
|---|---|
| `standard_opening` | Completely valid fresh game |
| `edge_and_corner_fleet` | Ships starting/ending on board edges |
| `horizontal_vertical_mix` | Both permitted orientations |
| `minimum_separation` | Exact adjacency boundary for editions that restrict touching |
| `touching_legal` | Positive fixture for editions that permit touching |
| `win_in_one` | Opponent has exactly one unhit cell remaining |
| `one_ship_sunk` | Sunk-state projection and notifications |
| `duplicate_shot_state` | Target coordinate already fired upon |
| `max_history` | Maximum legitimate game progression |
| `hidden_information` | Opponent fleet deliberately easy to detect if leaked |

A fixture should state the edition explicitly:

```text
fixture:
  ruleset: CLASSIC_V1
  currentPlayer: P1
  p1Fleet: ...
  p2Fleet: ...
  p1Shots: ...
  p2Shots: ...
```

That prevents a future edition change from silently changing the interpretation of old tests.

### Seeded generator strategy

A generator can have an interface such as:

```java
Fleet generateFleet(RuleSet rules, RandomGenerator random);
```

Tests may pass `new Random(seed)`. Java specifies that two `java.util.Random` instances created with the same seed and invoked with the same sequence of methods return the same sequence, and the class specifies its algorithm for portability. citeturn12view0

Use the seed for **reproduction**, not as the primary rule oracle. Recommended generator checks are:

1. for thousands of seeds, the generated fleet satisfies every fleet invariant;
2. running a particular seed twice produces the same fleet;
3. selected regression seeds cover historically interesting cases;
4. a very small number of golden seeds may assert an exact layout if algorithm stability is intentionally part of the contract.

Do **not** make hundreds of ordinary rule tests depend on exact output from seed `42`. If the fleet-generation algorithm is legitimately improved, that creates needless fixture churn. Explicit board fixtures are much more stable.

For property-based tests, jqwik already records the random seed that generated a failing case, supports fixed seeds and previous-seed reruns, injects edge cases, and shrinks failures toward simpler counterexamples. Its current documentation states a default of 1,000 tries per property unless configured otherwise. citeturn2view2turn2view3

A useful policy is therefore:

```text
Normal domain examples        → named explicit fleets
Property tests                → generated states/commands, failure seed retained
Fleet generator tests         → explicit seeded RNG
Production fleet generation   → injected RNG source
Session/token security        → SecureRandom or equivalent, outside game rules
```

Do not substitute a test-seeded game PRNG for security-sensitive session credentials. Oracle distinguishes `Random`, which is not cryptographically secure, from `SecureRandom`, whose output is intended for security-sensitive randomness. citeturn12view0turn4search4

### Deterministic clock

For application tests, use a controllable clock:

```java
final class TestClock extends Clock {
    private Instant current;
    private final ZoneId zone;

    TestClock(Instant current) {
        this(current, ZoneOffset.UTC);
    }

    TestClock(Instant current, ZoneId zone) {
        this.current = current;
        this.zone = zone;
    }

    void advance(Duration duration) {
        current = current.plus(duration);
    }

    @Override
    public Instant instant() {
        return current;
    }

    @Override
    public ZoneId getZone() {
        return zone;
    }

    @Override
    public Clock withZone(ZoneId newZone) {
        return new TestClock(current, newZone);
    }
}
```

Then a 15-minute TTL test takes microseconds rather than 15 minutes:

```java
createSession();
clock.advance(Duration.ofMinutes(14).plusSeconds(59));
assertSessionExists();

clock.advance(Duration.ofSeconds(1));
assertSessionExpiredAccordingToBoundaryPolicy();
```

You need one explicit product decision here: whether expiry means

```text
now - lastActivity >= 15 minutes
```

or

```text
now - lastActivity > 15 minutes
```

That single comparison deserves an exact boundary test because mutation testing will typically expose an inadequately tested `>`/`>=` distinction.

### Deterministic identifiers

Inject identifier production as an interface:

```java
interface SessionIdSource {
    SessionId next();
}
```

A test implementation can yield:

```text
SESSION-A
SESSION-B
SESSION-C
```

Likewise, command identifiers should come from callers or an injectable source rather than being invented inside the rules transition.

This makes snapshots, assertions, serialization fixtures and retry tests stable. It also allows deliberate collision tests.

## Domain invariant catalog, properties, editions, fuzzing, and mutation testing

Example-based tests are necessary for readable specification examples, but the Battleship state space is much larger than a useful hand-written example set. Property-based testing is therefore particularly valuable. jqwik is built for property-based testing on the JVM and supports generated parameters, edge cases, shrinking, replay of failing seeds and stateful testing. citeturn0search1turn2view2turn2view3

### Domain invariant catalog

The following invariants should be represented explicitly in test code, ideally as reusable assertion functions such as `GameInvariants.assertValid(state, rules)`.

| Area | Invariant |
|---|---|
| Ruleset | Every game identifies exactly one supported ruleset/edition. |
| Board | Every occupied ship cell is inside the edition's board bounds. |
| Fleet | Fleet composition matches the edition's configured ship multiset. |
| Ship size | Each ship contains exactly the number of cells prescribed by its type. |
| Geometry | Each ship has legal shape/orientation for that edition. |
| Contiguity | Where ships are straight vessels, their cells are contiguous without gaps. |
| Overlap | No board coordinate belongs to two different ships. |
| Adjacency | If an edition forbids touching, no prohibited adjacency occurs; if it permits touching, the engine must not accidentally impose this constraint. |
| Shot bounds | Every accepted shot targets a valid board coordinate. |
| Shot ownership | A player's shot history contains only shots made by that player. |
| Hit correctness | Every recorded hit corresponds to an occupied opponent cell. |
| Miss correctness | Every miss corresponds to an unoccupied opponent cell. |
| Partition | A shot cannot simultaneously be both hit and miss. |
| Sinking | A ship is sunk iff every required ship cell has been hit, subject to the edition's sinking rule. |
| Phase | Only commands legal in the current phase can alter game state. |
| Actor | Only an actor permitted by the current rules can execute the command. |
| Turn | Turn progression follows the selected edition's rules. |
| Duplicate target | Repeated targeting behaves exactly as that edition specifies and never double-counts damage. |
| Terminal state | No gameplay command changes a finished game. |
| Winner | A winner exists only when the edition's victory predicate has been met. |
| Single winner | Normal two-player terminal state cannot name both players as winner. |
| Monotonic damage | Once a cell has been hit it never becomes unhit. |
| Monotonic sinking | Once a ship is sunk it never returns to afloat. |
| Version | Every accepted state-changing application increments the game's logical version exactly according to protocol; rejection does not masquerade as a new game transition. |
| Determinism | Identical state + command + rules produce equal transition results. |
| Immutability | Applying a command cannot alter the value represented by the input state. |
| Hidden information | A player's view contains only opponent information made observable by the edition's rules. |
| Projection consistency | Public/player projections describe the same underlying shot outcome without revealing forbidden private state. |

Several entries deliberately say “according to the edition.” Do not encode “one shot always changes turns,” “ships can never touch,” or another edition-dependent convention as a global invariant unless every supported edition actually guarantees it.

### High-value property-based tests

The best properties avoid rebuilding the production algorithm inside the test.

**Determinism**

```text
apply(S, C, R) == apply(S, C, R)
```

for arbitrary valid `S`, command `C`, and ruleset `R`.

**Input preservation**

```text
before = structuralSnapshot(S)
apply(S, C, R)
structuralSnapshot(S) == before
```

This verifies semantic immutability without requiring that the new state be a physically deep copy.

**Generator validity**

```text
for every generated fleet F:
    all fleet invariants hold
```

This is more powerful than asserting only a few exact generated layouts.

**Accepted-shot partition**

After any accepted shot at coordinate `c`, exactly the edition-defined outcome holds. For a classic hit/miss edition:

```text
occupied(c) XOR miss(c)
```

and exactly one new distinct shot is represented.

**Rejected-command stability**

For every command rejected because of wrong actor, wrong phase, invalid coordinate, already-finished game or another domain precondition:

```text
result.state == input.state
```

apart from explicit metadata that the design intentionally treats as separate from game state.

**Damage monotonicity**

```text
oldHits ⊆ newHits
oldSunkShips ⊆ newSunkShips
```

for every accepted gameplay transition.

**Victory equivalence**

For valid states constructed near completion:

```text
victoryPredicate(opponent) ⇔ terminalWinner == attacker
```

Use an independently represented test fixture rather than calling production `isDefeated()` as the test oracle.

**Projection noninterference**

Take two internally different opponent fleets that are observationally indistinguishable to player P1 at the current shot history. Their P1 views should be equal with respect to unrevealed information:

```text
projectFor(P1, S1) == projectFor(P1, S2)
```

This is an unusually strong hidden-information test. It catches leaks that ordinary snapshot tests may miss.

**Serialization semantics**

For public DTO `D`:

```text
decode(encode(D)) == D
```

where equality is semantic equality, not necessarily byte-for-byte JSON equality.

**Edition polymorphism**

Generate the same abstract command against multiple `RuleSet` values, then verify universal invariants while applying edition-specific expected behavior only where the configurations differ.

### Fuzzing invalid commands

Property-based testing is good for *structured* generation. Coverage-guided fuzzing adds another attack surface: malformed and unexpected data.

Jazzer integrates with JUnit and runs `@FuzzTest` methods in two modes: coverage-guided fuzzing and regression mode over previously retained findings. The latter makes discovered inputs ordinary repeatable regression tests. citeturn6search0turn6search1

Good fuzz targets are the boundary parsers, not just `GameEngine` methods accepting already-valid value objects:

```text
coordinate parser
JSON command decoder
edition identifier parser
command discriminator
session ID parser
WebSocket message parser
```

Fuzz coordinates including:

```text
negative row/column
Integer.MIN_VALUE / MAX_VALUE
zero and exact upper boundary
very long strings
empty values
Unicode homoglyphs
A0 / A-1 / Z999999...
embedded NUL/control characters
duplicate JSON fields
unknown command names
null fields
extra fields
oversized arrays
```

A fuzz invariant should be stronger than “does not crash”:

```text
Malformed input:
  → deterministic validation error
  → no persistent state change
  → no private-data disclosure
  → bounded resource consumption
```

Jazzer's retained corpus is particularly useful here because a discovered pathological coordinate or JSON command becomes a deterministic fixture on subsequent JUnit runs. citeturn6search0

### Mutation testing

Line and branch coverage should remain diagnostics, not the acceptance definition. Run PIT against the rules package. PIT deliberately introduces mutations into JVM code and checks whether the test suite detects them, making it a direct test of assertion effectiveness rather than merely whether execution passed through a line. citeturn0search2turn0search14

Battleship has especially meaningful mutation operators:

```text
<  ↔ <=        board/TTL boundary
== ↔ !=        coordinate and ownership checks
true ↔ false   sunk/finished flags
+1 removed     turn/version progression
condition negated
method return replaced
collection test inverted
```

Surviving mutations around these operations should normally trigger either a new example test or a stronger invariant/property.

Because mutation testing consumes substantially more CPU than ordinary unit tests, a sensible limited-hosting CI policy is:

```text
Every change:
  JUnit domain + application + contract tests
  property regression runs
  Jazzer regression corpus

Important PR / affected rules package:
  PIT on changed domain package

Scheduled CI:
  full PIT suite
  longer fuzzing
  jcstress / load / heap tests
```

Do not adopt an arbitrary “100% mutation score” goal. Equivalent or irrelevant mutants exist; instead establish a baseline, inspect surviving mutations in rule-bearing code and treat important survivors as specification gaps.

## State-machine model and concurrency testing

### Reference state-machine model

Model-based testing should exercise *sequences* rather than isolated calls. jqwik provides stateful-testing facilities including actions, invariant checking and rerunning falsified action chains; its current 1.10.1 documentation still labels the newer stateful-testing API experimental, so a project that wants a conservative dependency boundary can also implement a tiny reference model manually while using jqwik only to generate/shrink action sequences. citeturn2view0

A useful abstract game model is:

```text
             create/setup
     ┌──────────────────────────┐
     ▼                          │
  SETUP / WAITING ──ready────► ACTIVE(P1/P2)
                                 │
                         accepted command
                                 │
                      ┌──────────┴─────────┐
                      ▼                    ▼
                ACTIVE(P1/P2)         FINISHED
                                           │
                                           │ no gameplay
                                           ▼
                                        FINISHED
```

Session expiry should **not** be put into this domain model if TTL is an application concern. Model that separately:

```text
ABSENT ──create──► LIVE
                    │
            activity│ refresh deadline
                    │
                    ├──expire──► EXPIRED/ABSENT
                    │
                    └──command──► LIVE
```

For domain model-based testing, keep the reference representation deliberately different from production. For example:

```java
record ModelGame(
    Phase phase,
    Player turn,
    Set<Coordinate> p1Shots,
    Set<Coordinate> p2Shots,
    Set<Coordinate> p1ShipCells,
    Set<Coordinate> p2ShipCells,
    Optional<Player> winner
) {}
```

A known fixture lets the test oracle determine a hit with simple set membership:

```text
shot is hit ⇔ targetShipCells.contains(coordinate)
```

and a simple map from ship identifier to cell set can independently decide sinking. This is preferable to instantiating production `Ship`, `Board` and `DamageCalculator` classes inside the reference model, which would make the oracle too similar to the implementation.

Generate action chains containing legal and illegal transitions:

```text
join
ready
shoot(valid)
shoot(outOfBounds)
shoot(previousCoordinate)
shootAsWrongPlayer
shootAfterFinished
repeatSameCommandId
```

After **every action**, call the invariant catalog, not merely an expected final-state assertion. This frequently shrinks failures to much more useful sequences such as:

```text
ready
P1 shoots A1
P1 shoots A1 again
```

rather than a 200-command random history.

### Application concurrency boundary

The pure immutable rules engine itself does not need locks. Concurrency belongs where an old immutable `GameState` is replaced by a new one in the in-memory repository.

A desirable conceptual operation is:

```text
load current state
validate command against current state
apply pure transition
publish new state
publish corresponding event
```

as one linearized per-game mutation.

`ConcurrentHashMap.compute(...)` is one Java mechanism for achieving atomic per-key computation: Oracle documents the complete `compute` invocation as atomic for the mapping, while warning that its function should remain short and simple. An `AtomicReference<GameState>` with compare-and-set is another possible mechanism when the critical state fits a single reference. citeturn9search3turn9search4

Do not mistake `ConcurrentHashMap` itself for complete game atomicity. A sequence such as independent `get()` → compute → `put()` calls is not automatically one atomic transition. Java's generic `Map` interface explicitly does not promise atomicity for these default operations unless the concrete implementation documents it. citeturn9search6

### Concurrency test matrix

Tests should synchronize worker threads with a barrier so that the commands really compete, then assert the *set of allowed outcomes*, rather than whichever winner your laptop happened to schedule first.

| Race | Required invariant/outcome |
|---|---|
| Current player sends two different shots simultaneously | In a one-shot-turn edition, exactly one transition wins; the other is evaluated against the newer state and fails as stale/wrong-turn. |
| P1 and P2 shoot simultaneously | Only command(s) legal under that edition's current state may commit. |
| Same `commandId`, same payload, two threads | Gameplay effect occurs once. Both callers receive the same semantic result or one receives an explicit “already processed” result pointing at that result. |
| Same `commandId`, different payload | Never process both. Return deterministic idempotency-key conflict. |
| Same coordinate, two distinct IDs | Edition-defined duplicate-shot semantics apply once; damage cannot double-count. |
| Winning shot versus another shot | Exactly one terminal history is produced; no shot may mutate the game after the winning transition linearizes. |
| Shot versus session expiry | Exactly one ordering wins: either command linearizes first and refreshes activity, or expiry removes the session first. **Never resurrect an expired session accidentally.** |
| Reconnect/read versus shot | Reader may see pre- or post-shot snapshot, but never a structurally torn state. |
| Commands on different games | Correctness is independent; one game's lock/atomic reference must not mix state with another. |
| Two joins for final player slot | Exactly one identity acquires the slot. |
| Expiry cleanup versus duplicate retry | Cannot recreate the old session from dedupe metadata after expiry. |

For deterministic unit-level races, use `CountDownLatch`, `CyclicBarrier` or `Phaser` to stage the critical section. Then add stress testing because no finite schedule test can cover all possible JVM memory interleavings.

OpenJDK's `jcstress` exists specifically for concurrency-correctness stress testing on the JVM and is a strong fit for testing a custom `GameCell`, CAS loop, per-game state holder or other low-level concurrency primitive. citeturn0search3turn0search7

The split should be:

```text
GameEngine                      → ordinary deterministic tests
InMemoryGameStore API          → barrier-controlled JUnit races
custom atomic synchronization  → jcstress
full HTTP simultaneous shots   → a small number of integration tests
```

### Duplicate commands and idempotency

Do not conflate domain legality with transport retries. A player may make one logical `Shoot(A5)` command while HTTP/WebSocket delivery sends it twice.

Model the application command with something like:

```text
commandId
gameId
actorId
expectedVersion   (optional but useful)
payload
```

Then retain enough deduplication information during the session lifetime to enforce:

```text
same commandId + same semantic payload
    → same logical effect, no additional event

same commandId + different payload
    → conflict, no new effect
```

HTTP itself defines idempotency in terms of multiple identical requests having the same intended server effect. POST is not inherently idempotent, so application-level idempotency is appropriate for a POST-like gameplay command. An IETF HTTPAPI draft specifically describes an `Idempotency-Key` header for making otherwise non-idempotent operations fault tolerant; because it remains a draft rather than a final RFC, adopting the header name should be treated as a protocol choice rather than a requirement. citeturn7search4turn7search2

## Realtime ordering, expiry, and capacity

Near-realtime delivery should transmit **authoritative consequences of committed state changes**, not become a second mutation path.

A robust envelope is:

```json
{
  "gameId": "G-123",
  "version": 17,
  "eventId": "G-123:17",
  "type": "SHOT_RESOLVED",
  "view": { "...player-safe representation..." }
}
```

or, for delta-style messages:

```json
{
  "gameId": "G-123",
  "fromVersion": 16,
  "toVersion": 17,
  "type": "SHOT_RESOLVED",
  "payload": {}
}
```

WebSocket defines an ordered message transport while a connection exists; RFC 6455 requires message fragments to be delivered in the order sent. However, game-state replay and recovery after reconnect are outside the Battleship application semantics defined by WebSocket itself. It follows that versioning, replay, resynchronization and duplicate suppression should be application-level protocol features. citeturn7search0turn7search3

### Realtime test matrix

| Scenario | Test oracle |
|---|---|
| Single accepted transition | Exactly one new logical game version becomes observable. |
| Two sequential transitions | Client receives/observes monotonically increasing versions. |
| Rejected command | No gameplay delta pretending that state changed. |
| Same idempotent command retried | No second logical game transition/event. |
| Duplicate event frame delivered to client | UI state remains unchanged after first application. |
| `v17` arrives after client already has `v18` | Client ignores stale update. |
| Client receives `v18` while holding `v16` | Detect gap; do not blindly treat `v18` as a complete delta if it requires `v17`; request snapshot/resync. |
| Disconnect before receiving committed event | Reconnect obtains authoritative state containing the committed transition. |
| Disconnect after server commit but before acknowledgment | Retried command is idempotent; reconnect converges to the committed state. |
| Reconnect with current version | No unnecessary state regression or duplicated effect. |
| Reconnect with replayable old version | Replay exactly the missing range in order, if replay is supported. |
| Reconnect older than retained replay window | Send authoritative snapshot instead of incomplete replay. |
| Snapshot races with live event | Client ends at newest version regardless of whether snapshot or event completes first. |
| Old socket delivers delayed message after new socket is active | Version check prevents rollback. |
| Two tabs for same player | Both converge to identical player-safe views. |
| Player-specific event | P1's message cannot contain P2-only secret data and vice versa. |
| Game expires while socket remains open | Client receives/observes deterministic expiry semantics and cannot keep issuing valid gameplay commands. |
| Reconnect after expiry | Returns expired/not-found contract; must not recreate state. |

Spring's own WebSocket/STOMP testing documentation distinguishes server-side message-handler tests from full end-to-end tests with a real client and server. That distinction maps well here: most realtime logic should be tested below the browser, with only a few true client/server tests. citeturn5search3

Playwright can also intercept or mock WebSocket traffic, which is useful for frontend tests of gaps, duplicates and reconnect ordering without standing up a second fake game engine. citeturn5search4

### TTL policy

A 15-minute inactivity TTL sounds simple but is underspecified until “activity” is defined. Make that definition part of the application contract.

A sensible resource-oriented policy would be:

| Action | Suggested TTL effect |
|---|---|
| Session creation | Set `lastActivity = now`. |
| Player joins | Refresh. |
| Valid gameplay command | Refresh. |
| Idempotent retry of a real client interaction | Either refresh or not; choose explicitly and test it. |
| Explicit reconnect/session fetch by authenticated participant | Usually refresh. |
| Server-to-client push | **Do not** refresh by itself. |
| WebSocket ping/pong heartbeat | Prefer not to refresh game inactivity by itself, otherwise an abandoned open tab can keep a game alive indefinitely. |
| Malformed unauthenticated traffic | Do not refresh. |
| Scheduler inspection | Do not refresh. |

The exact policy is a product decision, but the principle is important: TTL must depend on the injected `Clock`, never on sleeps.

### TTL and capacity test matrix

| Scenario | Setup | Expected |
|---|---|---|
| Just before expiry | `lastActivity + 15m - ε` | Live. |
| Exact boundary | exactly `+15m` | Defined explicitly by chosen `>=`/`>` policy. |
| Just after expiry | `+15m + ε` | Expired. |
| Activity before boundary | advance to `14m59s`, perform qualifying action | Deadline moves forward. |
| Non-qualifying heartbeat | heartbeat near deadline | Deadline unchanged. |
| Expired lookup | advance beyond TTL | Not returned as live. |
| Expired command | issue shot after expiry | No transition; no session resurrection. |
| Expiry is idempotent | cleanup same game repeatedly | Same final result; no exception/leak. |
| Concurrent command/expiry | barrier race | One legal linearization; never partial state. |
| Expire then reuse old command ID | old dedupe key retained accidentally | Must not recreate session. |
| Many sessions expire together | same timestamp cohort | All eligible entries reclaimed within defined sweep semantics. |
| Session at capacity | fill to configured maximum | Existing games continue correctly. |
| One over capacity | attempt new game | Deterministic admission failure, not OOM. |
| Expiry frees capacity | expire one, create another | New session accepted. |
| High churn | repeatedly create/play/expire | Repository/subscriber/dedupe/replay counts return near baseline. |
| Maximum legal game | worst-case shot history | State remains bounded. |
| Invalid-command flood | millions of malformed/rejected commands | No persistent per-command memory growth. |
| Reconnect churn | repeated socket attach/detach | Subscriber objects are removed. |
| Replay buffer limit | exceed retained event window | Old events discarded and reconnect falls back to snapshot. |
| Dedupe cache limit | many unique command IDs | Storage bounded by explicit policy. |
| Constrained heap | run realistic max sessions in small `-Xmx` fork | Satisfies capacity target without OOM and with acceptable headroom. |

Capacity correctness should primarily be asserted through **deterministic counts**:

```text
number of live sessions
number of subscriber registrations
dedupe entries/game
replay events/game
shots/game
stored command results/game
```

rather than demanding an exact heap-byte number from an ordinary JUnit test. JVM memory measurements involve allocation, GC and runtime effects; `MemoryMXBean` exposes JVM memory usage but is fundamentally a monitoring interface, and pool usage can be a best-effort estimate. citeturn3search6turn3search26

For the operational lane, run a forked JVM with the same tight heap budget planned for hosting and record Java Flight Recorder data. Oracle describes JFR as a JVM-integrated diagnostic/profiling facility that captures thread, lock and garbage-collection information; it is much more appropriate for answering “do 5,000 sessions cause unacceptable allocation/GC behavior?” than embedding fragile heap-byte assertions in domain tests. citeturn11search9

A particularly important capacity invariant for this architecture is:

```text
memory per session must have an upper bound
```

That means bounding not just board state but also auxiliary structures:

```text
event replay history
idempotency/command-result cache
connected-client registry
pending outbound messages
diagnostic histories
```

A finite board naturally bounds legitimate Battleship moves if duplicate damage is prevented, but protocol metadata can still grow without bound if every arbitrary command ID or outbound event is retained forever.

## Contracts, serialization, hidden information, and browser testing

The frontend requirement—**no second copy of Battleship rules**—should directly shape the wire contract.

The browser should send **intent** and render **server-authoritative state**:

```text
Frontend:
  "player selected A5"
          │
          ▼
POST /games/G/commands
{
  "commandId": "...",
  "type": "SHOOT",
  "coordinate": "A5"
}
          │
          ▼
Backend rules engine:
  validates turn
  validates coordinate
  resolves hit/miss
  resolves sinking
  resolves winner
  advances turn
          │
          ▼
Player-safe response/event
```

The browser may perform presentation-only checks such as “is this string parseable as a board coordinate?” but should not own rules such as:

```text
Is it my turn?
Does this edition permit another shot?
Is this ship sunk?
Has the player won?
Is this coordinate legally targetable under special-edition rules?
What information about the opponent may be shown?
```

Prefer the server to expose the information needed to render those decisions:

```json
{
  "gameId": "G-1",
  "version": 12,
  "phase": "ACTIVE",
  "viewer": "PLAYER_1",
  "yourTurn": true,
  "allowedActions": ["SHOOT"],
  "ownBoard": { "...": "..." },
  "opponentKnowledge": { "...": "..." }
}
```

For complex edition-specific targeting rules, `allowedActions` can be richer:

```json
{
  "shoot": {
    "enabled": true,
    "allowedTargets": ["A2", "A3", "B7"]
  }
}
```

On a Battleship-size board, sending an authoritative allowed-target set is inexpensive and removes pressure to recreate legal-move logic in TypeScript.

### Contract-test strategy

Use two complementary contracts.

**Schema contract:** maintain an OpenAPI description for HTTP DTOs. OpenAPI is specifically a language-independent description of HTTP APIs, which makes it suitable for generating or validating frontend types without embedding gameplay logic. The current OpenAPI specification line includes version 3.2.0. citeturn5search6

**Consumer contract:** use Pact for the interactions the frontend actually consumes. Pact's model is consumer-driven: frontend tests state the requests and responses they depend upon, and provider verification checks that the backend implements those contracts. Pact JVM provides provider verification independently of needing a browser. citeturn5search1turn5search5turn5search9

The split is useful:

```text
OpenAPI
  → broad structural API definition
  → generated TypeScript/Java DTO compatibility
  → enums, required fields, response schemas

Pact
  → "the browser actually depends on these interactions"
  → provider verification against backend adapters
  → protects consumer assumptions from accidental breaking changes

Domain tests
  → actual Battleship truth
```

Neither OpenAPI nor Pact should become a second game engine.

### Canonical frontend fixture catalog

Have the backend contract module publish player-safe JSON examples for states such as:

```text
waiting_for_opponent.json
your_turn.json
opponents_turn.json
shot_miss.json
shot_hit.json
ship_sunk.json
game_won.json
game_lost.json
session_expired.json
reconnected_snapshot.json
version_gap.json
```

Frontend component tests consume these fixtures.

The UI test oracle is then:

```text
Given backend fixture X,
does the browser render X correctly?
```

not:

```text
Given a board and shot,
can JavaScript independently calculate what the backend should have done?
```

That distinction is the key to avoiding a second rules implementation.

### Serialization round trips

Do serialization testing at adapter boundaries.

For every public DTO:

```text
DTO
 → JSON
 → DTO
 → semantic equality
```

Also retain golden JSON fixtures for contract-critical cases, especially enum names and optional/required fields.

Jackson's `ObjectMapper` is explicitly the component responsible for binding Java objects to/from JSON representations, so round-trip tests around those DTOs are straightforward and do not require an HTTP server. citeturn3search7

Do **not** automatically Jackson-annotate the pure domain model merely so it can cross the network. A cleaner separation is:

```text
Domain GameState
    │
    ▼ mapper/projector
PlayerGameView DTO
    │
    ▼ Jackson
JSON
```

Then separately test:

```text
GameState → correct PlayerGameView
PlayerGameView → correct JSON contract
```

Internal `GameState` serialization need only be tested if the implementation actually serializes it for snapshots, debugging or replay. With a purely in-memory, no-database design it is unnecessary to create a persistence serialization contract that the application does not use.

### Hidden-information tests

Hidden information deserves **negative** assertions, not just snapshot approval.

For each game state generate at least:

```text
viewFor(P1)
viewFor(P2)
spectator/public view, if one exists
realtime event for P1
realtime event for P2
command response for P1
command response for P2
```

Then verify that before information is legally revealed:

```text
P1 response has no coordinates of P2's unhit ships
P2 response has no coordinates of P1's unhit ships
no opponent internal fleet ID leaks
no fleet-generation seed leaks
no private placement structure leaks through "allowed" metadata
no hidden coordinates appear in WebSocket deltas
error messages do not reveal whether an unobserved cell contains a ship
```

The strongest property test is observational equivalence:

```text
S1 and S2 differ only in opponent information
that P1 has not discovered

⇒

projectFor(P1, S1) == projectFor(P1, S2)
```

This tests the *absence* of information rather than keeping a blacklist of field names.

Hidden-information testing should also cover invalid commands. For example, shooting an invalid/already-used coordinate must not return different error timing or payload depending on whether an undisclosed ship is present there unless the game rules intentionally reveal that fact.

### Browser tests

Keep browser tests small. Playwright's own documentation recommends locator/web-first assertions rather than brittle timing-based waits; that is especially relevant for near-realtime games where `sleep(1000)` style synchronization creates flaky tests. citeturn5search0turn5search12

A compact browser suite should cover:

| Browser scenario | Backend mode |
|---|---|
| Waiting screen renders | Contract fixture/mock |
| Player can select and send a shot intent | Contract fixture/mock |
| Hit/miss/sunk server states render correctly | Contract fixtures |
| Controls disabled according to server-provided capabilities | Contract fixtures |
| Duplicate realtime message does not duplicate UI state | Mocked WebSocket |
| Version gap triggers resync UX | Mocked WebSocket |
| Disconnect/reconnect recovers | Mocked WebSocket + one real-server test |
| P1 cannot see hidden P2 fleet data | Inspect network response + rendered DOM |
| Two real browsers complete a small game | Real hermetic server |
| Expired session UX | Real or deterministic test endpoint/fake clock in test profile |

The full two-browser test should prove the integration path, not exhaustively prove the rules. Rule correctness belongs below HTTP where thousands of deterministic cases can run cheaply.

### Recommended CI gates

A resource-conscious pipeline can separate fast deterministic correctness from expensive exploration:

| Gate | Contents |
|---|---|
| **Developer / every commit** | Domain JUnit tests, edition tests, application fake-clock tests, serialization tests, contract tests, saved jqwik counterexamples, Jazzer regression corpus |
| **Pull request** | All above + property suite + focused PIT on changed rule packages + deterministic concurrency tests |
| **Scheduled** | Full mutation suite, longer randomized/property runs, coverage-guided Jazzer run, jcstress |
| **Release / infrastructure change** | Real HTTP/WebSocket tests, two-browser Playwright flows, constrained-heap capacity and churn tests, JFR recording |
| **Production smoke** | Startup/health/protocol wiring only; do not play synthetic games against real user state |

The important quality signals should therefore be a portfolio rather than a single coverage percentage:

```text
examples passing
+ invariant coverage
+ generated property distributions
+ mutation score / survivor review
+ fuzz corpus
+ state-machine action coverage
+ concurrency outcome coverage
+ contract/provider verification
+ bounded-capacity evidence
+ a small number of browser journeys
```

jqwik can collect and report statistics about generated classifications, which is useful for proving that properties really exercised cases such as edge coordinates, duplicate shots, terminal states and different editions rather than producing 1,000 superficially random but equivalent examples. citeturn2view3
