# Independent Contract-First React Frontend for a Server-Authoritative Battleship Game

**Research baseline: 18 August 2026.**

The strongest architecture for this product is a **contract-first React/TypeScript SPA with ports at external I/O boundaries, TanStack Query owning authoritative server snapshots, ordinary React state owning transient UI state, a single game-level realtime synchronization coordinator, generated HTTP code hidden behind an adapter, and runtime validation of every REST and event payload before it enters application state**.

The frontend should deliberately contain **no Battleship engine**. It may render legal actions and provide interaction previews, but hit/miss/sunk/turn/winner/placement validity must remain server decisions. Realtime messages should primarily make the cached server snapshot fresher rather than force the browser to reproduce server transitions.

## Architectural conclusion

### Facts

Ports and adapters are a good fit for the *integration edges* of this frontend. Alistair Cockburn's original description defines a port as a purposeful conversation with the outside world and allows multiple adapters to satisfy the same port. That maps naturally to `GameApi`, `GameEventStream`, `SessionCredentialStore`, and `RuntimeConfig`, with browser/network implementations in production and deterministic substitutes in tests. It does **not** imply that every component, hook, or utility needs an interface. citeturn13search0

OpenAPI provides a language-agnostic HTTP API description independent of implementation source code, while AsyncAPI provides the analogous machine-readable description for message-driven APIs and explicitly supports protocols including WebSockets. OpenAPI 3.1.x aligns its Schema Object dialect with JSON Schema 2020-12. citeturn13search2turn16search2turn16search3

TanStack Query explicitly positions itself around fetching, caching, synchronizing, and updating **server state**, including the problem that such state is remotely owned and may change without the current browser knowing. That is almost exactly the state model of this game: the browser holds a projection of a game whose authoritative state lives elsewhere. citeturn14search0

### Recommendation

Use this dependency direction:

```text
React UI
   │
   ▼
frontend application hooks / orchestration
   │
   ├──── TanStack Query ──── authoritative server snapshots
   │
   ▼
frontend-owned ports
   │
   ├── GameApi
   ├── GameEventStream
   ├── SessionCredentialStore
   └── RuntimeConfig
          │
          ▼
adapters
   ├── generated OpenAPI HTTP client + runtime validators
   ├── WebSocket/SSE implementation
   ├── browser session storage
   └── runtime config loader
          │
          ▼
VERSIONED REST + REALTIME CONTRACT
          │
          ▼
backend implementation
```

The critical architectural boundary is therefore **not React versus Java**. It is:

> **Frontend ↔ versioned wire contract ↔ backend.**

No frontend production module should know whether the server is Java, Kotlin, Go, Node.js, Rust, or something else. Conversely, no backend implementation class should be a source from which frontend code directly imports or derives runtime assumptions.

### Recommended decision set

| Concern | Decision |
|---|---|
| Authoritative game state | Server; cached in TanStack Query |
| Shared frontend client state | Avoid a global store until one is demonstrably needed |
| Screen-local interactions | `useState`; `useReducer` for genuinely state-machine-like local interaction |
| HTTP | OpenAPI-generated TypeScript client behind `GameApi` adapter |
| Runtime safety | Validate all external JSON before caching/using it |
| Realtime | One game-level synchronization subscription per active game per browser document |
| Event semantics | Prefer versioned “state changed” notifications plus authoritative snapshot retrieval |
| Concurrency | Monotonic `gameVersion` + command idempotency + expected-version precondition |
| Anonymous credential | Opaque short-lived capability; memory + `sessionStorage` for the portable separate-hosting profile |
| Tabs | Do not make shared browser storage authoritative; optionally coordinate via `BroadcastChannel` |
| Testing | Contract-valid fixtures, network/adaptor mocks, and real-backend E2E; never a fake Battleship engine |
| Deployment | One frontend build artifact, environment-specific runtime configuration |
| Version compatibility | API major at transport boundary; contract artifact additionally versioned as a release |

### Trade-off

This architecture adds several explicit seams—generated contract code, validators, adapters, query orchestration—that a tiny prototype would not need. The payoff is precisely the property requested here: the frontend can be replaced or separately deployed without importing backend implementation assumptions.

### Unresolved architectural decision

The largest decision still requiring product/backend agreement is **realtime transport and authentication**. For a server→browser-only stream, SSE is simpler and has standardized automatic reconnection and `Last-Event-ID`; WebSocket is bidirectional and its browser API is easier to combine with an application-level authentication exchange when the player credential is JavaScript-held. Native `EventSource` exposes URL plus credentials mode rather than arbitrary request-header configuration, whereas the browser `WebSocket` constructor exposes URL and optional subprotocols. citeturn18search3turn20search0turn20search6

For the independently hosted, bearer-token profile described below, I would choose **WebSocket by default**, while keeping `GameEventStream` transport-neutral.

### Why ports and adapters fit here

The useful ports are the places where substitutability matters:

```ts
interface GameApi {
  getGame(gameId: string): Promise<GameSnapshot>;
  fire(command: FireCommand): Promise<GameSnapshot>;
  placeFleet(command: PlaceFleetCommand): Promise<GameSnapshot>;
  // ...
}

interface GameEventStream {
  subscribe(
    gameId: string,
    credential: SessionCredential,
    listener: GameEventListener,
  ): Unsubscribe;
}

interface SessionCredentialStore {
  read(gameId: string): SessionCredential | null;
  write(gameId: string, credential: SessionCredential): void;
  remove(gameId: string): void;
}
```

Production adapters speak HTTP/WebSocket/browser storage; unit tests can supply deterministic implementations. This follows the purpose of ports and adapters without turning ordinary frontend logic into an enterprise abstraction hierarchy. Cockburn explicitly describes multiple adapters plugging into a port. citeturn13search0

### Keep the generated client quarantined

OpenAPI Generator currently provides a `typescript-fetch` client generator and marks its generator metadata as `STABLE`. Generated code should therefore be treated like a compiler artifact: regenerate it, pin its generator version, and never make business/UI modules depend directly on its internal class names or generator conventions. citeturn16search0

The dependency rule should be:

```text
features/*            ─┐
application/*          ├─ MAY NOT import contract/generated/*
shared/*              ─┘

adapters/* ───────────── MAY import contract/generated/*

contract/generated/* ─── MAY import nothing from application/features
```

A generated `GameSnapshotDto` is a **wire representation**, not the application's domain model. `OpenApiGameApi` may map it to a small frontend projection such as `GameSnapshot`, but that projection should exist because the UI needs a stable concept—not as a TypeScript copy of a Java class.

### Do not recreate a domain engine

The frontend may know presentation facts such as board coordinates, which cell is selected, how to rotate a ship preview, or which button is currently disabled. It should **not** decide authoritative facts such as:

```text
"This shot is definitely legal"
"This ship is definitely sunk"
"It is now player B's turn"
"This fleet placement is valid"
"Player A has won"
```

Those facts should come from the authoritative snapshot or from explicitly contracted capabilities such as `allowedActions`. Doing otherwise creates two implementations of Battleship semantics that will eventually disagree.

A particularly useful contract shape is:

```ts
type GameSnapshot = {
  gameId: string;
  gameVersion: number;
  phase: "waiting" | "placing" | "playing" | "finished";
  turn: "self" | "opponent" | null;
  allowedActions: readonly AllowedAction[];
  ownBoard: OwnBoardView;
  opponentBoard: OpponentBoardView;
  outcome?: GameOutcome;
};
```

The names above are illustrative frontend concepts, not proposed Java/backend classes.

## State ownership and state-management choice

### The key principle: server state is not client state

TanStack Query's documentation distinguishes remotely owned server state from normal client state: it is asynchronous, may be shared, may change elsewhere, and can become stale in the browser. Those properties are especially strong in a two-player authoritative game. citeturn14search0

React also recommends Effects primarily for synchronization with external systems rather than as a general-purpose mechanism for deriving or moving application state around. Building a homemade cache out of `useEffect`, `useState`, request flags, and timers would therefore recreate a problem already handled by a server-state library. citeturn14search6turn14search12

### State ownership table

| State | Source of truth | Frontend owner | Persistence | Notes |
|---|---|---|---|---|
| Game snapshot | Backend | TanStack Query cache | None beyond active browser cache | Never copy into Redux/Zustand/Context |
| `gameVersion` | Backend | Part of cached snapshot | None | Used to reject stale responses/events |
| Turn, hit/miss, sunk state, winner | Backend | Part of snapshot | None | Never computed authoritatively by frontend |
| `allowedActions` | Backend/contract | Snapshot | None | Drives UX but server still validates commands |
| Pending command | Browser request lifecycle | TanStack mutation | No | Exact command can expose pending/error state |
| Command ID | Client for one logical operation | Mutation/application command | Until operation is conclusively resolved | Same ID reused on retry |
| Realtime connection status | Browser | `GameSync` local state or narrow Context | No | Do not put transport health in game snapshot |
| Selected/hovered board cell | Browser | Component `useState` | No | Pure UI state |
| Fleet-placement editing state | Browser | Local `useReducer` if complex | No | Draft interaction, not authoritative validity |
| Open dialog / focus target | Browser | Component state | No | Keep close to consumer |
| Route/game ID | URL/router | Router | Browser navigation history | Game ID is not the secret credential |
| Anonymous credential | Backend-issued capability | Credential adapter: memory + `sessionStorage` | Tab lifetime | Never TanStack Query state |
| Runtime API endpoints | Deployment | Immutable config provider | Loaded at startup | No secrets |
| Cross-tab presence | Browser | Optional BroadcastChannel coordinator | No | Advisory only |

### Recommended state-management combination

**Use TanStack Query for all remotely authoritative game/session snapshots, and ordinary React state for frontend-owned state. Do not add a general-purpose global client store initially.**

Queries represent server reads; mutations represent commands. TanStack Query provides an imperative `QueryClient.setQueryData` for synchronously installing an already-known authoritative response, and `useMutation` is explicitly intended for create/update/delete and other server side effects. citeturn14search23turn14search10

That gives a clean separation:

```text
useState / useReducer
        │
        └── "what is this particular UI doing?"

TanStack Query
        │
        └── "what does the server currently say exists?"

GameSync
        │
        └── "how do I discover that the server has newer state?"
```

### Alternatives and why they are not selected

| Alternative | Assessment | Decision |
|---|---|---|
| **TanStack Query** | Purpose-built server-state cache, queries, mutations, invalidation, programmatic cache updates. citeturn14search0turn14search23 | **Recommended** |
| **Redux Toolkit + RTK Query** | Fully credible alternative. RTK Query is explicitly designed for fetching/caching and supports streaming cache updates, including WebSocket-oriented lifecycle patterns. citeturn14search1turn14search11 | **Not selected because Redux itself is not otherwise justified** |
| **Redux Toolkit slices for game data** | Redux Toolkit is the official recommended way to write Redux, but manually storing API snapshots in ordinary Redux slices would recreate server-cache concerns that RTK Query/TanStack Query already solve. citeturn15search4turn14search1 | **Reject** |
| **Zustand** | Lightweight general store with straightforward hooks/store APIs, but it does not by itself define server freshness, refetch, mutations, reconnect reconciliation, or cache invalidation. citeturn14search2turn14search0 | **Do not use for authoritative game state** |
| **Context + `useReducer`** | React officially supports reducer+context for distributing application state, but context consumers rerender when the provided value changes and the combination provides no server-cache semantics by itself. citeturn14search3 | **Use only for appropriate client-local state/dependencies** |
| **Custom external store** | React supplies `useSyncExternalStore`, but React originally described it primarily as an API for libraries integrating external stores; React's 2025 Labs update also notes concurrency costs from synchronous external-store updates. citeturn13search5turn15search3 | **Reject for game data** |

### Why not “TanStack Query plus Zustand just in case”?

Because that immediately creates an ownership question:

```text
Is game.phase in Query?
Is it also in Zustand?
Which one does an event update?
Which one wins after reconnect?
```

There should be exactly **one client cache of the authoritative snapshot**. If future UI complexity eventually creates substantial *frontend-owned* cross-route state, Zustand could be added for that narrow purpose without moving server data into it.

### Credible Redux alternative

If the organization already standardizes strongly on Redux, the better alternative architecture is not “Redux slices plus TanStack Query.” It is:

```text
Redux Toolkit
   └── RTK Query owns all server state
```

RTK Query explicitly supports query caching and streaming updates, and Redux's own documentation recommends Redux Toolkit for modern Redux code. citeturn14search1turn14search11turn15search6

Using both RTK Query and TanStack Query for the same server entities would create two cache authorities and should be avoided.

## Contract-first workflow and versioning

### Contract artifacts

Use a **neutral, independently versioned contract artifact** such as:

```text
battleship-api-contract/
├── openapi.yaml
├── asyncapi.yaml
├── schemas/
│   ├── GameSnapshot.schema.json
│   ├── GameChangedEvent.schema.json
│   ├── EventEnvelope.schema.json
│   ├── FireCommand.schema.json
│   └── Problem.schema.json
├── examples/
│   ├── waiting-game.json
│   ├── active-game.json
│   ├── finished-game.json
│   └── game-changed-event.json
└── CHANGELOG.md
```

OpenAPI is explicitly implementation-language agnostic; AsyncAPI is designed to describe message-driven APIs over technologies including WebSockets. OpenAPI 3.1.2's Schema Object dialect incorporates JSON Schema 2020-12 vocabularies, making a common schema vocabulary practical. citeturn13search2turn16search2turn16search3

As of August 2026, OpenAPI 3.2.0 is published, and OpenAPI's official migration guidance describes 3.2 as backward-compatible with 3.1 documents. For this project I would use **OpenAPI 3.1.2 unless the chosen complete toolchain has been proven against 3.2.0 in CI**. That is a tooling-conservatism recommendation, not a limitation of the specification itself. citeturn13search2turn13search4turn13search10

### Contract-first development workflow

The desired sequence is:

```text
Contract change proposed
        │
        ▼
OpenAPI + event schema + examples changed
        │
        ▼
Schema validation / lint / compatibility check
        │
        ├─────────────┐
        ▼             ▼
Generate TS client   Backend implements
+ validators         contract independently
        │             │
        ▼             ▼
Frontend adapter     Backend conformance tests
tests                 │
        └──────┬──────┘
               ▼
      shared contract examples
               │
               ▼
        integration / E2E
               │
               ▼
      immutable contract release
```

The contract is the shared artifact; generated Java and TypeScript representations, if any, are **separate build products**. Neither side should import the other's generated implementation.

### OpenAPI client generation

Generate the TypeScript HTTP layer, but wrap it:

```text
generated typescript-fetch client
             │
             ▼
      OpenApiGameApi
      ├── authentication
      ├── base URL
      ├── runtime validation
      ├── error normalization
      └── DTO → frontend projection
             │
             ▼
          GameApi
```

OpenAPI Generator's `typescript-fetch` generator gives a concrete route to automated TypeScript client creation. citeturn16search0

Do **not** expose generator constructs such as generated service-class names throughout components. That would merely replace Java coupling with code-generator coupling.

### Runtime response validation is still necessary

Static TypeScript types do not prove that bytes received across a network match those types. The wire boundary begins with untrusted parsed JSON, and validation should happen before the result is installed into the query cache.

JSON Schema exists specifically to describe and validate JSON structure, and the JSON Schema project lists JavaScript validators supporting Draft 2020-12, including Ajv. citeturn16search1turn16search5turn16search7

Recommended sequence:

```ts
const raw: unknown = await generatedClient.getGame(...);

const validated = gameSnapshotValidator.parse(raw);
// or validate(raw) + typed narrowing

return mapContractGame(validated);
```

The precise validator library is less important than **single-source generation**. Avoid this:

```text
openapi.yaml
+
independently hand-written Zod GameSnapshot
+
independently hand-written TS GameSnapshot
```

That creates three contracts.

Prefer:

```text
canonical contract schema
       │
       ├── generated TS client/types
       └── generated or compiled runtime validator
```

Using Ajv against JSON Schema 2020-12 is a natural option because OpenAPI 3.1.x's schema model is based on that vocabulary. citeturn16search3turn16search5

### Forward compatibility and validation strictness

Runtime validation should not accidentally destroy API compatibility.

Suppose version `1.4` adds:

```json
{
  "gameId": "g123",
  "gameVersion": 19,
  "spectatorCount": 0
}
```

An older `1.3` client should normally continue working if it does not know `spectatorCount`. Therefore, response/event object schemas should generally **tolerate unknown additive fields**, or validators should be configured accordingly. Otherwise every response-property addition becomes a major breaking change.

The same idea is especially useful for events: an unknown event subtype should not terminate the UI. The frontend can validate the stable envelope, recognize that something changed, and recover through the snapshot endpoint.

### Distinguish three different “versions”

Do not overload the word `version`.

```text
contract release version
    e.g. 1.7.2
    = lifecycle of published OpenAPI/AsyncAPI bundle

API major
    e.g. /api/v1 and battleship.events.v1
    = compatibility boundary

gameVersion
    e.g. 42
    = monotonic revision of one individual game
```

A snapshot might therefore be conceptually:

```json
{
  "gameId": "G7",
  "gameVersion": 42,
  "phase": "playing"
}
```

and a realtime envelope:

```json
{
  "type": "game.changed",
  "eventId": "01J...",
  "gameId": "G7",
  "gameVersion": 42
}
```

`gameVersion` is concurrency/synchronization data, not an API schema version.

### REST and event versioning

Recommended public boundaries:

```text
GET  /api/v1/games/{gameId}
POST /api/v1/games/{gameId}/commands/...
```

and for WebSocket:

```text
Sec-WebSocket-Protocol: battleship.events.v1
```

RFC 6455 explicitly permits WebSocket subprotocol names to identify different incompatible versions; changing the subprotocol name is therefore an appropriate major-version boundary. citeturn4search3

For a breaking contract transition, support old and new majors concurrently for a migration interval:

```text
frontend A ─── /api/v1 ─── backend
frontend B ─── /api/v2 ─── backend
```

That is what permits actual independent deployment.

### Event contracts should optimize for recovery, not client computation

For this game, the strongest event contract is deliberately modest:

```json
{
  "type": "game.changed",
  "eventId": "...",
  "gameId": "...",
  "gameVersion": 27,
  "reason": "SHOT_RESOLVED"
}
```

The frontend uses the message primarily as **a freshness notification**.

That is preferable to requiring events such as:

```text
ShotFired
ShipHit
ShipSunk
TurnAdvanced
GameWon
```

to be replayed in the browser to reconstruct the state machine. The latter makes the frontend behave like a replica of the game engine and creates much harder event-gap recovery.

Rich domain events may still exist, but **the UI must always be recoverable from `GET game snapshot` without replaying history**.

## Realtime, anonymous sessions, and command lifecycle

### Recommended realtime data flow

```mermaid
flowchart LR
    U[React UI] -->|read| Q[TanStack Query cache]
    U -->|command| M[TanStack mutation]
    M --> A[GameApi port]
    A --> H[OpenAPI HTTP adapter]
    H --> S[Backend]

    S -->|authoritative snapshot vN| H
    H --> V[Runtime validation]
    V -->|version-guarded update| Q

    S -. game.changed vN .-> W[One GameEventStream per game]
    W --> EV[Event runtime validation]
    EV --> C{Compare with cached gameVersion}

    C -->|event <= cached| I[Ignore duplicate/stale event]
    C -->|event > cached| R[Invalidate/refetch snapshot]
    R --> A

    W -->|disconnect| D[Reconnect coordinator]
    D -->|fallback GET| A
    D -->|reconnect succeeds| R
```

This yields an important invariant:

> **The REST snapshot is the recovery truth; realtime is a low-latency freshness mechanism.**

### One realtime subscription per game

Place `GameSync` at the game-route boundary:

```tsx
function GameRoute() {
  const { gameId } = useRouteParams();

  return (
    <GameSync gameId={gameId}>
      <GameScreen gameId={gameId} />
    </GameSync>
  );
}
```

Board cells, status panels, fleet displays, timers, dialogs, and command buttons must **not** independently open sockets.

An Effect is appropriate here because React explicitly describes Effects as the mechanism for synchronizing a component with an external system and emphasizes cleanup when synchronization stops. citeturn14search6turn14search12

The scope should normally be:

> **one subscription per active game per browser document**, not magically one socket across every tab.

Attempting cross-tab single-socket leader election is possible with Web Locks and BroadcastChannel, but introduces failure detection, leader handover, browser compatibility, and hidden-tab complexity. Web Locks can coordinate mutually exclusive work among same-origin tabs/workers, while BroadcastChannel supports same-origin cross-context communication. citeturn18search0turn19search2

For a two-player Battleship application, that complexity is not justified initially.

### Stale events and race handling

The cache update rule should be monotonic:

```ts
if (incomingVersion <= cachedVersion) {
  ignore();
} else {
  refetchAuthoritativeSnapshot();
}
```

That handles:

```text
duplicate events
out-of-order delivery
command-response/event races
reconnect replay
two tabs issuing commands
slow HTTP responses
```

Likewise, when installing a command response:

```ts
queryClient.setQueryData(gameKey(gameId), old => {
  if (old && old.gameVersion > response.gameVersion) {
    return old; // a newer state already won the race
  }
  return response;
});
```

TanStack Query provides synchronous `setQueryData` specifically for installing already-available data into the cache. citeturn14search23

### Reconnect strategy

WebSocket exposes close/error events but does not itself provide SSE-style automatic replay semantics; application reconnect behavior needs to be designed. SSE, by contrast, defines automatic reconnection behavior and `Last-Event-ID`. citeturn18search2turn18search3turn18search6

For WebSocket:

```text
socket closes
    │
    ├── mark realtime status "disconnected"
    │
    ├── GET authoritative snapshot immediately
    │
    ├── reconnect with bounded exponential backoff + jitter
    │
    └── once reconnected
          └── GET authoritative snapshot again
```

The second snapshot matters because changes may have occurred between the first recovery fetch and establishment of the replacement stream.

While disconnected, **visible active gameplay may use slow temporary polling as a degraded mode**, but polling must stop when the route is inactive/hidden unless the session-lifetime contract explicitly says passive polling should keep sessions alive.

### Important unresolved expiry question

The backend retains in-memory state for 15 minutes after “last client access.” The contract must define whether each of these resets that lifetime:

```text
GET snapshot?
successful command?
failed command?
open realtime socket?
WebSocket ping/pong?
event delivery?
fallback poll?
hidden browser tab?
```

That semantic cannot safely be left as an implementation accident.

For example, a hidden tab polling every five seconds could otherwise prevent a nominally temporary session from ever expiring. This is a contract-level lifecycle decision, not a React implementation detail.

### Anonymous-session credential recommendation

For an anonymous, temporary game, use a **high-entropy opaque server-issued capability**, not a meaningful player/game identifier.

There are two reasonable deployment profiles.

**Security-preferred same-site profile:** use a `Secure`, `HttpOnly`, appropriately `SameSite` cookie when the deployment topology allows it. An HttpOnly cookie is inaccessible to normal page JavaScript and therefore provides better protection against direct session-token extraction by XSS. OWASP recommends avoiding JavaScript-readable storage for session identifiers where cookies can provide HttpOnly protection. citeturn18search1turn18search5

**Portable independently hosted profile:** when the frontend must work from arbitrary separately configured origins and bearer authorization is the chosen contract, keep the opaque token in memory and mirror it in **`sessionStorage`**, not `localStorage`.

`sessionStorage` has precisely useful lifetime properties here: it survives reloads/restores but normally belongs to the page session/tab rather than persisting indefinitely. MDN also notes that a newly opened page with an opener initially receives a copy of the opener's session storage, after which the stores diverge. citeturn19search0

Recommended abstraction:

```ts
interface SessionCredentialStore {
  get(gameId: GameId): SessionCredential | null;
  put(gameId: GameId, value: SessionCredential): void;
  delete(gameId: GameId): void;
}
```

The rest of the frontend should not know whether a future deployment switches this adapter from `sessionStorage` bearer tokens to an HttpOnly-cookie session.

### Security trade-off of `sessionStorage`

`sessionStorage` is **not XSS-safe** merely because it is less persistent than localStorage. JavaScript executing in the origin can read it. OWASP's storage guidance warns that JavaScript-accessible browser storage can be exposed by XSS and specifically advises against localStorage for session identifiers. citeturn18search1

Therefore:

```text
sessionStorage is recommended here for lifecycle/isolation,
not because it cryptographically secures the credential.
```

The application should also use CSP, avoid unsafe HTML injection, never put the token in logs, URLs or analytics, and minimize token lifetime. CSP allows operators to restrict where scripts/resources/connections can originate and is an important defense layer. citeturn20search16

### Multiple tabs

Do **not** use `localStorage` merely so every tab automatically becomes the same player.

Instead:

```text
Tab A
 └── credential A in sessionStorage

Tab B
 └── normally independent sessionStorage
```

If same-origin tabs need awareness, `BroadcastChannel` can exchange non-secret state such as:

```json
{
  "type": "GAME_OPEN_IN_ANOTHER_TAB",
  "gameId": "G7",
  "tabId": "..."
}
```

BroadcastChannel is specifically intended for communication among same-origin browsing contexts. citeturn18search0

Avoid broadcasting the player credential unless the product explicitly chooses cross-tab session sharing and its security implications.

### WebSocket authentication implication

A browser-created WebSocket exposes:

```js
new WebSocket(url)
new WebSocket(url, protocols)
```

rather than a general arbitrary-header argument. citeturn20search0turn20search2

Consequently, with the portable bearer-token profile, use one of two explicit contract designs:

```text
WSS connection
    │
    ▼
first application message:
{ type: "authenticate", token: "..." }
    │
    ▼
server validates token + Origin
    │
    ▼
authenticated acknowledgement
    │
    ▼
subscription becomes active
```

or use a short-lived realtime connection ticket obtained via authenticated REST.

Do not casually append the long-lived session token to a WebSocket URL, because URLs commonly propagate into logs and diagnostics.

If cookie authentication becomes the chosen deployment profile, native SSE becomes much more attractive because the game only needs server→client realtime traffic and EventSource supports credential mode. SSE is explicitly unidirectional. citeturn20search1turn20search6

### Command lifecycle

Every state-changing user action should be treated as a command with explicit lifecycle:

```text
IDLE
  │ user clicks
  ▼
COMMAND CREATED
  ├── commandId = fresh unique ID
  └── expectedVersion = current gameVersion
  │
  ▼
PENDING
  │
  ├── success
  │      ▼
  │   validate authoritative response
  │      ▼
  │   version-guard cache update
  │      ▼
  │    RESOLVED
  │
  ├── version conflict
  │      ▼
  │   refetch snapshot
  │      ▼
  │   CONFLICT MESSAGE
  │
  ├── ambiguous network failure
  │      ▼
  │   retry SAME commandId
  │   or reconcile snapshot first
  │
  └── expired session
         ▼
      clear credential/cache
         ▼
      EXPIRED ROUTE
```

### Duplicate clicks are a server problem too

The UI should disable the exact action while its mutation is pending, but that is only a usability measure. Correctness must survive:

```text
double click
browser retry
mobile network retry
two tabs
timeout after server committed
socket notification racing command response
```

Use a client-generated `commandId` with server-defined idempotency semantics.

A proposed IETF `Idempotency-Key` header describes precisely this pattern for fault-tolerant POST/PATCH requests, but as of 18 August 2026 the HTTPAPI working-group draft has **expired and is not an RFC**. citeturn17search1turn17search6turn17search8

Therefore I would make idempotency an explicit application contract, for example:

```json
{
  "commandId": "f59b...",
  "expectedGameVersion": 41,
  "target": "B7"
}
```

Using the draft header as an additional convention is possible, but the API should not pretend it is currently a settled HTTP standard.

### Optimistic concurrency

A command should carry the version on which the user's decision was based.

Either:

```http
If-Match: "<game-state-etag>"
```

or:

```json
{
  "expectedGameVersion": 41
}
```

is defensible.

HTTP `If-Match` is a standardized precondition mechanism, and HTTP defines `412 Precondition Failed` for a false request precondition; `409 Conflict` represents a request that conflicts with current resource state. citeturn7view0turn7view1

For this application, an explicit `expectedGameVersion` has the advantage that the same concept appears naturally in REST command schemas, event documentation, test fixtures, and diagnostics.

### Conflict behavior

Recommended semantics:

| Outcome | Frontend behavior |
|---|---|
| Success | Validate response, install authoritative snapshot if not older |
| Same `commandId` already completed | Return/recover the same logical result |
| Version/precondition conflict | Fetch latest snapshot; tell user game changed |
| Domain conflict | Fetch latest snapshot; show contract-provided user-safe message |
| Network timeout | Do **not** create a new command ID; safely retry same logical command or reconcile |
| Unauthorized/invalid credential | End local session |
| Expired/removed game | Clear game cache and credential; route to expiry screen |
| Contract-invalid response | Do not cache it; surface compatibility/service failure |

A version conflict should generally **not automatically replay the user's command against new state**. A shot chosen on version 41 may no longer represent valid intent after version 42 arrives.

### Avoid authoritative optimistic game updates

TanStack Query supports optimistic updates, but the fact that a library can optimistically mutate a cache does not mean this game should do so. citeturn14search4

Safe optimistic state:

```text
"B7 shot request is pending"
button disabled
spinner/progress announcement
```

Unsafe authoritative optimism:

```text
"B7 is now a HIT"
"ship is sunk"
"it is the opponent's turn"
```

until the server has confirmed those facts.

### Route guard and session expiry

A route guard should use local credentials only as a **cheap prerequisite**:

```text
/game/G7
   │
   ├── no local credential
   │      └── start/join/expired route
   │
   └── credential exists
          │
          ▼
      GET authoritative game
          │
          ├── success → render
          └── expired/unauthorized → remove credential + cache → expired route
```

Possessing a value in `sessionStorage` is not evidence that the backend session still exists.

The contract should provide a stable machine-readable problem code such as:

```json
{
  "type": "...",
  "status": 410,
  "code": "SESSION_EXPIRED",
  "detail": "..."
}
```

rather than forcing the frontend to infer the product meaning from HTTP status alone.

## Testing, independent deployment, accessibility, and resilience

### Testing architecture

The testing strategy should reinforce the architectural boundary rather than undermine it.

```text
                  ┌───────────────────────────────┐
                  │ Contract/schema validation    │
                  └──────────────┬────────────────┘
                                 │
                 ┌───────────────▼───────────────┐
                 │ Pure unit tests               │
                 │ versioning / mapping / errors │
                 └───────────────┬───────────────┘
                                 │
              ┌──────────────────▼──────────────────┐
              │ React integration tests             │
              │ real query layer + adapters         │
              │ mocked network / event port         │
              └──────────────────┬──────────────────┘
                                 │
              ┌──────────────────▼──────────────────┐
              │ Playwright E2E with real backend    │
              │ same-host + separate-host profiles │
              └─────────────────────────────────────┘
```

Testing Library's guiding philosophy is to test software in ways resembling user interaction, while Mock Service Worker intercepts at the network layer rather than requiring application code to replace its HTTP implementation. That is a good combination for adapter/integration tests. citeturn8search0turn8search1

### Never build a mock Battleship engine

Bad test double:

```ts
function fakeFire(board, coordinate) {
  // calculates hits, sinks ships, updates turn...
}
```

That silently becomes game engine number two.

Good fixtures:

```text
waiting-for-opponent.json
placement-required.json
my-turn-v17.json
opponent-turn-v18.json
shot-hit-v19.json
shot-miss-v20.json
game-won-v35.json
session-expired.problem.json
conflict-v22.problem.json
game-changed-v23.event.json
```

Each fixture represents **a server statement**, not a computation.

Tests should then script exchanges:

```text
GET snapshot v17
user clicks B7
POST fire
server returns snapshot v18

or

POST fire
server returns version conflict
GET snapshot
server returns v19
```

### Contract tests

Every fixture should be runtime-validated against the same schemas used in production.

CI should fail when:

```text
OpenAPI is invalid
event schemas are invalid
generated client is stale
runtime validators are stale
frontend fixtures violate contract
frontend code expects a removed field
```

A separate backend CI pipeline should prove that its implementation satisfies the same neutral contract. The frontend CI should not compile Java code merely to obtain DTOs.

### Component and integration tests

Use real:

```text
React components
TanStack Query
command hooks
OpenApiGameApi
runtime validators
error mapping
```

while replacing only the network boundary with MSW responses or replacing `GameEventStream` with a scripted test adapter.

MSW's network-level interception is useful because the application still executes its normal request stack rather than calling a test-only repository. citeturn8search1

Important integration scenarios include:

```text
command response arrives before realtime event
realtime event arrives before command response
duplicate event
stale event
event with newer version
malformed event → snapshot repair
socket disconnect → snapshot fallback
reconnect → snapshot reconciliation
double click
same command ID retried
version conflict
session expiry during game
two tabs issuing competing commands
```

### E2E tests

Playwright E2E should run against the **real backend engine**, not an in-browser copy.

At minimum test:

```text
create game
join from second browser context
placement flow
one complete server-authoritative turn exchange
hit/miss visibility
realtime opponent update
reload recovery
network disconnect/reconnect
expired session behavior
```

Also run deployment smoke tests in both modes:

```text
Mode A:
JAR/static host + API on same origin

Mode B:
frontend origin A
backend origin B
CORS + runtime configuration + realtime connection
```

A test suite that only exercises the co-packaged JAR mode does not prove independent deployability.

### Independent deployment design

The JavaScript bundle must not contain a build-time hardcoded production API location.

Load an environment-specific non-secret runtime document before rendering:

```json
{
  "apiBaseUrl": "/api/v1",
  "eventsUrl": "/events/v1",
  "contractMajor": 1
}
```

Co-packaged profile:

```json
{
  "apiBaseUrl": "/api/v1",
  "eventsUrl": "wss://game.example.com/events/v1",
  "contractMajor": 1
}
```

Separate-host profile:

```json
{
  "apiBaseUrl": "https://api.example.net/api/v1",
  "eventsUrl": "wss://api.example.net/events/v1",
  "contractMajor": 1
}
```

The exact values are illustrative. The architectural property is:

```text
same frontend build bytes
+
different runtime config
=
different deployment
```

Runtime configuration must itself be validated. If it is invalid, fail before mounting the normal game UI with a clear configuration error.

### JAR packaging

The packaged deployment should behave conceptually as:

```text
independent frontend CI
      │
      ▼
frontend-dist.tar/zip
      │
      ▼
packaging step copies opaque static assets
      │
      ▼
JAR
├── backend
└── static frontend files
```

The JAR build should **not** generate TypeScript from Java classes, rewrite frontend models based on Spring/Jackson classes, or rely on package-private implementation details.

The same `dist/` should also be publishable to a CDN/static host.

### Cross-origin deployment

CORS is the browser mechanism allowing a server to authorize reads from another origin. Separately hosted REST therefore requires explicitly configured allowed frontend origins and, where applicable, headers used for authorization or preconditions. citeturn19search17turn20search15

Prefer an explicit allowlist:

```text
https://game.example.com
https://staging-game.example.com
```

rather than treating `*` as the default production design.

With credentialed cookie requests, wildcard `Access-Control-Allow-Origin` cannot be combined with credential mode; the browser requires the appropriate credential-aware CORS configuration. citeturn20search4turn20search12

For WebSocket, the backend should separately validate the browser's handshake origin and authenticate the session before subscribing it to game information. Do not assume ordinary fetch CORS policy is a substitute for WebSocket authorization.

### CSP and runtime endpoints

The deployed Content Security Policy must permit the configured API/realtime origins through `connect-src`. CSP exists to control which resources/origins the browser is allowed to load and is an important defense against classes of injection abuse. citeturn20search16

That means runtime configuration and deployment security policy should be produced together:

```text
runtime config:
apiBaseUrl = https://api.example.net

CSP:
connect-src 'self' https://api.example.net wss://api.example.net
```

Configuration contains locations, feature toggles, release metadata, and contract versions—**never secrets**.

### Error boundaries

Use at least:

```text
RootErrorBoundary
    │
    └── GameRouteErrorBoundary
```

React Error Boundaries can replace a rendering subtree that throws with fallback UI, but React explicitly notes they do **not** generally catch event-handler errors or arbitrary asynchronous failures such as timer callbacks. citeturn13search1

Therefore:

```text
rendering/programming exception
    → Error Boundary

HTTP command failure
    → mutation error handling

query/server failure
    → query/route error UI

realtime schema failure
    → GameSync recovery

expired session
    → session lifecycle / routing
```

Do not convert every expected REST `409` into a thrown render exception just so an Error Boundary handles it.

### Accessibility of the Battleship board

A Battleship board is inherently two-dimensional. The WAI-ARIA Authoring Practices grid pattern provides an appropriate interaction model when implementing a genuinely interactive grid: focus enters the grid, and directional keys navigate cells. citeturn10search1

A good targeting cell should expose meaning such as:

```text
"B7, untried"
"B7, miss"
"B7, hit"
```

rather than forcing assistive technology users to infer semantics from background color.

Recommended keyboard interaction:

```text
Tab          enter/leave the game board
Arrow keys   move among cells
Enter/Space  activate/select the current target
Escape       cancel an interaction/dialog where appropriate
```

WCAG requires keyboard-operable functionality and visible focus; WCAG 2.2 also defines minimum target-size requirements relevant to dense interactive board cells. citeturn11search1turn11search2turn11search3

Changes such as:

```text
"Opponent joined"
"Your shot was a hit"
"Opponent disconnected"
"Connection restored"
"Game expired"
```

should use appropriate status/live-region behavior where the update matters without moving keyboard focus. WCAG's status-message requirement exists so assistive technologies can announce such changes programmatically. citeturn11search0

Errors also need textual identification rather than color or icon alone. citeturn11search12

If fleet placement supports dragging, provide a non-drag alternative—such as keyboard selection, rotate controls, and destination-cell selection—because WCAG 2.2 includes a dragging-movement requirement. citeturn11search24

Automated accessibility checks should be part of Playwright tests, but Playwright itself cautions that automated testing cannot find every accessibility problem, so keyboard and assistive-technology review remains necessary. citeturn8search3

## Decisions, trade-offs, and anti-coupling rules

### Recommended decisions

The following should be recorded as architecture decisions rather than informal coding conventions.

| Topic | Recommended decision | Main trade-off |
|---|---|---|
| Architecture style | Lightweight ports/adapters around external dependencies | A few additional abstractions |
| REST contract | OpenAPI 3.1.2 initially | 3.2 features deferred until toolchain proven |
| Event contract | AsyncAPI + JSON Schema payload schemas | Additional contract artifact/tool |
| Generated client | Yes, hidden behind HTTP adapter | Mapping layer required |
| Runtime validation | Yes, at every network/event boundary | Runtime/build complexity |
| Server state | TanStack Query | Adds one focused dependency |
| Global client store | None initially | Must add later if real client-state complexity emerges |
| Realtime model | Notification + authoritative snapshot | Extra GETs versus delta replay |
| Realtime connection | One per active game/browser document | Multiple tabs may each connect |
| Default realtime transport | WebSocket for JS-held bearer profile | Must implement reconnect/auth exchange |
| Credential | Opaque capability; sessionStorage portable profile | Accessible to XSS |
| Commands | Client command ID + expected game version | Server must retain idempotency record long enough |
| Optimistic updates | Pending affordances only | Slightly less instant-looking gameplay |
| Route guard | Verify with backend snapshot | Initial navigation requires request |
| Mocking | Contract fixtures, never game simulation | More explicit scenario fixtures |
| Deployment | Runtime API configuration | Additional startup/config artifact |

### Unresolved decisions that should be settled in the contract

**Realtime transport.** If production authentication becomes an HttpOnly same-site cookie, SSE deserves serious reconsideration because it is unidirectional, automatically reconnects, and has standardized event-ID resume semantics. If the required profile is arbitrary independently hosted frontend + JS-held bearer credential, WebSocket is the more straightforward native-browser abstraction. citeturn18search3turn20search6turn20search0

**Expiry semantics.** Specify what qualifies as client access for the 15-minute server lifetime, especially passive realtime connections, heartbeats, background tabs, and recovery polling.

**Session recovery after browser close.** `sessionStorage` intentionally prioritizes tab lifetime. If the product requires reopening a closed browser and recovering an anonymous game within the backend's remaining lifetime, the credential strategy needs to change—preferably toward an HttpOnly server-managed cookie rather than long-lived localStorage. OWASP favors HttpOnly cookies over script-accessible storage for session identifiers. citeturn18search1turn18search5

**Cross-tab behavior.** Decide whether intentionally duplicating a game should represent the same player, produce a warning, or be unsupported. Correctness must not depend on this decision because expected-version/idempotency protections should make concurrent clients safe.

**Conflict status vocabulary.** Decide whether stale-version commands use HTTP `412`, `409`, or another documented convention. The more important requirement is a stable machine-readable application problem code and consistent snapshot reconciliation. HTTP defines both precondition failure and conflict semantics. citeturn7view0turn7view1

**Expired versus unknown game.** `410 Gone` can express a resource that is no longer available, but an implementation might be unable or unwilling to distinguish an expired in-memory game from an unknown identifier. The UI should therefore use a contracted problem code where possible rather than hardcoding product semantics to a status alone.

### Architecture rules that prevent frontend/backend coupling

| Rule | Enforcement |
|---|---|
| **The versioned wire contract is the only shared integration artifact.** | Separate contract package/release; no Java source dependency |
| **Generated frontend code is not the application API.** | Generated imports permitted only from adapters/contract infrastructure |
| **UI code never imports backend package/class names.** | ESLint/module-boundary rule |
| **No TypeScript is generated directly from backend implementation classes.** | Generate only from neutral contract |
| **No Java model is generated directly from frontend interfaces.** | Backend implements contract independently |
| **Server snapshot is the only authoritative game representation.** | One TanStack Query cache; no Redux/Zustand mirror |
| **Frontend never reconstructs the game from domain-event history.** | Snapshot endpoint must recover any active game |
| **Realtime messages are runtime validated before affecting synchronization.** | Event adapter owns validator |
| **HTTP responses are runtime validated before entering the query cache.** | HTTP adapter owns validator |
| **Unknown/stale events cannot corrupt current state.** | Envelope + monotonic `gameVersion` |
| **Every state-changing operation has concurrency semantics.** | `commandId` + expected version in contract |
| **Duplicate-click protection is not trusted for correctness.** | Server idempotency required |
| **Routes never treat browser storage as proof of a valid session.** | Authoritative snapshot required |
| **Secrets never appear in runtime deployment config.** | Config schema/review |
| **Backend URL is runtime-configurable.** | Same frontend artifact tested against two origins |
| **Co-packaged deployment is only a hosting option.** | Separate-host E2E test is mandatory |
| **Tests do not implement Battleship rules.** | Contract fixtures + real backend E2E |
| **Backend-specific error strings never drive UI logic.** | Contracted problem codes |
| **Contract additions remain forward compatible where intended.** | Runtime validators tolerate documented additive response fields |
| **A breaking wire change requires a new contract/API major.** | CI compatibility check and parallel-major migration policy |

The most important four invariants are worth making explicit in code review documentation:

```text
INVARIANT A
There is exactly one frontend cache of authoritative game state.

INVARIANT B
A complete current UI can always be reconstructed from an authoritative
snapshot without replaying realtime event history.

INVARIANT C
No frontend correctness decision depends on preventing double clicks,
ordered event delivery, or having exactly one browser tab.

INVARIANT D
Changing the backend implementation without changing the supported
contract major requires no frontend source-code change.
```

Those invariants are more consequential to independent replaceability than the choice between Redux, Zustand, or any particular directory naming scheme.
