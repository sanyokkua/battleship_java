# Operating an Ephemeral Realtime Game on Free Hosting

## Operating contract: what can be guaranteed and what cannot

The most important operational fact is architectural, not JVM-specific: **a game that exists only in one JVM is disposable state**. A restart, redeploy, process crash, out-of-memory termination, scale-to-zero event, or host replacement creates a new process with an empty game map. Graceful shutdown can improve the client experience before a planned stop, but it cannot make that state durable. This is especially relevant on free hosting: Render currently states that a Free web service can be restarted at any time, while Koyeb's Free Instance scales to zero after an hour without traffic and is explicitly described as unsuitable for production applications. citeturn18view1turn18view3

For this game, the cleanest transport architecture is **ordinary HTTP for commands and snapshots plus one Server-Sent Events stream per player for notifications/state updates**. SSE is a good match because the realtime direction is primarily server-to-browser; browser-to-server actions such as create, join, place ships, fire, surrender, or refresh remain ordinary API calls. SSE has a standardized `text/event-stream` format, reconnection timing, event IDs, and `Last-Event-ID` behavior. citeturn19view7turn19view8

The application contract should explicitly distinguish the following four categories.

| Category | Operational meaning |
|---|---|
| **Application guarantee, within one live JVM** | At most two player seats per game; TTL semantics; game-version ordering; configured game/SSE admission limits; bounded queues; deterministic rejection codes. These are enforceable by your code as long as the process is alive and functioning. |
| **Assumption to validate** | Retained heap per game, retained heap/native memory per SSE stream, CPU per heartbeat, startup time, sustainable request rate, and practical connection count. There is no portable Spring/JVM number for these; measure them with the actual JDK, framework version, container, TLS/proxy path, and host. Oracle provides heap and native-memory diagnostics through `jcmd`, including heap histograms and `VM.native_memory`. citeturn20view0 |
| **Recommendation** | Bound every resource independently; use SSE as an optimization over a snapshot API; make reconnection idempotent; expose a process epoch; reject new work before memory exhaustion; and make realtime failure non-fatal to gameplay. |
| **Provider-dependent behavior** | Memory/CPU quota, sleeping, cold-start latency, arbitrary restarts, proxy and absolute request timeouts, health-check semantics, bandwidth quotas, maximum open connections, shutdown grace, and whether a held stream prevents sleep. Current provider behavior differs substantially. citeturn18view0turn18view2turn18view4turn18view5 |

A useful API-level concept is a **`serverEpoch`**, generated randomly on each JVM startup. Every game snapshot and SSE event should include that epoch along with a monotonically increasing `gameVersion`. A browser that reconnects and sees a different epoch immediately knows that it is talking to a fresh process. This does **not** recover anything; it merely turns an otherwise confusing `404` into an honest user-facing message such as “The server restarted; this game no longer exists.”

The API contract should therefore be independently usable whether the frontend is bundled in the JAR or hosted elsewhere:

```text
POST /api/v1/games
POST /api/v1/games/{gameId}/join
GET  /api/v1/games/{gameId}
POST /api/v1/games/{gameId}/commands
GET  /api/v1/games/{gameId}/events   # SSE

Every state-bearing response:
{
  "serverEpoch": "...",
  "gameVersion": 42,
  ...
}
```

Bundling the frontend and backend is operationally attractive because same-origin deployment removes a layer of CORS configuration. Independent deployment should remain possible by making the backend base URL configuration-driven and explicitly configuring CORS and browser `connect-src` policy for the API/SSE origin. Browser CORS rules and CSP `connect-src` both apply when separate origins are used. citeturn3search18turn3search9

A particularly important TTL decision is what **“last client access”** means. Transport-maintenance traffic should not silently redefine the business rule. **Recommendation:** update the 15-minute TTL on meaningful inbound game access—create/join, user-initiated state access, or a game command—but do **not** update it because the server emitted an SSE heartbeat, because EventSource automatically reconnected, or because a fallback poller is running. Otherwise an abandoned browser tab can keep an otherwise dead game alive indefinitely. If product semantics intentionally define a connected browser as active presence, implement an explicit presence request and add a separate absolute game lifetime.

## Resource budget, JVM heap, garbage collection, and capacity

A 512 MB free instance is large enough for a small Spring application, but **512 MB is a process/container budget, not a heap budget**. Heap, metaspace, code cache, thread stacks, direct/native buffers, networking/TLS state, JVM internals, shared libraries, and the web container all consume process memory. Oracle documents `-Xmx` as the maximum heap size and container-aware memory sizing through `MaxRAM`/`MaxRAMPercentage`; current JDK documentation gives `MaxRAMPercentage` a default of 25%, with separate ergonomics for small heaps. Relying on those defaults is therefore less predictable than deliberately sizing a very small hosted service. citeturn19view0

For a host with `M_host` bytes of available memory, use both a heap budget and a process-RSS budget:

\[
RSS_{steady} \le 0.80\,M_{host}
\]

\[
RSS_{emergency} \approx 0.90\,M_{host}
\]

\[
H_{games}+H_{SSE}+H_{baseline}+H_{burst} \le H_{live-target}
\]

where

\[
H_{games}=N_{games}\times G
\]

\[
H_{SSE}=N_{SSE}\times C
\]

and therefore

\[
N_{games,memory}=
\left\lfloor
\frac{H_{live-target}-H_{baseline}-H_{burst}-N_{SSE}C}
{G}
\right\rfloor
\]

`G` is **measured retained heap per game**, not a guessed Java-object count; `C` is **measured retained heap per SSE stream**. The actual game cap is then:

\[
MAX\_GAMES =
\min(N_{games,memory}, N_{cpu}, N_{business/abuse})
\]

Likewise, the connection ceiling should be the minimum of the application limit, provider limit if documented, file-descriptor/socket limit, RSS-derived limit, and CPU/bandwidth-derived limit:

\[
MAX\_SSE =
\min(C_{app},C_{provider},C_{fd},C_{memory},C_{cpu/bw})
\]

Do not use Tomcat's socket limit as the only SSE limit. Tomcat 11 currently defaults `maxConnections` to 8192 and `maxThreads` to 200, values designed for much larger general-purpose servers; moreover HTTP/2 can multiplex multiple streams over fewer TCP connections. The application therefore needs its own atomic count of active SSE subscriptions. citeturn14search0turn19view8

**A conservative 512 MB starting model** is:

| Budget item | Starting value | Meaning |
|---|---:|---|
| Host/container memory | 512 MB | Example matching current Render and Koyeb Free instances. citeturn18view0turn18view3 |
| JVM `-Xmx` | 256 MiB | Recommendation: reserve roughly half the container for non-heap JVM/framework/network memory until measured. |
| JVM `-Xms` | 64 MiB | Recommendation: avoid committing the full maximum heap immediately on a tiny host. |
| Steady RSS target | ≤ ~410 MiB | 80% operating target, leaving host-level headroom. |
| Emergency protection | ~461 MiB | At roughly 90%, stop admitting new games/SSE before the host kills the JVM. |
| Post-GC live-heap planning target | ~179 MiB | 70% of 256 MiB, leaving allocation/GC headroom. |
| Illustrative warm live heap | 90 MiB | **Assumption only** until measured. |
| Planning value per game | 16 KiB heap | **Conservative placeholder, not a Spring/JVM guarantee.** Measure it. |
| Planning value per SSE | 64 KiB heap | **Placeholder.** Native/socket/proxy memory is additional and must be measured via RSS/NMT. |
| Transient-allocation reserve | 60 MiB | Recommendation for JSON serialization, bursts, GC timing, class loading, etc. |
| Initial `MAX_GAMES` | 500 | Safe pre-measurement starting limit. |
| Tested target `MAX_GAMES` | 1,000 | Raise only after heap/RSS/GC/load tests. |
| Initial `MAX_SSE` | 64 | At two streams per fully connected game, this permits 32 fully connected games. |
| Tested upper target | 128 | 64 fully connected games; only raise after actual-host testing. |

Using the illustrative values at 1,000 games and 128 SSE streams gives approximately:

\[
1000\times16KiB = 15.625MiB
\]

\[
128\times64KiB = 8MiB
\]

so

\[
90+15.625+8+60=173.625MiB
\]

of modeled heap, just under the chosen ~179 MiB post-GC planning target. That arithmetic is useful for admission design, but **the 16 KiB and 64 KiB coefficients are deliberately assumptions**. An object-heavy representation using nested collections, strings, listener closures, cached JSON, or per-client queues can be much larger.

The correct way to obtain those coefficients is differential measurement:

1. Warm the JVM with zero games and streams; record post-GC live heap and process RSS.
2. Create, for example, 10,000 representative games without SSE, stabilize the heap, and calculate `Δheap / 10,000`.
3. Remove them, open 64 then 128 representative SSE streams, and calculate `Δheap / N` and `ΔRSS / N`.
4. Repeat through the **actual public HTTPS endpoint**, because TLS termination, proxies, HTTP versions, and native buffers change the result.
5. Repeat with slow clients and update bursts rather than measuring only idle streams.
6. Use `jcmd GC.class_histogram`, heap dumps in non-production tests, and `VM.native_memory summary`/`summary.diff` to see where memory actually went. Oracle warns that some heap inspection commands have significant impact, so these diagnostics belong in controlled testing rather than routine high-frequency production polling. citeturn20view0

For garbage collection, **do not begin by tuning generations or pause targets**. Oracle's GC documentation notes that G1 is selected by default on server-class machines; a fractional-CPU, 512 MB environment should therefore not be assumed to have the same ergonomic selection as a conventional multi-core server. Inspect the collector actually selected, then benchmark the JDK's ergonomic choice against Serial GC for this small heap and simple workload. citeturn19view1

For this particular application, ultra-low-latency collectors are unlikely to be the first optimization target. A Battleship game has tiny long-lived state, modest update frequency, and a small heap; on a `0.1` CPU host, extra concurrent GC activity can matter more than shaving already-small pauses. The production decision should be based on **after-GC occupancy, allocation rate, GC wall-clock percentage, and request/SSE latency under the target load**, not on a collector's marketing category.

The TTL implementation should also remain deliberately boring. Store games in a bounded thread-safe map and run **one periodic sweep every 30 seconds**, rather than one timer per game. Each access independently verifies expiry before returning state, so the sweep controls reclamation latency, not semantic expiry. At 500 games a 30-second sweep examines about 16.7 entries/second on average; at 1,000 games it is about 33.3 entry checks/second. The algorithm is `O(N)` per sweep, but at these bounded values its cost should be negligible compared with framework/network overhead.

Use a monotonic elapsed-time source for TTL comparison. Java's `System.nanoTime()` is specifically documented for measuring elapsed time rather than wall-clock time, so clock corrections cannot accidentally extend or prematurely expire an in-process game. citeturn14search1

There is one concurrency trap in TTL cleanup: a sweeper must not read “expired,” race with a client's TTL refresh, and then delete the newly refreshed game. Perform expiry re-check and removal atomically with respect to the game's current deadline, for example with `ConcurrentHashMap.computeIfPresent`, a per-game lock, or a compare-and-remove generation/version.

**Recommended configurable starting limits:**

| Configuration | Initial recommendation | Operational reason |
|---|---:|---|
| `GAME_TTL` | 15 min | Product requirement. |
| `TTL_SWEEP_INTERVAL` | 30 s | Cheap bounded scan; semantic expiry is checked lazily too. |
| `MAX_GAMES` | 500 | Raise toward 1,000 only after measured retained heap and soak tests. |
| `MAX_SSE_GLOBAL` | 64 | Conservative for 0.1 CPU; test toward 128. |
| `MAX_SSE_PER_GAME` | 2 | One stream per player; no spectator amplification by default. |
| `MAX_SSE_PER_PLAYER` | 1 | A new stream replaces/closes an older stream for that seat. |
| Tomcat `maxConnections` | ~256 | Leave room for SSE plus short HTTP requests without exposing an 8192-connection default. Tomcat's current defaults are documented here. citeturn14search0 |
| Tomcat worker threads | ~32 | A small bounded pool is more appropriate to fractional CPU; SSE should use Servlet async rather than retaining one request worker per stream. Spring documents MVC async/SseEmitter support. citeturn19view2 |
| Request JSON body | ≤16 KiB | Battleship commands are tiny; enforce at application/filter/proxy level. Tomcat's `maxPostSize` is not a universal arbitrary-JSON body limit. citeturn14search0 |
| HTTP request header limit | keep ~8 KiB | Current Tomcat default is 8 KiB; there is no reason for this API to increase it. citeturn14search0 |
| Pending per-SSE data | latest state or ≤64 KiB | Prevent slow clients from creating unbounded queues. |
| Graceful shutdown budget | 20 s | Matches the documented Spring Boot example; provider shutdown grace must still be verified. citeturn21view3 |

## Realtime transport, timeouts, heartbeats, overload, and abuse resistance

SSE needs **three different timeout concepts**, which should not be conflated.

First, a server connector's ordinary connection/request-read timeout concerns how long the server waits for request data. Current Tomcat documentation, for example, defines `connectionTimeout` around receipt of the request URI line, and `keepAliveTimeout` around waiting for another request on a persistent connection. Those are not the lifetime of a successfully established SSE response. citeturn14search0

Second, Servlet asynchronous processing has its own timeout. Current Tomcat documentation gives a 30-second default async timeout, while Spring explicitly says the default async timeout depends on the underlying Servlet container unless the application sets it. An SSE application should therefore **set the `SseEmitter`/MVC async timeout explicitly** instead of hoping the embedded-container default happens to be suitable. citeturn14search0turn19view2

Third, there is an **upstream/provider request or proxy timeout** that the application does not control. Cloud Run, as one documented example, defaults request timeout to five minutes and permits configuration up to 60 minutes; Google also warns that a reconnect is a new request and is not guaranteed to reach the same instance. Render separately documents HTTP responses up to 100 minutes. These figures demonstrate why stream lifetime must be provider-specific rather than hard-coded from Tomcat documentation. citeturn18view5turn21view0

A robust timeout ladder is therefore:

| Layer | Recommendation |
|---|---|
| Ordinary API handler | Design create/join/move/snapshot to complete in hundreds of milliseconds; treat multi-second execution as overload or a bug because there is no database/external call in the critical path. |
| Client timeout for ordinary reads | About 3–5 s, then retry reads safely. |
| SSE heartbeat | 15 s. |
| Application SSE lifetime | Intentionally finite; start with 10 min **only when the host permits it**, otherwise choose <80% of the host's documented absolute request timeout. |
| Spring async/SseEmitter timeout | Explicitly slightly longer than the planned application stream rotation, or use the timeout itself to initiate reconnect. |
| Provider absolute timeout | Must be discovered/documented per host and treated as authoritative. |
| Reconnect delay | ~1–3 s initial with jitter/backoff, capped around 15 s during an outage. |

The WHATWG SSE specification explicitly recommends a comment line beginning with `:` roughly every 15 seconds to help protect connections against intermediaries that drop idle HTTP streams. That is strong support for a heartbeat such as `: ping\n\n`. It is **not** a guarantee that an arbitrary proxy will retain the stream, and it cannot defeat a provider's absolute request-duration limit or an instance replacement. citeturn19view6

At 64 connected clients, a 15-second heartbeat produces only about 4.27 heartbeat writes per second; at 128 clients, about 8.53 writes/second. The application payload itself is tiny, although TCP/TLS/HTTP framing means actual wire traffic is larger. The bandwidth model is:

\[
BW_{out} \approx
N_{SSE}\frac{B_{heartbeat-wire}}{15s}
+
\lambda_{events}B_{event-wire}
\]

Measure `B_wire` from real traffic rather than estimating it from the eight or ten visible heartbeat characters.

Browser limits are another reason to keep **one** EventSource per player rather than opening separate streams for game state, turn status, chat, presence, etc. MDN warns that HTTP/1.x browsers traditionally have a very low per-browser/domain SSE connection cap—six in the cited Chrome/Firefox behavior—whereas HTTP/2 multiplexes streams with a negotiated concurrent-stream limit. citeturn19view8

Every event should carry the current `gameVersion` as its SSE `id`. Browsers retain event IDs for reconnect behavior, and the protocol permits the server to send a `retry` value controlling reconnection time. citeturn19view7 However, **do not interpret Last-Event-ID as durable replay capability**. Since this service has no persistent event log, the simplest bounded design is:

```text
SSE connects/reconnects
        |
        v
compare Last-Event-ID / client's gameVersion
        |
        +-- same version --> continue
        |
        +-- behind/unknown --> send authoritative full game snapshot
```

A Battleship state is sufficiently small that sending the latest authorized snapshot is much simpler than retaining an unbounded per-game event history. An optional tiny in-memory event ring can optimize same-process reconnects, but the client must still be correct when the ring is missing because a restart erased it.

Snapshot HTTP responses can expose the `gameVersion` as an ETag and support conditional reads to make fallback polling cheap. RFC 9110 defines entity tags and conditional request headers such as `If-None-Match`; this provides standard HTTP semantics rather than inventing a custom “has state changed?” endpoint. citeturn16view0

**Capacity rejection must happen before resource exhaustion.** Do not create a game and then discover that the process is over capacity. Admission should be backed by an atomic permit/counter rather than `map.size()` followed by creation, which is race-prone under concurrent requests.

Use semantically different responses:

- `429 Too Many Requests` for a caller exceeding an IP/player/game request-rate budget; RFC 6585 explicitly defines 429 for rate limiting and permits `Retry-After`. citeturn17view1
- `503 Service Unavailable` with `Retry-After` for temporary **global** capacity exhaustion or draining; RFC 9110 defines 503 for temporary overload/maintenance and permits `Retry-After`. citeturn17view0turn17view2
- `409 Conflict` for a stale `gameVersion`, already occupied seat, or explicit server-epoch conflict where the request cannot apply to current server state.
- `404 Not Found` when the current process simply has no such game.
- `410 Gone` only when the current process can actually establish that an object expired; after a restart, without persistent tombstones, it cannot reliably distinguish “expired previously” from “never existed here.”

Reasonable **starting**, not guaranteed-optimal, anonymous rate limits are:

| Action | Initial limit |
|---|---:|
| Create game | 3/min/IP, burst 5; optionally 30/hour/IP |
| Join attempts | 10/min/IP |
| Game mutations | 5/sec/player token, burst 10 |
| Snapshot reads | 1/sec/player token, burst 5 |
| SSE opens/reconnects | 6/min/player token, burst 3 |
| Reconnect admission globally | e.g. 20 new SSE streams/sec |
| Concurrent streams/player | 1 |
| Concurrent streams/game | 2 |

These are intentionally much higher than normal human Battleship behavior while still limiting trivial automation. Because there is no account identity, combine limits: source IP **and** an opaque per-player/game capability. IP-only identity is weak: the SSE standard itself notes that multiple clients can share an IP and an individual client can appear behind different proxies. citeturn19view6 Long-window anonymous quotas also reset on every JVM restart unless stored externally.

Denial-of-service protection should focus on **resource multiplication** rather than just request count. OWASP's API Security guidance treats uncontrolled CPU, memory, bandwidth, and similar consumption as a resource-consumption vulnerability and recommends limits such as rate and input-size restrictions. citeturn19view9 For this game that means bounding:

- live games;
- open SSE streams;
- streams per game/player;
- request bodies and headers;
- concurrent request processing;
- reconnect frequency;
- command frequency;
- queued outbound data per slow stream;
- tombstones/event histories;
- logs.

Never maintain an unbounded outbound event queue for a slow browser. Battleship does not need every intermediate notification preserved: retain/coalesce to the **latest game version**, and if a client falls behind, close its stream and require a fresh snapshot. That turns a slow-consumer memory leak into a bounded reconnect.

## Lifecycle, restarts, graceful shutdown, and graceful realtime degradation

Free hosting makes lifecycle events part of the normal product experience rather than rare disaster scenarios. As of August 18, 2026, Render documents 512 MB RAM and `0.1` CPU for a Free web service, spins free web services down after 15 minutes of inactivity, and explicitly reserves the ability to restart one at any time. citeturn18view0turn18view1turn18view2 Koyeb's Free Instance also provides 512 MB/0.1 vCPU, scales to zero after one hour without traffic, cannot disable that behavior, and is explicitly recommended only for testing/hobby use rather than production. citeturn18view3turn18view4

That means a process startup must always begin conceptually as:

```text
games          = empty
SSE clients    = empty
rate-limit state = empty
serverEpoch    = newly generated value
readiness      = false until initialization finishes
```

There should be **no “recovery” code that pretends old games still exist** unless external persistence is later introduced.

The alignment between a 15-minute game TTL and Render's currently documented 15-minute free-service inactivity sleep must not be treated as a guarantee. The host and application have different definitions of activity, transport traffic may affect host idleness differently, and Render independently states that a Free service can restart at any time. citeturn18view1turn18view2

Cold-start behavior must therefore be visible in the client. During a wake-up, the first API/SSE connection may take substantially longer than the normal game latency. Koyeb documents 1–5 second startup for its deep-sleep scale-to-zero mode, but that figure is provider-specific and must not be generalized to Render or another service. citeturn18view4 A browser should display “Connecting/starting server” rather than interpreting the first slow request as a lost game.

For planned termination, use Spring's graceful-shutdown facilities but add game-specific draining. Current Spring Boot documentation states graceful shutdown is enabled by default for its embedded Tomcat, Jetty, and Reactor Netty servers and shows `spring.lifecycle.timeout-per-shutdown-phase=20s` as the configurable grace period. It also makes clear that new-request rejection semantics vary by server. citeturn19view3turn21view3

A recommended shutdown sequence is:

```text
SIGTERM / application context closing
        |
        v
set draining = true
        |
        +--> reject new game creation with 503 + Retry-After
        +--> refuse new SSE subscriptions
        +--> readiness -> false if provider semantics make that safe
        |
        v
send "server-draining" SSE control event where possible
        |
        v
complete/close existing SseEmitters
        |
        v
allow already-running short mutations to finish
        |
        v
wait within bounded shutdown budget
        |
        v
process exits
        |
        v
new process starts with EMPTY game map
```

Closing streams proactively matters because otherwise long-lived asynchronous SSE requests can consume much of the graceful-shutdown window. Even a perfectly implemented sequence remains **best effort**: an OOM kill, `SIGKILL`, VM/host failure, or provider replacement may offer no usable termination notice.

Readiness during draining requires provider awareness. On Render, an HTTP health check succeeds only if a 2xx/3xx response arrives within five seconds; after 15 seconds of consecutive failure Render temporarily stops routing traffic, and after 60 seconds it restarts the instance. Because a restart destroys every in-memory game, **do not deliberately fail readiness merely because the game cap is full**. A full instance is still healthy enough to serve its existing games; it should reject only additional admission. citeturn18view6turn21view4

Realtime delivery should be a **performance feature, not a correctness dependency**. When SSE fails:

```text
SSE healthy
   |
   | disconnect
   v
UI shows "Live updates reconnecting"
   |
   +--> EventSource reconnect with jitter/backoff
   |
   +--> after short failure window, begin snapshot polling
           |
           +--> conditional GET every ~3 s
           +--> back off toward ~10 s when unchanged
           |
           +--> commands still use ordinary HTTP
   |
SSE re-established
   |
   v
receive full/versioned snapshot
   |
   v
stop fallback polling
```

The browser can continue sending game commands while SSE alone is unavailable, provided normal HTTP is still reachable. Every command should include an expected game version or an opaque command ID so a retry does not accidentally execute twice **within the surviving JVM**. Across a crash boundary, exactly-once behavior is not achievable without durable command state.

The UI should distinguish at least four conditions:

| Condition | User experience |
|---|---|
| SSE temporarily disconnected, HTTP works | “Live updates reconnecting”; enable polling; gameplay may continue. |
| API overloaded | Preserve local UI; show temporary capacity/rate-limit message; obey `Retry-After`. |
| Game expired | Explicit “Game expired after inactivity”; return to lobby/create flow. |
| `serverEpoch` changed | Explicit “Server restarted; this ephemeral game was lost.” Never display “reconnecting to game” indefinitely. |

This snapshot-first recovery model also avoids making `Last-Event-ID` promise more than in-memory state can provide. SSE supports event IDs and reconnection semantics, but durable event replay requires a durable source that this architecture intentionally does not have. citeturn19view7

## Health, observability, logging, and load testing

Current Spring Boot Actuator exposes dedicated liveness and readiness groups, including `/actuator/health/liveness` and `/actuator/health/readiness`; it can additionally expose `/livez` and `/readyz` on the main server port. Spring explicitly warns that a probe on a separate management stack can misleadingly succeed even when the actual application server cannot accept connections. citeturn19view4

A suitable **health and observability checklist** is:

- **Liveness:** `/livez` is allocation-light, fast, and checks that the application's request-processing path has not fatally wedged. It does not fail because `MAX_GAMES` or `MAX_SSE` is reached.
- **Readiness:** `/readyz` becomes true only after startup initialization and the TTL scheduler/admission controller are functioning; false while deliberately draining.
- **No external dependency in liveness:** Spring recommends that liveness not depend on external systems because doing so can trigger cascading restarts. This application has no database anyway, so its liveness check should remain local. citeturn19view4
- **Provider check:** verify the provider probes the same public server stack. For Render, configure an HTTP health-check path rather than relying only on a TCP socket check if application-level readiness matters. citeturn18view6
- **Restart visibility:** expose JVM uptime/start time and log a startup record containing a new `serverEpoch`, build version, JDK version, heap maximum, and configured capacity.
- **No secrets in health:** do not expose game/player tokens, state, environment secrets, heap dumps, or detailed management data on the public health endpoint.

Spring Boot's Micrometer integration already publishes JVM memory, buffer-pool, garbage-collection, thread, class-loading, process/system CPU, file-descriptor, uptime, startup, and HTTP server-request metrics; Tomcat metrics can also be exposed when its MBean registry is enabled. citeturn21view2turn19view5

Add low-cardinality application metrics:

| Metric | Purpose |
|---|---|
| `games.live` | Main state-capacity gauge |
| `games.created` | Creation rate / abuse indicator |
| `games.expired` | TTL behavior |
| `games.capacity_rejected` | Evidence that game cap is reached |
| `sse.connections` | Realtime occupancy |
| `sse.opens`, `sse.reconnects` | Reconnection storm detection |
| `sse.send_failures` | Dead clients/proxy trouble |
| `sse.capacity_rejected` | Connection cap pressure |
| `realtime.poll_fallback_clients` | Detect systemic SSE failure |
| `ttl.sweep.duration` | Cleanup-cost regression |
| `ttl.sweep.removed` | Expiry wave size |
| `rate_limit.rejected` by endpoint class | Abuse/false-positive signal |
| command conflict/version mismatch count | Retry/race correctness |
| ordinary API latency/error histograms | User-visible health |

Never use `gameId`, player token, client IP, or `serverEpoch` as an unrestricted metrics tag. Those values have high cardinality; keep epoch/build identifiers in logs or resource metadata instead.

Reasonable **starting alert thresholds**, to be tuned from real measurements rather than treated as universal JVM rules, are:

| Signal | Warning / action |
|---|---|
| Process RSS | >80% host memory for 5 min: warn; near 90%: stop new-game/SSE admission |
| Post-GC heap | >70–75% of `Xmx` sustained: inspect leak/capacity |
| Live games | >80% `MAX_GAMES`: warn |
| SSE streams | >80% `MAX_SSE`: warn |
| Unexpected HTTP 5xx | >1% for 5 min: investigate |
| Normal API p95 | >500 ms sustained: investigate CPU/GC/host throttling |
| GC pause/GC time | material sustained increase from tested baseline |
| Reconnects | abrupt multi-fold increase: proxy/network/restart signal |
| Rate/capacity rejection | sustained non-zero growth: attack or under-provisioning |
| JVM uptime reset | alert unless correlated with known deployment |
| Health failures | immediate operational event, because on some providers repeated failure triggers process replacement |

Logs must be intentionally sparse. Render currently processes at most **6,000 application-generated log lines per minute per instance** and drops excess lines, with retention dependent on plan. citeturn18view7 Do not log every SSE heartbeat, fallback poll, or successful health probe. At INFO level, keep startup/shutdown, unexpected errors, deployment/build metadata, aggregate admission/rate-limit events, and perhaps game create/expire lifecycle at controlled volume. Player capability tokens must never be logged.

Load testing should run both against a locally resource-constrained replica and through the **actual hosting proxy**. Proxy timeouts, sleeping, TLS, HTTP/2, cold-start behavior, and provider health logic cannot be reproduced by an unconstrained localhost benchmark. Gatling has first-class SSE operations for opening, checking, and closing streams, which makes it suitable for the realtime portion of this test suite. citeturn19view10

**Recommended load-test scenarios:**

| Scenario | Load shape | Acceptance target |
|---|---|---|
| Functional SSE smoke | Two browsers: create, join, commands, reconnect | Correct `gameVersion`, no duplicated/missed final state |
| Nominal steady load | 500 live games; 32 fully connected games/64 SSE; representative moves | Stable RSS and post-GC heap; no unexplained 5xx; event delivery comfortably within near-realtime target |
| Tested connection ceiling | Ramp 64 → 128 SSE | No OOM/thread explosion; measured per-stream heap/RSS coefficient remains bounded |
| Beyond connection ceiling | Attempt 129+ after chosen hard limit | New streams rejected deterministically; existing games remain responsive |
| Game-cap test | Create exactly configured cap, then more | Cap+1 rejected cleanly; no race allowing map growth past bounded allowance |
| Reconnect storm | Drop 64–128 streams simultaneously and reconnect over several seconds | No OOM, no runaway thread/task queue; rate limiter/jitter protect service; snapshots restore correctness |
| Idle/proxy test | Hold SSE with only 15 s heartbeat for longer than planned stream life | Observe heartbeat delivery; deliberate rotation/reconnect succeeds; record actual intermediary behavior |
| TTL wave | Create 500–1,000 games in a narrow window, then stop meaningful access | Expiry batch does not cause CPU/GC spike; semantic expiry correct even before sweeper removes entry |
| TTL race | Repeatedly access games exactly around expiry boundary | No sweeper deletes a legitimately refreshed game |
| Slow-consumer test | Client stops reading or reads extremely slowly | Per-client memory remains bounded; server eventually disconnects/coalesces instead of accumulating events |
| Polling degradation | Block/fail SSE while keeping ordinary HTTP available | Client automatically uses snapshots; game remains correct; polling does not refresh business TTL unintentionally |
| Soak | 2–4 hours at ~70–80% configured capacity | No monotonic after-GC heap/RSS/connection growth |
| Abuse: creation | High-rate anonymous game creation from several sources | Per-source/global admission works; legitimate existing games remain usable |
| Abuse: oversized input | Oversized JSON, excessive parameters/headers | Request rejected before expensive parsing/retention |
| Abuse: reconnect | Rapid connect/disconnect loops | Stream-open limiter and global cap protect CPU/memory |
| Graceful SIGTERM | Terminate under 50–80% load | New admission stops; SSE clients get best-effort drain signal; process exits within configured grace |
| Abrupt crash | `SIGKILL`/container replacement equivalent | On new epoch, game map is empty and clients explicitly report restart/state loss |
| Cold-start/sleep | Allow actual free host to sleep | First request wakes service as provider promises; UX handles startup delay; old in-memory games are **not** assumed recoverable |
| Memory-pressure/breakpoint | Increase games/connections until protection triggers | Admission rejection occurs before host OOM; determine true safe ceiling |

Suggested initial load-test SLOs—not guarantees—are: normal server-side API p95 below roughly 250–500 ms and p99 below one second at nominal load; SSE state update visible to a connected test client well inside two seconds; no OOM/restart; no unbounded live-heap/RSS slope; and no unexpected 5xx. Deliberate `429` and admission `503` responses should be evaluated separately rather than counted as mysterious application failures.

## Deployment checklist and provider-dependent hosting constraints

The current free-host landscape illustrates why operational guarantees must remain provider-specific.

| Provider/example | Current documented behavior relevant to this design | Consequence |
|---|---|---|
| **Render Free web service** | 512 MB RAM, 0.1 CPU; 750 free instance-hours/workspace/month; free service can be restarted at any time; no scaling beyond one instance; no persistent disk; spins down after 15 min inactivity and wakes on incoming HTTP/WebSocket request. citeturn18view0turn18view1turn18view2 | Architecturally compatible with a disposable single JVM, but **cannot provide game-state continuity**. Treat arbitrary restart as normal failure mode. |
| **Render request/health behavior** | Render documents HTTP responses up to 100 minutes. HTTP health checks require 2xx/3xx within 5 s; 15 s consecutive failure removes traffic temporarily and 60 s causes restart. citeturn21view0turn21view4 | Explicitly rotate SSE below provider limits; keep health independent of “game capacity full.” |
| **Koyeb Free Instance** | 512 MB/0.1 vCPU/2 GB SSD; one free instance per organization; cannot use persistent volumes; scales to zero after one hour without traffic; Koyeb explicitly says Free Instances should not be used for production. citeturn18view3 | Suitable as a hobby/test deployment, not a basis for a production availability guarantee. |
| **Koyeb scale-to-zero behavior** | Scale-to-zero considers incoming traffic/held connections; free-instance scale-to-zero is mandatory. Koyeb documents 1–5 s startup for deep-sleep mode. citeturn18view4 | Cold start and process loss must be handled explicitly; do not generalize timing to another provider. |
| **Cloud Run as a managed-host timeout example** | Default request timeout 5 min, configurable to 60 min; reconnect is not guaranteed to reach the same instance. citeturn18view5 | An in-memory game must force single-instance behavior if used there, but even that does not prevent replacement. SSE must reconnect before/at timeout. |

For an explicitly **free** production-like deployment, the conclusion is uncomfortable but clear: free tiers can host the application, but their lifecycle terms generally prevent a meaningful continuity SLA for in-memory games. Render's arbitrary-restart statement is enough by itself to rule out a guarantee that a 15-minute game will remain available for all 15 minutes. citeturn18view1 Koyeb goes further by explicitly stating its Free Instance should not be used for production. citeturn18view3

The deployment checklist should therefore be treated as a release gate:

- [ ] **Pin a supported JDK and Spring version**, and run the same version in load tests.
- [ ] **Set an explicit heap maximum** appropriate to host RAM rather than consuming most of the container with Java heap. For a measured 512 MB process, begin around `-Xmx256m`. Oracle's current JVM memory options are documented below. citeturn19view0
- [ ] Record at startup the effective `Xmx`, selected GC, JVM/container memory, configured game/SSE limits, application build, and fresh `serverEpoch`.
- [ ] Enforce `MAX_GAMES`, `MAX_SSE`, one SSE/player, and two SSE/game independently.
- [ ] Keep the provider at **one application instance**. Do not enable horizontal scaling with in-memory authoritative state.
- [ ] Configure the actual host memory/CPU quota in staging/load test; do not benchmark only on a developer laptop.
- [ ] Explicitly set the Spring MVC/SseEmitter async timeout. Spring warns that otherwise the timeout depends on the underlying container. citeturn19view2
- [ ] Verify provider absolute request timeout and test a heartbeat-only stream through the public HTTPS proxy.
- [ ] Emit a comment heartbeat every ~15 seconds, following WHATWG's interoperability guidance. citeturn19view6
- [ ] Deliberately rotate long-lived SSE streams and ensure reconnect always starts from a current snapshot/version.
- [ ] Ensure transport heartbeats, automatic reconnect, and automatic polling do **not accidentally extend the 15-minute business TTL**.
- [ ] Run TTL cleanup every ~30 seconds, but enforce expiry on access independently.
- [ ] Bound slow-client output instead of queuing events indefinitely.
- [ ] Add request body/header limits and disable unused parsing/upload features.
- [ ] Configure source-IP and player/game capability rate limits plus global admission.
- [ ] Return `429` for client rate limiting and `503 + Retry-After` for global temporary capacity where a response can still be generated. citeturn17view1turn17view0
- [ ] Expose `/livez` and `/readyz` on the actual application port and configure the provider HTTP health path. Spring recommends main-port probes where a separate management port could hide main-server failure. citeturn19view4
- [ ] Do not make “all game slots occupied” a liveness/readiness failure.
- [ ] Configure a ~20-second application shutdown phase, then test the provider's real termination behavior. Spring's graceful shutdown is bounded, not durability. citeturn21view3
- [ ] Close SSE streams deliberately during planned draining.
- [ ] After a deploy/restart, verify `serverEpoch` changes and the game map begins empty.
- [ ] Make the frontend render an explicit “server restarted — ephemeral game lost” state.
- [ ] Test cross-origin deployment even when production normally bundles the frontend; configure exact CORS/CSP origins rather than `*`. citeturn3search18turn3search9
- [ ] Do not place player secrets in logs; do not log heartbeat/poll traffic at INFO.
- [ ] Export JVM/process/HTTP/custom capacity metrics; verify alerts actually function on the selected hosting plan.
- [ ] Run nominal, ceiling, reconnect-storm, TTL-wave, slow-client, soak, graceful-shutdown, abrupt-restart, and cold-start tests through the production proxy before raising configured caps.

## Failure modes and guarantees impossible without external persistence

The following failure table assumes the authoritative game state remains strictly inside one JVM.

| Failure mode | Detection | Correct behavior | State impact | Mitigation |
|---|---|---|---|---|
| Planned deploy | Shutdown/drain lifecycle, build change | Stop admission; notify/close SSE best effort | **All remaining games disappear when old JVM terminates** | Deploy only when acceptable, or introduce persistence; graceful shutdown cannot migrate games |
| Provider arbitrary restart | JVM uptime/server epoch changes | New empty instance; explicit restart message | **All games lost** | `serverEpoch`, honest UX; external persistence is the only continuity solution |
| Host scale-to-zero/sleep | Host lifecycle/cold first request | Wake; initialize empty JVM | **Previous process state lost** | Treat sleeping host as potentially destructive; do not advertise resume |
| OOM / memory-limit kill | RSS/heap alerts, uptime reset | New process if host restarts | **All games lost** | Heap headroom, admission limits, bounded queues, stress tests |
| JVM crash / `SIGKILL` | Epoch/uptime change | Empty restart | **All games lost; no final SSE** | Same; there is no in-memory recovery path |
| Graceful SIGTERM | Lifecycle hook | Drain new admission, close streams, finish short requests | State remains only until process exits | 20 s bounded drain; never claim durability |
| CPU throttling | latency/CPU/GC metrics | Keep serving existing games; reject new admission if necessary | Normally none unless host restarts | Low thread count, caps, load test on 0.1 CPU |
| Excessive GC | GC metrics, latency, heap after-GC high | Reduce admission; investigate leak/allocation | None until OOM/restart | Smaller bounded load; correct heap sizing; measure collector |
| Game cap exhausted | `games.live == MAX_GAMES` | `503 + Retry-After` for creation | Existing games intact | Hard atomic admission permit |
| SSE cap exhausted | active stream counter | Reject new stream; client uses polling | Game state intact | App-level cap; polling fallback |
| Per-client rate exceeded | limiter | `429 + Retry-After` | State intact | IP + participant/game-token limit |
| Distributed abuse | elevated create/open/request rates | Global admission/rejection | Existing games should remain protected | Hard global caps; host/WAF controls where available |
| Proxy idle timeout | SSE disconnect/reconnect counters | Reconnect, then snapshot | State intact | ~15 s comment heartbeat; verify actual proxy |
| Absolute request timeout | periodic stream closure | Deliberate reconnect and snapshot | State intact | Rotate before provider limit |
| Browser/network offline | EventSource error, fetch failures | Backoff; show offline/reconnecting | Server game continues until TTL | Snapshot on return; TTL remains authoritative |
| Realtime endpoint broken, HTTP healthy | SSE failures while REST succeeds | Poll snapshots; commands continue over HTTP | State intact | Realtime is optional for correctness |
| HTTP API unavailable | failed commands/snapshots | Disable uncertain actions; retry carefully | Unknown to client until recovery | Command IDs/versioning; never assume failed response means command was not applied |
| Lost mutation response | client timeout after server may have changed state | Snapshot before blind retry, or retry with command ID/version | Potential duplicate without idempotency | Per-command IDs/version preconditions |
| SSE event missed | version gap | Fetch/send full authorized snapshot | No state loss | `gameVersion`; do not require event replay |
| Slow SSE client | queue occupancy/send errors | Coalesce to latest state or disconnect | No game-state loss | Hard per-client buffer bound |
| SSE reconnect storm | reconnect-rate spike | Jitter, admission limit, snapshot recovery | No state loss while JVM survives | Global reconnect rate ceiling |
| TTL sweeper delayed | sweep-duration metric | Expiry still checked on every access | Small temporary memory retention only | Semantic expiry independent of sweep |
| TTL sweep/touch race | concurrency test | Refresh must win if logically later | Could wrongly delete game if coded badly | Atomic deadline re-check/removal |
| Log flood | log-rate metrics/provider drops | Reduce/suppress repetitive logs | Observability loss | No heartbeat/poll INFO logs; aggregate counters |
| Health check too aggressive | probe failures/restart | Host may replace JVM | **All games lost unnecessarily** | Liveness only for genuine broken state; capacity is not sickness |
| Frontend/backend CORS misconfiguration | browser console/network errors | UI reports API configuration failure | Backend state may still exist | Same-origin default; separately test independent-origin contract |
| Free-tier quota/suspension | provider dashboard/status | Service inaccessible | Eventually state lost if process stops | Cannot guarantee around provider quota; monitor and communicate |

Finally, the following guarantees are **fundamentally impossible under the stated architecture**. More JVM tuning, more heartbeats, graceful shutdown, or better SSE code cannot create them.

**Game survival across JVM/process/container restart is impossible.** A Java object graph exists only in that JVM. Render explicitly allows arbitrary restarts of Free web services, and scale-to-zero providers can destroy the running process. citeturn18view1turn18view4

**Game survival across a deployment is impossible.** A new deployment starts a new process with a new heap. A platform's “zero-downtime deployment” for network traffic does not migrate Java objects from the old process into the new one.

**Seamless resume of the exact pre-restart board, turn, winner state, player capabilities, and TTL deadline is impossible.** The new process has no source from which to reconstruct those values.

**Durable SSE replay across a restart is impossible.** `Last-Event-ID` tells the server what the browser last saw, but an empty post-restart JVM has neither the game nor an event log to replay. SSE's protocol support for IDs does not itself constitute storage. citeturn19view7

**Exactly-once mutation processing across a crash boundary is impossible.** Suppose the JVM applies a “fire at B7” command and crashes after changing memory but before its HTTP response reaches the browser. After restart there is neither the updated game nor a durable command-id record; the system cannot establish whether that particular command was committed.

**A durable distinction between “this game expired,” “this game was deleted,” and “this ID never existed” is impossible after a restart.** In-memory tombstones vanish with the same process as the games.

**Long-window rate-limit guarantees across restarts are impossible.** An hour/day IP counter held only in memory resets with the JVM. Persistent enforcement needs a durable/shared limiter store.

**High availability or failover is impossible.** A replacement instance can make the URL available again, but it cannot continue the game. Availability of the HTTP service and availability of an existing in-memory game are different properties.

**Safe horizontal scaling is impossible without shared authoritative state or routing that permanently binds every game to one surviving instance.** Even session affinity is insufficient for failure recovery; Cloud Run, for example, explicitly notes that a reconnect is not guaranteed to reach the same instance. citeturn18view5

**Guaranteed zero-state-loss deployments are impossible.** Draining can allow an existing match to run briefly on the retiring process, but once that process terminates, the state is gone. Delaying termination merely postpones the loss.

**Guaranteed realtime delivery is impossible.** Browsers disconnect, networks partition, proxies close streams, hosts impose request lifetimes, and processes restart. What can be guaranteed by application design is **eventual resynchronization to the latest surviving in-memory snapshot while that same JVM still possesses it**, not guaranteed delivery of every SSE event. citeturn19view6turn18view5

**A guarantee that every admitted game will live for its full 15-minute TTL is impossible on a free host that reserves arbitrary restart rights.** The application can guarantee “expire no earlier than the configured inactivity rule while this process remains alive,” but provider restart is an independent termination condition. Render's current Free-service documentation makes that distinction explicit by allowing restarts at any time. citeturn18view1

The resulting production contract should therefore be stated plainly: **this is a bounded, single-process, ephemeral game service. Realtime delivery is recoverable through snapshots; overload is handled by admission rejection; ordinary process-lifetime faults are observable and degradable; but process loss means game loss. Any requirement to survive restart, deploy, scale-to-zero, node failure, or failover changes the architecture and requires authoritative state outside the JVM.**
