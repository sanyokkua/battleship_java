# Production Java/Spring Architecture for an Anonymous Ephemeral Battleship Game

## Architecture baseline and module boundaries

**Overall recommendation.** Build this as a **single-node, bounded, in-memory Spring Boot application with an imperative domain core, Spring MVC for REST and SSE, per-game serialization, opaque capability credentials, and explicit resource limits everywhere**. The most important architectural property is not the choice of cache or HTTP framework; it is that every potentially attacker-controlled dimension—games, command history, SSE replay, subscriber queues, rate-limit keys, request sizes, asynchronous work, and connection count—has a hard bound.

As of August 18, 2026, Spring Boot's current reference documentation lists Spring Boot 4.1.0 as stable; its system requirements state that it requires Java 17 or later and supports Java versions through 26. A reasonable baseline is therefore **Spring Boot 4.1.x on Java 25 where the hosting platform supports it**, with the exact JDK pinned to what the host can reliably run. citeturn17search0turn25search1

The recommended shape is:

```text
                         same public origin
 ┌──────────────────────────────────────────────────────────────┐
 │ Browser                                                      │
 │ static frontend  ─── REST /api/v1 ───┐                       │
 │                  └── SSE  /api/v1 ───┼─────────────────┐     │
 └───────────────────────────────────────┼─────────────────┼─────┘
                                         │                 │
                             auth / CSRF / rate limits     │
                                         │                 │
                              ┌──────────▼──────────┐       │
                              │ API v1 adapters     │       │
                              │ DTOs + ProblemDetail│       │
                              └──────────┬──────────┘       │
                                         │                 │
                              ┌──────────▼──────────┐       │
                              │ Application layer   │       │
                              │ commands / queries  │       │
                              └──────────┬──────────┘       │
                                         │                 │
                    ┌────────────────────▼────────────────┐ │
                    │ Bounded SessionRegistry             │ │
                    │ ConcurrentHashMap<GameId, Slot>     │ │
                    │ + capacity permits                  │ │
                    └────────────────────┬────────────────┘ │
                                         │ lock per game    │
                              ┌──────────▼──────────┐       │
                              │ SessionSlot         │◄──────┘
                              │ immutable Game ref  │
                              │ dedupe ring         │
                              │ SSE replay ring     │
                              │ subscribers         │
                              │ lastAccessNanos     │
                              └──────────┬──────────┘
                                         │
                              ┌──────────▼──────────┐
                              │ Pure domain model   │
                              │ commands → new Game │
                              │          + events   │
                              └─────────────────────┘
```

The Java concurrency library explicitly describes `ConcurrentHashMap` as supporting concurrent retrievals and high concurrency for updates, but it also warns that aggregate status such as `size()` can reflect transient states during concurrent modification and should generally not be used for program control. That distinction is central here: use `ConcurrentHashMap` for safe lookup and atomic insertion/removal, **not** `map.size() < maxSessions` as admission control. citeturn18search0

**Recommended module structure.**

| Module | Responsibilities | Dependencies and restrictions |
|---|---|---|
| `game-domain` | `Game`, `Board`, `Fleet`, player roles, phases, invariant checking, domain `Command` and `DomainEvent`, pure transition logic | **No Spring, HTTP, Jackson, persistence, SSE, cookies, clocks, or logging dependencies.** |
| `game-application` | Create/join game use cases, execute command, get player view, open event subscription, projections, application ports | Depends on `game-domain`; sees interfaces for registry/security/realtime rather than Servlet classes. |
| `game-infrastructure` | `InMemorySessionRegistry`, `SessionSlot`, TTL sweeper, token hashing, rate limiting, event ring, subscriber hub, metrics adapters | Implements application ports; may use Java concurrency, Caffeine, Micrometer. |
| `game-api-v1` | Request/response DTOs, API command DTOs, controller mappings, validation, `ProblemDetail`, SSE event envelope | Maps API types to application commands and application projections to response DTOs. Never exposes domain classes. |
| `game-boot` | `@SpringBootApplication`, Spring Security configuration, executor configuration, Actuator, scheduling, properties, static resources | Composition root only. |
| `frontend` | Independently built HTML/CSS/JS application consuming only `/api/v1` | Its production build is copied into the Boot JAR, but its source is not coupled to Java internals. |

Spring Boot supports static resources from classpath locations such as `/static`, and its executable-JAR mechanism packages application classes under `BOOT-INF/classes` and dependencies under `BOOT-INF/lib`. This makes a multi-module build compatible with a single distributable JAR. citeturn25search2turn26search1turn26search6

**Recommendation:** maintain those boundaries even if the initial repository uses one Gradle/Maven project and Java packages rather than six physical artifacts. Physical modules make accidental coupling harder, but logical boundaries are the important part.

A representative immutable transition API is:

```java
public interface GameCommand {
    CommandId id();
    PlayerRole actor();
}

public record DomainResult(
        Game next,
        List<DomainEvent> events
) {}

public final class GameRules {
    public DomainResult handle(Game current, GameCommand command) {
        // Validate invariant and command against current state.
        // Construct a new Game value.
        // Do not mutate current.
        throw new UnsupportedOperationException("example");
    }
}
```

Oracle's Java core-libraries guidance notes the fundamental concurrency advantage of immutable objects: immutable state can be shared without the synchronization requirements of mutable state; it also cautions, in effect, that an unmodifiable collection is not deeply immutable if its elements remain mutable. citeturn2view0turn3view0

That implies several implementation rules:

A `Game` aggregate may use records and final classes, but **record syntax alone does not make referenced mutable collections deeply immutable**. Store `List.copyOf(...)`, immutable value objects, primitive masks, or defensive copies. Do not expose mutable arrays or `BitSet` instances without copying. The current aggregate reference can therefore be replaced atomically after a successful command while old snapshots remain valid for readers.

Internally, commands such as `PlaceFleet`, `Ready`, `Fire`, and `Resign` should generate domain events such as `FleetPlaced`, `PlayerReady`, `ShotResolved`, or `GameFinished`. These are **domain facts**, not Spring `ApplicationEvent`s and not automatically API events. A separate projection layer turns them into player-safe API events. This prevents an internal event containing ship coordinates, for example, from being serialized accidentally to the opponent.

**Verified fact:** Spring Boot can package and run this complete composition as an executable JAR and serve the built frontend from the classpath. citeturn25search2turn26search1

**Recommendation:** use a pure immutable domain with a small mutable `SessionSlot` shell around it.

**Trade-off:** this allocates a new aggregate after each accepted move. Battleship state is tiny, so the simplicity and concurrency safety dominate the allocation cost.

**Uncertainty:** exact allocation/GC behavior depends on the selected representation and JVM. It must be measured under load rather than estimated from source-code field counts.

## Session lifecycle, concurrency, and capacity

The session registry should have three distinct responsibilities that are often mistakenly collapsed into a cache:

1. locate a game;
2. decide whether it is still logically alive;
3. enforce a hard global admission limit.

Those responsibilities are better made explicit.

A recommended session shell is conceptually:

```java
final class SessionSlot {
    final ReentrantLock lock = new ReentrantLock();

    // Guarded by lock:
    Game game;
    long lastClientAccessNanos;
    boolean closing;

    final RecentCommands dedupe;
    final EventReplayRing replay;
    final SubscriberSet subscribers;

    SessionSlot(Game game, long nowNanos, /* ... */) {
        this.game = game;
        this.lastClientAccessNanos = nowNanos;
        // ...
    }
}
```

The main registry becomes:

```java
final ConcurrentHashMap<GameId, SessionSlot> sessions;
final Semaphore sessionPermits;
```

A counting `Semaphore` maintains an explicit number of permits, which is exactly the primitive needed for strict resource admission. By contrast, `ConcurrentHashMap.size()` is not suitable as a concurrent admission invariant. citeturn16search1turn18search0

### Session lifecycle and TTL algorithm

**Recommended semantic definition of “last client access”:** an access is **authenticated inbound activity from a player** that reaches the game service after cheap abuse checks: a state GET, an accepted or domain-rejected authenticated command, initial/reconnecting SSE establishment, or an explicit presence operation. Server-generated SSE heartbeats do **not** refresh TTL.

That distinction matters. If every server heartbeat refreshed `expireAfterAccess`, an abandoned browser tab could pin a game indefinitely without sending application traffic. Conversely, if a long-open SSE connection never counts after initial establishment, a completely idle page expires after 15 minutes. For this game, I recommend the latter unless product requirements explicitly say that a visible idle tab should preserve the game.

When visible-tab presence should count, add a low-frequency authenticated endpoint such as:

```text
POST /api/v1/games/{gameId}/presence
```

and have the frontend call it only while visible, perhaps every few minutes. Its interval is a tuning recommendation, not part of the security protocol. It should not change the aggregate version.

Use `System.nanoTime()` or an injected monotonic equivalent for the inactivity deadline. The Java API explicitly states that `nanoTime()` is intended for elapsed-time measurements and is unrelated to wall-clock time; it recommends comparing a timeout using a difference such as `System.nanoTime() - start >= timeout`. citeturn16search0

Keep a separate `Clock`/`Instant` only for human/API timestamps.

The access path should behave like this:

```java
AccessResult withLiveSession(GameId id, PresentedCapability cap, Operation op) {
    SessionSlot slot = sessions.get(id);
    if (slot == null) {
        return unavailable();
    }

    CleanupPlan cleanup = null;

    slot.lock.lock();
    try {
        // The slot may have been removed while this request waited.
        if (slot.closing || sessions.get(id) != slot) {
            return unavailable();
        }

        long now = monotonicClock.nanoTime();

        // CRITICAL: expiry is checked before touching lastAccess.
        if (elapsed(slot.lastClientAccessNanos, now) >= TTL_NANOS) {
            cleanup = expireLocked(id, slot);
            return unavailable();
        }

        if (!capabilityService.matches(slot, cap)) {
            return unavailable();
        }

        slot.lastClientAccessNanos = now;

        return op.executeAgainst(slot);
    } finally {
        slot.lock.unlock();
        if (cleanup != null) {
            cleanup.runOutsideLock();
        }
    }
}
```

The rule **check expiry before touch** prevents a late request from resurrecting an already expired game.

The sweeper uses the same logical test:

```text
every ~5–15 seconds:

for each (gameId, slot) visible in registry:
    read candidate age
    if candidate might be expired:
        lock slot
        re-check:
            registry still maps gameId -> same slot
            !closing
            now - lastAccess >= 15 min
        if true:
            mark closing
            remove(gameId, slot)
            release capacity permit exactly once
            capture subscribers for termination
        unlock
        complete subscribers outside lock
```

Java's `ScheduledExecutorService` directly supports fixed-rate or fixed-delay periodic work. citeturn18search2

The registry must also perform the expiry check **on every game access**, not only in the background sweep. That makes the 15-minute rule logically precise even when the scheduler is delayed by GC, CPU throttling, or host suspension. The sweep is then primarily memory reclamation rather than the authority that decides whether a request may use an expired game.

When the creation endpoint cannot acquire a session permit, it can perform one opportunistic bounded/full expiry sweep and retry `tryAcquire()` once. If capacity is still unavailable, return `503 Service Unavailable`, not arbitrary eviction of an active game.

### Why custom registry rather than Caffeine as the lifecycle authority

Caffeine is a strong in-memory cache implementation. Its documented policies include `maximumSize`, `expireAfterAccess`, variable expiration, prompt scheduling through a `Scheduler`, and injectable `Ticker`s for deterministic expiry testing. It also documents that `expireAfterAccess` considers cache reads and writes to be accesses. citeturn18search3

That makes the options compare as follows:

| Registry design | Advantages | Problems for this game | Verdict |
|---|---|---|---|
| Plain `ConcurrentHashMap` only | Minimal dependency; excellent concurrent key lookup | No TTL, no admission mechanism, no lifecycle callbacks by itself | Insufficient alone |
| `ConcurrentHashMap` + explicit timestamps + sweeper + permit counter | Exact application definition of “client access”; explicit expiry race handling; exact capacity rejection | More code to test | **Recommended for game sessions** |
| Caffeine `expireAfterAccess(15m)` | Mature expiry implementation; straightforward time policy; testable `Ticker` | Internal/cache reads count as access; normal cache policy is not equivalent to game lifecycle semantics | Good only if semantics happen to match |
| Caffeine `maximumSize` + expiry | Automatically bounded | A cache may evict a still-active game to make room; that is a bad user-visible business policy | Reject for primary session capacity |
| Caffeine custom `Expiry` plus explicit lifecycle wrapper | Can encode sophisticated expiry | Ends up rebuilding much of the explicit lifecycle layer anyway | Valid, but unnecessary complexity |

A particularly important distinction is **capacity rejection versus cache eviction**. When all allowed games are genuinely active, a new game should receive `503` rather than silently killing an existing session because an eviction algorithm considers it least valuable.

Caffeine remains excellent for **auxiliary, attacker-keyed short-lived data** such as rate-limit buckets, invalid-code backoff records, or a small create-request dedupe cache, because those are caches whose entries may legitimately disappear. Always set both expiry and a maximum size. citeturn18search3

### Per-session command serialization

`ConcurrentHashMap` only protects operations on the map. It does not make this safe:

```text
read game
check "whose turn?"
apply shot
increment version
publish events
```

when two requests execute the sequence concurrently. `ConcurrentHashMap`'s thread-safety guarantees therefore do **not** replace an aggregate-level concurrency policy. citeturn18search0

For Battleship, a `ReentrantLock` per `SessionSlot` is the simplest production choice.

Within the lock, an authenticated command follows this order:

```text
lookup and lock
    ↓
re-check slot identity / closing / expiry
    ↓
authenticate player capability
    ↓
touch last client access
    ↓
look up commandId in bounded dedupe window
    ├─ same command + same normalized payload → duplicate success
    └─ same commandId + different payload → 409
    ↓
check expected optimistic version
    ├─ stale → 412
    └─ current
    ↓
domain authorization and rule validation
    ↓
Game current
    ↓ pure transition
Game next + DomainEvent(s)
    ↓
next.version = current.version + 1
    ↓
assign slot.game = next
assign monotonically increasing API event ID(s)
append bounded replay entries
enqueue to bounded subscriber queues
unlock
    ↓
perform SSE I/O outside session lock
```

Two details matter.

First, **deduplication happens before the stale-version check**. Suppose command `C` at version 17 is successfully applied and produces version 18, but the HTTP response is lost. The exact retry still presents version 17. If version validation runs first, the server would incorrectly report `412`; finding the previously accepted `commandId` first lets it answer as a duplicate success without applying the move twice.

Second, no network write, JSON streaming, logging sink, or other potentially blocking I/O runs under the game lock.

An optimistic version and a server-side lock solve different problems:

- the lock linearizes simultaneous server transitions;
- the version prevents a client from knowingly or unknowingly applying an action to stale state.

Both are required.

**Rejected implementation:** one `Executors.newSingleThreadExecutor()` per game. Java documents that this executor guarantees sequential execution but uses an **unbounded queue**. A thread/executor/mailbox per attacker-created session is exactly the kind of unbounded resource multiplier this application should avoid. citeturn18search1

A shared actor/mailbox implementation with bounded per-game mailboxes could work, but for two-player Battleship it is materially more complex than a short critical section.

### Memory and capacity model

Do not choose `maxSessions` from intuition. Measure the heap footprint and use an explicit budget.

A useful model is:

```text
H_process_target
  = H_base
  + Nsessions × H_session_P99
  + Nsse × H_subscriber_P99
  + H_rate_limit_maps
  + H_request_burst
  + H_executor_queues
  + H_GC_headroom
```

or, solving for game capacity:

```text
Nmax_memory =
    floor(
      (H_heap_budget - H_base - H_burst_reserve - H_other_bounded_structures)
      / measured_P99_session_footprint
    )

Nmax =
    min(
      Nmax_memory,
      floor(maxSseConnections / maxSseConnectionsPerGame),
      host-tested CPU limit,
      configured business limit
    )
```

An **illustrative**, not prescriptive, example: if a 256 MiB heap leaves 96 MiB specifically for live game slots and load testing finds a P99 live-session footprint of 64 KiB including replay/dedupe/subscriber objects, the arithmetic limit is 1,536 sessions. A production setting should be appreciably lower because process memory also includes native stacks, code cache, metaspace, socket buffers, and burst allocations. The actual figure must come from a representative load test, not this example.

Everything inside a slot should have an explicit maximum:

| Resource | Recommended bound |
|---|---|
| aggregate | fixed by game rules |
| players | exactly two |
| recent command IDs | e.g. 64–128 per player |
| API event replay | e.g. 64–128 events per game |
| active SSE subscribers | e.g. 1–2 per player |
| subscriber pending queue | small fixed queue, e.g. 8–32 events |
| event payload size | schema-level upper bound |
| room/invite token count | fixed |
| scheduled tasks | global scheduler, not timer-per-session |

Those particular queue sizes are **starting configuration values**, not standards; test them with the real event sizes and reconnection behavior.

Use a `Semaphore(maxSessions)` or equivalent CAS-based admission counter. Acquire before inserting a new game and release exactly once when that slot transitions to `closing` and is removed. Never rely on `ConcurrentHashMap.size()` for correctness. citeturn16search1turn18search0

**Verified facts:** Java supplies the necessary concurrent-map, semaphore, monotonic-time, and scheduling primitives; Caffeine supports size/time eviction but defines access in cache terms. citeturn18search0turn16search1turn16search0turn18search2turn18search3

**Recommendation:** explicit `ConcurrentHashMap + SessionSlot + Semaphore + monotonic timestamp + sweeper`.

**Trade-off:** more lifecycle code than `expireAfterAccess`, but the semantics, resource accounting, and race handling become visible and testable.

**Uncertainty:** whether a permanently open SSE counts as ongoing “access” is a product-semantic question, not a Java question. The architecture should encode the chosen definition explicitly.

## Anonymous security and abuse resistance

The system has no identity provider, so authorization is necessarily **capability-based**: possession of an unguessable credential is what proves that a request acts as player A or player B.

RFC 6750's bearer-token security model is directly relevant even though these credentials do not need to be OAuth access tokens: a bearer credential grants authority to whoever possesses it, so disclosure is the core threat; the RFC requires protected transport and specifically warns against putting bearer tokens in page URLs because URLs can leak into logs, browser history, and other structures. citeturn24search0

### Capability design

Generate independent values for:

```text
public gameId       = random, unguessable resource identifier
human roomCode      = usability locator, NOT primary authorization
host capability     = 32 random bytes
guest invite secret = 16–32 random bytes
guest capability    = 32 random bytes after join
```

Java's `SecureRandom` is specifically defined as a cryptographically strong random-number generator. citeturn24search1

For player capabilities, 32 random bytes encoded as base64url without padding is a comfortable design. The server stores:

```text
SHA-256(capability bytes)
role
revocation/generation state if needed
```

rather than retaining the plaintext credential. Java's `MessageDigest` supports SHA-256 as a standard digest and provides `MessageDigest.isEqual` for digest equality comparison. citeturn24search2

A slow password hash is not needed for a uniformly random 256-bit credential: unlike a human password, there is no low-entropy dictionary to stretch. The important requirements are secure randomness, transport protection, non-logging, and a sufficiently large token space.

Revocation is therefore cheap: clear/replace the expected digest, revoke the unused guest invitation as soon as the join protocol permits, and remove all capabilities automatically with the game session.

Token validity should be bounded by **server state**, not only cookie expiration. An expired/removed `SessionSlot` makes the credential useless even if a browser still retains its cookie.

### Cookie versus Authorization bearer

For this particular single-origin browser game, **HttpOnly cookies are the better default for player capabilities**.

RFC 6265 defines `Secure` as limiting a cookie to secure channels and `HttpOnly` as preventing exposure through browser script APIs; the two attributes can be combined. citeturn24search3

Recommended credential cookie attributes are therefore:

```text
Secure
HttpOnly
SameSite=Strict
Path=/api/v1/games/{gameId}
no Domain attribute
```

Use a game-specific cookie name as well, for example a safe fixed prefix plus a short non-secret identifier derived from `gameId`, so concurrent games in different tabs do not rely on ambiguous same-name cookie ordering.

Do not rely on `Path` itself as an authorization boundary. RFC 6265 explicitly cautions that the Path attribute is not a security mechanism; authorization still binds the presented capability to the `gameId` and player role on the server. citeturn24search3

A session cookie with no long-lived expiration is reasonable because backend TTL is authoritative. An optional absolute game lifetime can also be reflected in `Max-Age`, but a cookie fixed at `Max-Age=900` would be wrong for a sliding 15-minute server session unless it were refreshed.

**Why not just `Authorization: Bearer`?** It works well for `fetch` REST calls, but then JavaScript must possess the bearer credential. That increases the value of any XSS bug. More importantly, native browser `EventSource` is deliberately simple: the standard constructor provides the URL and a credentials option, not an arbitrary user-supplied `Authorization` header facility. The SSE specification also defines automatic reconnect and `Last-Event-ID`. citeturn5search0turn19search2

A same-origin HttpOnly cookie therefore authenticates both REST and native `EventSource` without putting a credential into the URL or exposing it to application JavaScript.

Never use:

```text
GET /events?token=<player-capability>
```

RFC 6750's URL-leakage warning is directly applicable. citeturn24search0

### Cookie authentication means CSRF must remain in scope

HttpOnly stops script from **reading** the capability; it does not make cookie-authenticated state-changing requests immune to CSRF.

Spring Security documents CSRF protection and provides `CookieCsrfTokenRepository` as an alternative to its default `HttpSessionCsrfTokenRepository`. citeturn16search2turn16search10

That is a good fit for this application because it avoids creating a second generic server-side HTTP session solely for CSRF state.

Use:

```text
player capability:
    HttpOnly, Secure, SameSite=Strict

CSRF token:
    separate browser-readable CSRF cookie
    echoed in a custom header on state-changing REST operations
```

and retain exact-origin checks as an additional defensive layer. Spring Security's documentation treats SameSite as defense in depth rather than a complete replacement for CSRF protection. citeturn5search3

For `/events`, `GET` remains side-effect-free in game terms. Establishing a subscriber may allocate a bounded server resource but must never execute a game command.

### XSS and browser hardening

Because an XSS payload running in the game origin could issue authenticated requests even without reading the HttpOnly capability, frontend injection resistance remains important.

Spring Security supplies security-header infrastructure but explicitly does **not** invent a Content Security Policy automatically because the correct policy is application-specific. citeturn16search3turn16search11

A static SPA should be able to enforce a tight policy along the lines of:

```text
default-src 'self';
script-src 'self';
style-src 'self';
connect-src 'self';
img-src 'self' data:;
object-src 'none';
base-uri 'none';
frame-ancestors 'none';
```

adjusted to the actual frontend build. Avoid inline scripts where practical; do not embed secrets into HTML.

### Room-code enumeration

A **short human room code must not be the only authorization secret** if resistance to enumeration is a requirement.

Use the room code as a locator:

```text
roomCode -> gameId
```

and require a high-entropy `inviteSecret` to claim the guest role. A share-link flow can carry that secret into the frontend and then submit it in a POST body rather than making it an API query parameter. The server stores only its digest.

After successful guest admission:

```text
invite capability → revoked
guest player capability → issued
```

This cleanly separates:

- something convenient to type;
- something sufficiently secret to authorize joining;
- the ongoing player credential.

A manual **code-only** mode is a deliberate security downgrade. Longer codes and strict throttling improve it, but they do not provide the same assurance as a cryptographically strong invitation secret.

Use an unguessable `gameId` too. That way random scanning of `/games/{id}` is ineffective even before the player capability is evaluated. Unknown game, expired game, and wrong capability should normally produce the same externally bland response, typically `404`, so the endpoint does not become a useful existence oracle.

### Replay and duplicate commands

Capability authentication answers “which player may act?” It does not answer “has this network command already been applied?”

Every mutable in-game request should include a client-generated `commandId`, for example a UUIDv4 or equivalent 128-bit random identifier:

```json
{
  "commandId": "501768aa-43bf-4bff-986c-a5fc6f169661",
  "type": "fire",
  "target": { "x": 4, "y": 7 }
}
```

Per player, retain a bounded recent-command table:

```text
commandId -> {
    normalizedCommandFingerprint,
    acceptedGameVersion,
    lastEventId
}
```

If an identical ID and fingerprint is seen again, do not re-execute the domain command. If the same ID is paired with different semantic content, reject it with `409 Conflict`.

The optimistic version provides a second replay barrier: once a command ID has eventually aged out of the bounded dedupe ring, an exact old request still carries an obsolete expected version and fails.

This prevents accidental duplicate application and straightforward replay of captured requests. It **cannot** stop an attacker who has stolen the bearer capability from issuing a fresh, valid command with a new ID. That is intrinsic to bearer credentials; credential-theft prevention and fast expiration are therefore primary controls. citeturn24search0

The IETF HTTPAPI `Idempotency-Key` work is worth knowing about, but as of August 18, 2026 the working-group draft is not a finalized RFC and the tracked draft has expired. Do not silently assume semantics from an unfinished standard. Define `commandId` and its conflict/retry rules explicitly in the application's v1 contract. citeturn7search3turn7search11

### Abuse-prevention matrix

Rate limiting should be layered rather than “one requests-per-IP number.” RFC 6585 defines `429 Too Many Requests`, permits `Retry-After`, leaves identification/counting policy to the server, and explicitly notes that under severe attack a server need not spend resources generating a 429 response for every request. citeturn19search0

| Threat | First-line controls | Resource bound / behavior | Residual risk |
|---|---|---|---|
| Random path scanners | Cheap routing/404, no stack traces, restrictive actuator exposure, request/header limits | No game allocation | Scanner still consumes network/HTTP parsing |
| Session-creation bot | Per-source bucket + global creation bucket + exact `Semaphore` capacity | Creation returns `429` for client rate limit or `503` when server capacity is full | Distributed botnets bypass simple IP quotas |
| Room-code enumeration | Strong invite secret; per-source join limit; high-entropy `gameId`; uniform failure | No role granted from room code alone | Code-only UX remains weaker |
| Invalid capability brute force | 256-bit random capability, TLS, hash-only storage, early reject | No domain work; rate-limit repeated failures | Compromised browser/token is different from brute force |
| Command flood by valid player | Per-capability and per-game command bucket | Bounded CPU; queue no work unboundedly | Valid user can intentionally keep an idle-time session active |
| Duplicate/replayed mutation | `commandId` dedupe + optimistic version | Bounded recent-command ring | Stolen capability can create fresh valid commands |
| SSE reconnect storm | Per-capability/IP connect limiter, max active streams/player | Fixed subscriber count | Legitimate unstable networks need tolerant limits |
| Slow SSE reader | Tiny bounded subscriber queue; disconnect on overflow | No unbounded response backlog | Client may reconnect repeatedly; reconnect also rate-limited |
| Rate-limit key explosion | Caffeine expiry + hard `maximumSize` + global bucket | Attacker cannot grow limiter map indefinitely | Cache churn may weaken per-IP fairness, so global bound is essential |
| Oversized JSON / headers | Small request-body/header/path limits before expensive processing | Fixed parsing/memory ceiling | Exact limits need host/framework tuning |
| Executor exhaustion | Bounded executors/queues and rejection policy | No unbounded task accumulation | May intentionally shed streams during overload |
| Distributed application-layer DDoS | All application bounds plus hosting-provider/CDN/WAF controls where available | Instance survives longer by shedding work | **Cannot be solved fully inside one free-tier JVM** |

Suggested rate numbers should be treated as deployment parameters. A reasonable starting shape—not a standard—is much stricter on anonymous creation/join than on authenticated gameplay. For example, creation might allow only a few attempts per source per minute, while a player capability may receive a small burst of commands because a Battleship client has no legitimate reason to send hundreds per second. Tune from legitimate NAT/mobile traffic and attack tests rather than hard-coding these examples.

**Verified facts:** bearer-token secrecy, TLS, cookie attributes, CSRF facilities, and HTTP 429 semantics are standardized/documented. citeturn24search0turn24search3turn16search2turn19search0

**Recommendation:** opaque random capabilities in Secure/HttpOnly/SameSite cookies, hash-only server storage, strong one-time guest invitations, layered bounded rate limiting, CSRF protection, and no authentication secrets in URLs.

**Trade-off:** cookie authentication simplifies native SSE and protects the token from direct JavaScript access, but it adds CSRF obligations.

**Uncertainty:** no application-local rate limiter can reliably distinguish legitimate users from a sufficiently distributed botnet. Edge controls are the only meaningful additional layer if that threat becomes material.

## Versioned REST and realtime contract

The entire browser/backend boundary should be treated as a separately versioned product. The domain model is not that contract.

A compact v1 surface can be:

```text
POST /api/v1/games
    create game

POST /api/v1/game-joins
    present roomCode + inviteSecret

GET  /api/v1/games/{gameId}
    player-specific current view

POST /api/v1/games/{gameId}
    submit one application command against the game

POST /api/v1/games/{gameId}/presence
    optional authenticated inactivity-lease refresh

GET  /api/v1/games/{gameId}/events
    authenticated SSE
```

The recommendation to submit commands to the game resource itself is deliberate. It lets `If-Match` naturally describe a precondition on the current game representation instead of applying an ETag obtained from `/games/{id}` to an unrelated `/commands/fire` URI.

A command request remains an API DTO:

```json
{
  "commandId": "501768aa-43bf-4bff-986c-a5fc6f169661",
  "type": "fire",
  "target": {
    "x": 4,
    "y": 7
  }
}
```

The controller maps this to an internal `Fire` command. Jackson never receives a domain `Game`, `Board`, `Fleet`, or domain-event type as an API response.

### Optimistic version contract

`GET /api/v1/games/{id}` returns a **player-specific `GameViewV1` DTO** and an ETag, for example:

```http
ETag: "game-41-host"
```

A guest representation uses a distinct validator such as:

```http
ETag: "game-41-guest"
```

because host and guest representations can contain different bytes due to hidden information.

The next mutation sends:

```http
If-Match: "game-41-host"
```

RFC 9110 explicitly says `If-Match` is commonly used with state-changing methods to prevent lost updates, and a false condition can result in `412 Precondition Failed`. citeturn22view1turn22view2

Require the precondition for all normal in-game mutations. RFC 6585 defines `428 Precondition Required` specifically for servers that require a conditional request, with lost-update prevention as its canonical use. citeturn19search0

Thus:

```text
missing If-Match      -> 428 Precondition Required
wrong/stale If-Match  -> 412 Precondition Failed
```

The application also exposes an integer `version` in the player view and realtime event envelope because it is useful to application code and diagnostics, but the HTTP validator is the mutation precondition.

A successful state-changing command increments the aggregate version **once**, even if it produces several internal domain events. A GET, heartbeat, or presence touch does not increment it.

Optimistic versioning does not replace locking: the lock gives a linear server transition; the ETag prevents stale client intent.

### Idempotency

HTTP defines safe methods, PUT, and DELETE as idempotent; POST is not inherently idempotent, so an application using POST commands needs its own retry semantics. RFC 9110 specifically warns clients not to automatically retry non-idempotent methods unless they know the request semantics are effectively idempotent or can determine whether the original action was applied. citeturn22view0

That is exactly what the bounded `commandId` table supplies.

For an in-game command:

```text
new commandId
    → execute once

same commandId + same normalized command
    → report prior acceptance; no state transition

same commandId + different normalized command
    → 409 command-id-reused
```

A compact `CommandAckV1` can contain:

```json
{
  "commandId": "501768aa-43bf-4bff-986c-a5fc6f169661",
  "acceptedVersion": 42,
  "lastEventId": 108,
  "duplicate": false
}
```

The frontend obtains the authoritative current projection through SSE or a GET, rather than requiring the dedupe store to retain complete historical state representations.

**Create and join are harder.** Anonymous create/join responses establish a new credential. If the network fails at exactly the wrong time, perfect transparent retry can require temporarily retaining/recovering token material or designing a more elaborate handshake. Do not pretend this edge case has the same simple idempotency as an authenticated move.

A practical design is:

- do not blindly auto-retry game creation;
- give join a very short bounded recovery window if UX requires it;
- once a player capability has been received, all ordinary commands use strong `commandId` semantics.

This is one area where the anonymous/no-persistence requirement produces an unavoidable protocol trade-off.

### Error contract

Use RFC 9457 Problem Details everywhere outside successful SSE streams. RFC 9457 is the current Problem Details specification, replacing RFC 7807. Spring MVC directly supports `ProblemDetail`/`ErrorResponse` and selects `application/problem+json` for JSON problem responses. citeturn19search1turn26search2

A typical stale-version response:

```json
{
  "type": "urn:battleship:problem:stale-version",
  "title": "Game state has changed",
  "status": 412,
  "detail": "Refresh the current game view before issuing another command.",
  "instance": "/api/v1/games/...",
  "currentVersion": 42,
  "requestId": "..."
}
```

Recommended status mapping:

| Condition | HTTP status |
|---|---:|
| malformed JSON, out-of-range coordinates, invalid schema | `400` |
| unknown game, expired game, or invalid capability where existence should be masked | `404` |
| authenticated command conflicts with phase/turn/rules | `409` |
| reused `commandId` with different command | `409` |
| stale `If-Match` | `412` |
| required precondition missing | `428` |
| requester-specific abuse limit | `429` with `Retry-After` where useful |
| global game/session capacity exhausted | `503` with `Retry-After` where sensible |
| unexpected server defect | `500`, generic external detail |

RFC 6585 standardizes both 428 and 429; RFC 9110 defines the conditional request semantics underlying 412. citeturn19search0turn22view1

Do not expose Java exception class names, stack traces, capability fragments, room/invite secrets, or internal board state in `detail`.

### API versioning

Use the major version in the path:

```text
/api/v1
```

and keep all REST and SSE schemas under that version. Do not have `/api/v1` REST feeding an unrelated unversioned `/events`.

The external event envelope can still include a schema field for diagnostics:

```json
{
  "schemaVersion": 1,
  "eventId": 108,
  "gameVersion": 42,
  "type": "shot-resolved",
  "data": {
    "x": 4,
    "y": 7,
    "result": "hit"
  }
}
```

Treat additive optional response fields as v1-compatible; breaking meaning, field removal, incompatible type changes, or changed command semantics require v2.

Maintain a **single checked-in API contract artifact** for v1. OpenAPI can describe the REST shapes and the `text/event-stream` endpoint plus its event JSON schemas; document SSE replay/reconnect semantics alongside that same artifact rather than creating a second independently versioned contract.

### SSE event ordering and replay

The browser SSE specification defines an `id` field, automatic reconnection, and transmission of `Last-Event-ID` on reconnect. It also defines `retry` and comment lines, which are useful for heartbeat traffic. citeturn19search2

Use an independent monotonically increasing `eventId` per game:

```text
aggregate version: increments once per accepted command
event ID:          increments once per externally publishable API event
```

A command may therefore produce:

```text
version 42
event 108
event 109
```

without conflating the two counters.

Assign event IDs while holding the game's serialization lock. Then append role-safe representations to the bounded replay ring before exposing them to subscribers. That guarantees a total publication order matching command order.

On SSE connect:

```text
authenticate
lock SessionSlot

if Last-Event-ID is within replay window:
    register subscriber at current cutoff
    enqueue all events newer than Last-Event-ID
else:
    register subscriber at current cutoff
    enqueue an authoritative player-specific state snapshot

unlock

future events have IDs greater than cutoff
```

Registration and replay/snapshot selection must be atomic with respect to command publication; otherwise a command can fall into the gap between “read current state” and “start subscribing.”

Treat `Last-Event-ID` as hostile input. Parse only the bounded format you define; do not let it become a database/cache key that triggers arbitrary memory use.

A replay-ring miss is **normal**, not a fatal error. Send a current snapshot or tell the client to GET one. This is why the replay ring can remain small and bounded.

### Backpressure and slow clients

No server-side SSE implementation should assume that because game events are infrequent, all clients will read them promptly.

For each subscriber:

```text
small bounded FIFO
+
"draining" flag
+
global bounded I/O executor
```

Publication only enqueues. One drain task per subscriber writes in FIFO order. If the queue is full, disconnect that slow subscriber, remove it from the slot, and let the client reconnect and recover from the replay ring or snapshot.

This is strictly preferable to an unbounded queue.

Reactor's own documentation illustrates the same principle: some sink variants buffer by default and can be unbounded, while bounded queues and limited replay histories are available; `replay().limit(int)` is explicitly distinct from unbounded `replay().all()`. citeturn26search3

### Spring MVC versus WebFlux

Both stacks can implement the API.

Spring MVC's asynchronous request support includes SSE via `SseEmitter`. Spring's documentation states that MVC can support streaming and even reactive backpressure, but the actual response writes remain blocking and occur on another thread. It also warns that the default `AsyncTaskExecutor` used for asynchronous blocking work is not suitable for production load. citeturn23search0

Spring WebFlux instead uses non-blocking I/O and is designed around a small fixed number of event-loop threads. Spring's own guidance says reactive/non-blocking code does not inherently make application work faster; its principal advantage is predictable concurrency with fewer threads and less memory when latency/concurrent I/O is the limiting factor. citeturn23search1

For this application:

| Factor | Spring MVC | WebFlux |
|---|---|---|
| REST commands | Very natural imperative model | Works, but reactive composition adds little |
| In-memory domain transition | Excellent fit | Also works |
| Per-game lock | Straightforward | Blocking an event-loop thread on contention is undesirable |
| SSE | Supported via `SseEmitter` | Native non-blocking streaming |
| Slow network writes | Need controlled I/O threads/queues | Better fundamental I/O model |
| Learning/debug complexity | Lower | Higher |
| Expected benefit without DB/remote I/O | Mostly simplicity | Mainly SSE connection scaling |

**Recommendation: start with Spring MVC + `SseEmitter`**, because the game has no remote database/API latency, sessions are strictly bounded, and each game has only two participants. Configure a real bounded asynchronous/I/O executor rather than relying on defaults. citeturn23search0

Move to WebFlux only if measurement shows that the required number of simultaneous SSE connections makes blocking response writes/thread memory the dominant constraint. If WebFlux is selected, do not simply put the same contended `ReentrantLock` on Netty's event loop; use a non-blocking serialization strategy or move the tiny mutable section onto an appropriate bounded scheduler.

The exact concurrency point where WebFlux becomes advantageous cannot be derived from framework names. It depends on the host's memory limit, socket behavior, event rate, clients, TLS termination, and JVM configuration; Spring itself recommends evaluating the actual benefits rather than assuming reactive is always faster. citeturn23search1

### Disconnect detection

Spring MVC documentation points out a Servlet limitation: the application does not get a simple immediate notification whenever a remote streaming client disappears, so periodic writes are useful because the next write detects the broken client. WHATWG's SSE authoring guidance similarly describes comment lines as keepalive traffic. citeturn23search0turn19search2

Use one global heartbeat scheduler to enqueue SSE comments at a modest interval rather than allocating a timer per subscriber.

A heartbeat:

- detects dead sockets;
- keeps some intermediaries from considering the stream inactive;
- does **not** increment aggregate version;
- does **not** append to replay history;
- does **not** refresh game inactivity TTL.

**Verified facts:** SSE IDs/reconnect are standardized; MVC SSE writes are blocking whereas WebFlux uses non-blocking I/O; Spring supports RFC 9457 directly. citeturn19search2turn23search0turn23search1turn26search2

**Recommendation:** MVC initially, bounded subscriber queues, per-game ordered event IDs, small replay, snapshot fallback.

**Trade-off:** WebFlux handles large numbers of slow concurrent streams more efficiently, but creates considerably more design pressure around non-blocking domain serialization.

**Uncertainty:** only a load test on the target free-tier host can establish which SSE stack gives the better usable session limit.

## Operations, failure modes, and packaging

An in-memory-only game deliberately has a very different operational contract from a conventional durable backend: **process death equals session loss**. Observability and graceful shutdown improve diagnosis and UX, but they cannot turn ephemeral RAM into persistence.

### Observability design

Spring Boot Actuator supplies health and other operational endpoints. Current Boot documentation states that only health is exposed over HTTP by default and warns that exposed actuator endpoints can contain sensitive information. It also notes that defining your own `SecurityFilterChain` makes you responsible for actuator access rules. citeturn25search0

For a public free-tier instance:

```text
public:
    /actuator/health
    possibly only basic UP/DOWN, no sensitive details

not public:
    env
    beans
    mappings
    heapdump
    threaddump
    loggers
    metrics unless appropriately protected/scraped
```

Micrometer is auto-configured by Boot Actuator and supports a simple in-memory meter registry as well as external monitoring registries. citeturn26search0

Useful application metrics are:

```text
game.sessions.active                     gauge
game.sessions.created                    counter
game.sessions.expired                    counter
game.sessions.closed                     counter
game.sessions.capacity_rejected          counter

game.commands                            counter by type,outcome
game.command.latency                     timer
game.commands.duplicate                  counter
game.commands.stale_version              counter

game.auth.invalid                        counter
game.join.invalid_invite                 counter
game.rate_limited                        counter by coarse reason

game.sse.active                          gauge
game.sse.opened                          counter
game.sse.closed                          counter by bounded reason
game.sse.slow_client_disconnect          counter
game.sse.replay_hit                      counter
game.sse.replay_miss                     counter

game.cleanup.duration                    timer
game.cleanup.expired_per_run             distribution
game.capacity.permits_available          gauge

JVM heap / GC / thread metrics
HTTP server request metrics
executor active/queued/rejected metrics
```

Do **not** put any of these into metric tags:

```text
gameId
roomCode
inviteSecret
capability
raw IP address
commandId
```

They either leak sensitive data or create unbounded/high-cardinality telemetry.

Structured logs should similarly record a server-generated request correlation ID and coarse event/result fields, not credentials. Logging an invite/capability is equivalent to publishing a password.

**Health-state recommendation:** being at the configured game limit should **not** mark the whole application `DOWN`. The service can still serve all existing games, and an orchestrator restart would destroy them. Report capacity through a metric and return `503` specifically from new-game creation.

### Graceful shutdown

Spring Boot 4.1 documents graceful shutdown as enabled by default for embedded Tomcat, Jetty, and Reactor Netty, for both servlet and reactive applications. Existing requests receive a configurable grace period while new requests cease being accepted. citeturn25search1

That is useful, but the absence of a state store sets a hard limit:

```text
SIGTERM
  ↓
stop accepting new traffic
  ↓
allow in-flight REST operations to finish
  ↓
best-effort terminate SSE
  ↓
JVM exits
  ↓
all game sessions disappear
```

A best-effort `server-restarting` SSE event can improve UX, but clients **must not depend on receiving it**. Crashes, OOM kills, free-tier suspension, and forced deployment termination can bypass graceful paths.

On restart, an old browser's capability cookie has no corresponding slot. The API should treat that exactly like an unavailable/expired game and let the frontend show a clean “this ephemeral game no longer exists” state.

### Memory pressure behavior

Every logical resource needs a bound before the JVM is under pressure:

```text
hard max sessions
hard max subscribers
hard max replay entries
hard max dedupe entries
hard max rate-limit keys
hard max request body
hard max async queue
hard max concurrent SSE
```

Then **shed new work**, rather than attempting emergency eviction after allocation has already gone out of control.

Primary admission policy:

```text
session permit unavailable
    → reclaim already-expired slots once
    → retry permit
    → 503 if still unavailable
```

An optional second gate may reject creation before the hard maximum when observed heap/GC pressure exceeds a tested threshold, but that needs hysteresis and measurement. The deterministic configured limit should remain the primary protection.

Do not use weak/soft references for game state. A game disappearing because the garbage collector happened to need memory is not a meaningful lifecycle contract.

### Failure-mode catalog

| Failure | Required behavior | Why the design contains it |
|---|---|---|
| Process crash / host restart | Every game is lost; reconnect becomes unavailable | Explicitly accepted consequence of no persistence |
| Graceful deploy | Stop new admission; finish in-flight work where possible; best-effort close SSE | Boot graceful shutdown supports request draining citeturn25search1 |
| Global session capacity reached | Existing games continue; creation returns `503` | Exact admission permit |
| Client-specific rate exceeded | Return `429`, optionally `Retry-After` | RFC 6585 semantics citeturn19search0 |
| Cleanup scheduler runs late | Expired request still rejected | Every access performs expiry-before-touch |
| Sweeper races with command | Exactly one wins; removed slot cannot be resurrected | Same slot lock + identity recheck + `remove(key,value)` |
| Game expires with active SSE | Mark closing; remove; close subscriber resources outside lock | Explicit closing state and subscriber set |
| Browser disconnects silently | Heartbeat eventually hits failed write and cleanup runs | Spring MVC/Servlet streaming guidance citeturn23search0 |
| Very slow SSE reader | Fixed queue fills; disconnect client | No unbounded backpressure buffer |
| Replay ring overrun | Send current snapshot instead of arbitrary history | Bounded history is a deliberate protocol feature |
| Duplicate command | Return prior acceptance without transition | command-ID table |
| Stale command | `412` | `If-Match` optimistic precondition citeturn22view1 |
| Same command ID, different body | `409` | Detects ambiguous/malicious key reuse |
| Invalid/expired capability | Uniform unavailable result | Reduces game-existence oracle |
| Invite brute force | Rate limit + strong invitation secret | Room code is not authorization |
| Random IP churn against limiter | Bounded Caffeine map may evict individual buckets; global limiter remains | Prevents rate-limiter state itself becoming DoS vector |
| Async I/O executor full | Shed/close stream; never silently allocate more queue | Backpressure bound |
| Out-of-memory despite bounds | Process may die; all games lost | Limits reduce probability but cannot make OOM recoverable |
| Malformed oversized input | Reject before domain execution | Protects parsing and allocation budget |
| Actuator scanner | Only explicitly intended health endpoint visible | Current Boot supports controlled exposure citeturn25search0 |
| Distributed botnet | Protect local capacity; possibly require external edge controls | Single-instance IP reputation cannot identify a distributed attacker reliably |

### Single-JAR packaging with independently deployable frontend assets

Keep frontend compilation independent:

```text
frontend/
  package.json
  src/
  dist/          ← reproducible production artifact

backend/
  game-domain/
  game-application/
  game-infrastructure/
  game-api-v1/
  game-boot/
```

At build time:

```text
frontend build
      ↓
frontend/dist
      ↓ copy
game-boot/build/resources/main/static/
      ↓
Spring Boot executable JAR
```

Spring Boot natively serves classpath `/static` resources and its executable-JAR loader supports nested application dependencies. citeturn25search2turn26search1

Use relative frontend API URLs:

```javascript
fetch("/api/v1/games", ...)
new EventSource("/api/v1/games/" + gameId + "/events")
```

This gives the default deployment one origin:

```text
https://example-host/
https://example-host/api/v1/...
```

which avoids unnecessary CORS complexity and allows native EventSource cookie authentication.

The same `frontend/dist` remains independently deployable to static hosting later. Doing so cross-origin changes the browser security model—CORS, credentialed EventSource, SameSite/third-party-cookie policy—and therefore should be treated as an explicit deployment mode, not something accidentally enabled by permissive `Access-Control-Allow-Origin: *`.

Use content-hashed JS/CSS names for long-lived caching, but keep the shell/index conservative enough that an old HTML document does not pin users indefinitely to a frontend incompatible with the deployed API. Spring Boot itself supports static resource handling and cache-busting facilities. citeturn25search2

**Verified facts:** Boot supplies health/metrics integration, graceful web-server shutdown, static classpath serving, and executable JAR packaging. citeturn25search0turn26search0turn25search1turn25search2turn26search1

**Recommendation:** one same-origin executable JAR for deployment, but preserve a build-time frontend/backend contract boundary.

**Trade-off:** process-local telemetry, session state, and rate-limit history all disappear on restart. That is consistent with the no-external-state requirement but must be accepted operationally.

**Uncertainty:** free hosting providers can impose memory, idle-sleep, connection, proxy timeout, and forced-restart behavior outside Spring's control. Those limits must be tested against the selected provider.

## Proving tests, rejected alternatives, and key uncertainties

A production-quality design is not proven by unit tests of `fire(x,y)` alone. The difficult parts are the cross-boundary races and resource ceilings.

### Proving-test matrix

| Property to prove | Test |
|---|---|
| Immutable domain | Retain references to every previous aggregate version while executing future commands; assert all earlier values remain byte/field-equivalent and invariants still hold |
| Domain invariants | Exhaustive/property-oriented tests for fleet overlap, bounds, turn order, repeated shots, win conditions, ready transitions, resignation |
| Hidden information | For every state/role pair, serialize the API DTO and assert opponent ship coordinates and secret invitation/capability data never appear |
| Single-command linearity | Race two commands against the same version with a barrier; prove at most the valid serialized sequence is committed |
| Optimistic conflict | Two clients read v10; first mutates to v11; second with v10 must get `412` and produce no event |
| Concurrent exact duplicate | Send identical command ID concurrently many times; prove exactly one domain transition/version increment |
| Command-ID abuse | Reuse command ID with changed target; prove `409` and no state change |
| TTL before boundary | Fake monotonic clock to `TTL - ε`; session remains accessible |
| TTL at boundary | Advance to `TTL`; request must not refresh/resurrect it |
| Clock independence | Change wall-clock `Clock` dramatically while monotonic clock does not; inactivity decision remains unchanged |
| Sweeper/access race | Freeze candidate as expired, race sweeper and command; prove either expiry wins or a prior legitimate access wins—never resurrection after removal |
| Capacity race | Launch far more simultaneous create calls than permit count; registry count never exceeds configured hard maximum |
| Permit accounting | Repeated create/expire/close races; available permits eventually return exactly to configured maximum |
| Room-code collision | Force generator collisions; `putIfAbsent` retry never replaces existing game |
| Capability isolation | Host token cannot be used for another game; guest cannot access host-only projection |
| Revocation | Revoke invite/player credential and prove subsequent request fails immediately even if cookie remains |
| CSRF | Cross-site-style state-changing request with capability cookie but absent/wrong CSRF token fails |
| Credential leakage | Capture logs, errors, metrics, serialized DTOs; assert no token/invite value or digest is present where prohibited |
| SSE authentication | Unknown/incorrect capability cannot establish useful stream |
| SSE ordering | Run concurrent accepted commands and prove each subscriber observes monotonically increasing event IDs in commit order |
| SSE reconnect | Disconnect after event N, reconnect with `Last-Event-ID:N`, prove no gap/duplication outside documented duplicate tolerance |
| Replay-window miss | Reconnect with an event ID older than retained history; obtain coherent current snapshot |
| Snapshot/subscription race | Mutate exactly while reconnect registers; client ends with either snapshot+later event or replay sequence, never missing the mutation |
| Slow subscriber | Artificially block writes until queue fills; server disconnects only that subscriber and memory remains bounded |
| Dead SSE | Abort network connection; heartbeat eventually causes subscriber removal |
| Subscriber expiry cleanup | Expire game with all allowed connections active; subscriber count reaches zero and no references retain slot |
| Rate limiter cardinality | Generate a very large number of random attacker keys; limiter-state count remains within configured maximum |
| Global abuse gate | Churn per-IP keys fast enough to defeat local cache retention; global bucket still caps creation work |
| Request-size defense | Fuzz headers, deeply nested JSON, arrays, strings, malformed content; reject before large domain allocation |
| Problem Details | Every known API failure emits the expected RFC 9457 shape and content type |
| API/domain separation | Architecture or serialization test fails if a `game-domain` class appears in v1 controller return type |
| Graceful shutdown | Start REST/SSE traffic, send normal shutdown signal, verify no new admission and expected in-flight behavior |
| Hard restart | Kill process without graceful path; frontend correctly treats all prior games as permanently gone |
| Memory plateau | Sustained create/play/expire cycles at target concurrency; heap returns to stable baseline rather than monotonically growing |
| Endurance | Run repeated 15-minute lifecycle cycles long enough to reveal leaked emitters, executor tasks, or rate-limit keys |
| Overload | Fill sessions + SSE + command bursts and prove queues, threads, heap, and latency remain bounded or work is shed deliberately |

TTL tests should inject a monotonic clock instead of sleeping for 15 minutes. Caffeine itself uses the same philosophy for its timed-eviction tests by supporting a configurable `Ticker`. citeturn18search3

For SSE proving tests, include an actual networked embedded server in addition to controller-unit tests. Servlet disconnect and buffering behavior is precisely the area where an in-process mock is least representative. Spring's documentation notes the special lifecycle/disconnect characteristics of asynchronous streaming. citeturn23search0

### Rejected alternatives

| Alternative | Reason for rejection |
|---|---|
| Database / Redis / Spring Session store | Violates the explicit architecture constraint; also adds network/storage complexity unnecessary for intentionally ephemeral single-node games |
| Mutable `Game` stored directly in `ConcurrentHashMap` | Map thread safety does not make compound game-state transitions atomic citeturn18search0 |
| `map.size() < max` before create | `size()` under concurrent mutation is not an admission-control invariant citeturn18search0 |
| `ConcurrentHashMap.compute()` as the entire transaction engine | Can serialize some per-key changes, but encourages putting validation, history, cleanup, or side effects inside map callbacks; explicit slot locking is clearer |
| One single-thread executor per session | Java's factory uses an unbounded queue, while per-session workers/mailboxes multiply attacker-controlled resource allocation citeturn18search1 |
| One global game lock | Correct but unnecessarily lets unrelated matches block each other |
| Caffeine `maximumSize` as game admission | Cache eviction may choose an active game; global capacity should reject new work instead |
| Caffeine `expireAfterAccess` as sole TTL definition | Every cache read/write is an access, which may not equal “last authenticated client activity” citeturn18search3 |
| Soft/weak references for sessions | Makes lifecycle depend on GC rather than the 15-minute contract |
| Unbounded command history | Resource-exhaustion primitive |
| Unbounded SSE replay | Resource-exhaustion primitive; Reactor itself distinguishes bounded `replay().limit(...)` from unbounded replay citeturn26search3 |
| Unbounded subscriber write queue | A single slow connection can consume arbitrary heap |
| Direct SSE send under game lock | Slow network/client can stall all commands for that game |
| JWT player credentials | Self-contained claims add little because the game must exist in the in-memory registry anyway; revocation still needs state; opaque random capabilities are smaller and simpler |
| Plaintext capability storage | Unnecessary exposure in heap dumps/debugging; equality can be done against a stored digest |
| Room code as sole authorization | Human-friendly entropy and discoverability conflict with strong anti-enumeration requirements |
| Capability in SSE query string | URLs are poor locations for bearer secrets and native EventSource does not require this workaround when cookie auth is available citeturn24search0turn5search0 |
| LocalStorage bearer as default | Makes credential directly available to JavaScript; cookie authentication better matches native SSE |
| SameSite as the only CSRF defense | Spring Security treats CSRF protection as a distinct control; cookie-backed CSRF tokens avoid requiring generic server sessions citeturn16search2turn5search3 |
| WebSocket by default | Game input already fits request/response commands; only server-to-browser notification is needed, so SSE avoids a second bidirectional application protocol |
| WebFlux solely because “realtime” is present | Spring explicitly notes that reactive/nonblocking is not automatically faster; its principal value appears at concurrency/I/O scale citeturn23search1 |
| MVC without a bounded async strategy | Spring explicitly warns that its default async executor is not suitable for production under load citeturn23search0 |
| Publishing domain events directly as JSON | Risks hidden-information leakage and permanently couples internal model evolution to public v1 |
| Returning `Game` domain aggregate from controllers | Same coupling/leakage problem; violates the required DTO boundary |
| Marking full capacity as health `DOWN` | Could cause an orchestrator to restart the only process and destroy all active games; capacity is a creation-level condition, not application death |
| Promising recovery after restart | Impossible without state outside process memory |

### Final recommended configuration

The resulting architecture is deliberately conservative:

```text
Runtime
    Spring Boot 4.1.x
    Java supported by host, preferably current supported release
    Spring MVC + SseEmitter
    Spring Security + CSRF
    Micrometer / Actuator

Game state
    immutable Game aggregate
    long aggregateVersion
    internal domain events
    role-filtered API projections

Registry
    ConcurrentHashMap<GameId, SessionSlot>
    one short critical-section lock per slot
    Semaphore hard session capacity
    explicit lastClientAccessNanos
    15-minute inactivity rule
    one global scheduled sweeper
    access-path expiry recheck

Security
    random unguessable gameId
    human roomCode only as locator
    strong one-time guest invite secret
    256-bit opaque player capabilities
    SHA-256 digest stored server-side
    Secure + HttpOnly + SameSite capability cookies
    TLS only
    CSRF token/header
    no capability in URLs/logs

Commands
    POST against current game resource
    commandId on every mutation
    If-Match optimistic precondition
    bounded dedupe history
    428 missing precondition
    412 stale version
    409 domain conflict / key reuse
    RFC 9457 errors

Realtime
    GET /api/v1/games/{id}/events
    native browser EventSource
    cookie authentication
    monotonic event IDs
    role-safe events
    bounded replay ring
    Last-Event-ID reconnect
    snapshot on replay miss
    small bounded subscriber queues
    slow-client disconnect
    heartbeat that does not touch TTL

Abuse
    per-source limits
    per-capability limits
    per-game limits
    global anonymous-creation limit
    hard session and SSE capacity
    bounded Caffeine maps for attacker-keyed temporary data
    strict request-size bounds

Operations
    health only exposed publicly
    low-cardinality application metrics
    no credentials in logs or metrics
    graceful shutdown enabled
    restart explicitly destroys all games
```

The most important residual uncertainties are empirical rather than architectural. **The safe maximum session count, SSE subscriber limit, MVC-versus-WebFlux crossover, heap safety margin, and useful rate-limit thresholds cannot be proved from Spring documentation alone.** They depend on the actual host, memory ceiling, TLS/proxy layer, event sizes, frontend reconnect behavior, and workload. The proving matrix above should therefore be treated as part of the architecture—not as post-development performance testing.

A second unavoidable uncertainty is anonymous admission during unreliable networks. In-game commands can have excellent retry semantics because a player already owns a capability and the game retains a bounded command history. Initial creation and first guest admission establish the credential itself, so transparent exactly-once recovery across an unknown network outcome requires either a temporary recovery protocol or accepting a rare duplicate/ghost session. That trade-off should be explicit in the v1 contract rather than hidden in frontend retry code.

Finally, no amount of Java locking or Spring Security configuration can make an in-memory single instance durable or withstand an arbitrarily distributed application-layer DDoS. Within the stated constraints, the production objective is therefore **deterministic failure and bounded consumption**: no stale-state corruption, no unauthorized game access from guessable room identifiers, no duplicate shots from network retry, no unbounded queue or registry, and clean failure when process or capacity disappears.
