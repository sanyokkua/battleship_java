# Battleship Reference Implementations: Architecture, Rules, Realtime, Testing, Security, and Adaptation

## Scope, method, and reference comparison

This review focuses on publicly inspectable Battleship implementations that illuminate the design of a **two-player browser game with anonymous temporary sessions, no database, a 15-minute inactivity TTL, near-realtime updates, limited free-tier resources, one API contract, independently replaceable frontend/backend, and an optional single packaged JAR deployment**.

I prioritized source files and tests over screenshots and feature claims. The strongest references are **LAN Games** for server-authoritative rules, hidden-state projection, and tests; **NodeBattleship** as a compact realtime implementation that exposes several instructive failure modes; and **emiliayoffie/Battleship** for a small React/TypeScript client-side model. Two Spring references are included more cautiously: **NSAI_game-server** is a licensed Spring/WebFlux Battleship server but was archived on February 24, 2026, while **Mano-08/server.battleship** is valuable mainly as a negative reference because its repository currently advertises a Spring/Socket.IO backend but exposes only a Spring test under `src/`, not the implementation source that the README implies should exist. citeturn28search0turn28view0turn15view0turn26view0

## Per-project architecture observations

**emiliayoffie/Battleship — useful local-domain model, deliberately unsuitable as multiplayer authority.** The TypeScript model represents a board as a **flat array** rather than a nested matrix. Its square-state enum distinguishes empty, ship, hit, miss, sunk-ship, forbidden, and temporary/awaiting states; coordinates are `{x,y}`; and a `Vessel` contains identity/name, length, optional position, orientation, placement state, and optional sunk state. This makes rendering straightforward because every UI cell can be directly classified. citeturn8view0

The same source also illustrates a subtle modelling smell: it has both richer `Vessel` data and a simpler `Ship` concept. For a small frontend this is manageable, but in a network game multiple overlapping representations of “ship” tend to create conversion code and inconsistencies. A better contract has one authoritative ship-placement representation and distinct, explicitly named **view DTOs** rather than two near-synonymous domain entities. citeturn8view0

The utility tests are instructive because they show both what is tested and what is missing. They verify creation of a 10×10 empty board, index/coordinate conversion, boundary behavior, at least one legal-placement path, and randomized computer fleet generation; the test file itself lists still-uncovered helpers including random orientation/placement behavior, neighbour calculation, sinking checks, and sunk-ship updates. Random placement is exercised without a clearly injected deterministic RNG. citeturn10view1

For the target application, this project should be viewed as a **frontend reference only**. Keeping all truth in a browser is harmless against a local computer opponent, but in a network game it means the opponent can inspect or alter hidden fleet state with browser developer tools.

**NodeBattleship — impressively small, but the transport and domain are fused.** The server keeps a global `users` object keyed by Socket.IO `socket.id`. Each connected user's object has `inGame` and `player`; matchmaking pairs the first two sockets in a waiting room, builds a `BattleshipGame`, moves them to a game room, and puts the same game object into both user records. There is no database or separate session repository. citeturn25view3

Its domain structures are extremely compact. `Player` has two 100-element flat arrays: `shots`, initially zero, and `shipGrid`, initially `-1`. `shipGrid[cell]` stores a ship-array index. Each `Ship` stores `x`, `y`, `size`, hit count and a horizontal flag. This is memory-efficient and easy to reason about, although its magic integers need external knowledge: the shot array uses different integer values for untouched/miss/hit rather than an enum or tagged type. citeturn25view1turn25view2turn25view5

Random placement is server-side and enforces both non-overlap **and non-adjacency**. The adjacency check examines the one-cell perimeter around a candidate ship, including diagonals. After 25 unsuccessful attempts for a ship, placement fails and the constructor can fall back to a predetermined layout. citeturn25view1

Its firing rule is notable: `BattleshipGame.shoot` changes player **only on a miss**. A hit therefore gives another shot. It rejects a previously fired cell by consulting the target's `shots` array, detects victory when the opponent has no unsunk ships, and computes hidden views by returning only sunk enemy ships while returning the complete own fleet. citeturn25view0 This is a legitimate Battleship variant, but it demonstrates why a project must encode the rule explicitly rather than treating “Battleship rules” as universally agreed.

The biggest lifecycle weakness is identity. A player is the current Socket.IO connection ID; disconnect calls `leaveGame`, aborts an unfinished match in favor of the opponent, then deletes that socket's user record. A reconnect necessarily gets a new socket ID, so there is no resumable player identity or reconnect grace period. citeturn25view3

It does have useful server-side checks: the server verifies that the socket belongs to a game and that `game.currentPlayer` equals the socket's player index before accepting a shot. Chat text is HTML-entity encoded. But the shot payload is passed into grid-index arithmetic without a strong schema/type validation layer, and there are no command IDs or expected-state versions. citeturn25view3turn25view0

**LAN Games — the strongest reference for domain boundaries and tests.** Its Battleship module explicitly documents the game state as a top-level `GameState`, two `Player` records, lists of `Ship` objects, shot records and a `TurnState`. A `Ship` carries origin, orientation, derived cell coordinates and hit cells; a `Shot` carries a cell, `hit`/`miss`/`sunk`, optionally the sunk ship ID, and a timestamp. `TurnState` explicitly separates `setup` and `firing`, with `currentPlayerIndex=null` during simultaneous setup. citeturn24view0

This is one of the most useful lifecycle designs found. Instead of pretending setup is a turn, both players may place simultaneously. Each eventually executes a commit/ready operation. The setup-to-firing transition acts as a **barrier**: it occurs when both players have committed. That is a much cleaner state machine than special-casing alternating “placement turns.” citeturn24view0turn18view0

Placement validates player membership, phase, committed status, known ship type, orientation, integer coordinates, origin bounds, full-ship bounds and overlaps. Repositioning is naturally supported by ignoring the old cells of the ship being moved. Unlike NodeBattleship and Calimero's documented rules, this specific implementation checks **overlap but not ship adjacency**, so touching ships are permitted by the inspected rule path. citeturn24view0 That difference should become an explicit API/rules configuration decision in the target rather than an accidental implementation detail.

The hidden-information boundary is especially strong. The module comments identify use of an unfiltered default projection as a critical bug and state that the opponent's `ships` field is **removed**, not merely cosmetically masked. Placement/removal events also deliberately omit coordinates because the events are broadcast to both players. The test suite asserts that an opponent's `ships` field disappears and that a ship-removal event contains no `x` or `y` data. citeturn24view0turn23view0

That is important because hidden information can leak through at least four channels: snapshot state, incremental events, logs, and error messages. LAN Games addresses more than just the first.

The project is not a direct fit for the target, however. The broader framework uses accounts, bcrypt/JWT authentication, embedded SQLite save/resume and spectators. It automatically marks disconnects as AFK and can auto-skip after 30 seconds. Those are sensible LAN-platform features but unnecessary complexity for anonymous 15-minute ephemeral sessions. citeturn18view0

A particularly relevant security caveat is the spectator feature: spectators are intentionally given the full unfiltered state, including Battleship ship positions, while being prevented from issuing game actions. That makes sense for its documented product, but it would be an information disclosure bug if copied into a public two-player service where spectator access is not an explicit requirement. citeturn18view0

**Calimero Battleships — excellent privacy architecture, excessive machinery for the target.** The repository's architecture describes ship placements as private player data that are not replicated, while shared game state is synchronized through CRDT/gossip mechanisms. A shot is proposed through shared logic and resolved on the target player's node against that player's private board before the result becomes shared state. Identity and access are scoped through Calimero namespaces/contexts, and the frontend is a React/TypeScript application consuming generated service APIs. citeturn15view2

Its documented rule set uses the familiar five-ship fleet, straight contiguous ships, **non-adjacent placement**, alternating shots and victory after all enemy ships are sunk. citeturn15view2

The idea worth keeping is **private truth separated from shared/public projection**. The technology should not be carried over: CRDT replication, P2P nodes, namespaces, WASM services and cross-service calls solve a much harder distributed-trust problem than a single authoritative ephemeral server has. citeturn15view2

**Spring references — one overbuilt, one incomplete.** `NSAI_game-server` is explicitly a Spring game server supporting Battleships and Checkers with WebFlux; its repository includes `src/main/java/pl/beny/nsai`, Maven configuration and an MIT license. Its project metadata also advertises persistence/security technologies such as PostgreSQL, Hibernate, Spring Security and OAuth2. It was archived by its owner on February 24, 2026. citeturn28search0turn28view0

This proves that a Battleship server can sit inside a conventional Spring/WebFlux service, but virtually every persistence/account component is contrary to the target's anonymous/no-database objective. It is more useful as a reminder to resist framework-driven scope expansion than as the proposed design.

`Mano-08/server.battleship` is more directly aligned on paper: its README says Spring Boot handles REST/scheduling and a Java Socket.IO server handles realtime gameplay, with events such as `join`, `ready`, `dropTorpedo`, `gameOver`, replay request/accept and room-full notification. citeturn15view0 Yet the inspected repository's `src` tree exposes only `src/test/java/com/server/battleship/BattleshipApplicationTests.java`; no production `src/main` tree is visible. citeturn16view0turn26view0

That is a significant reference failure, not merely a documentation inconvenience. A protocol list cannot prove that the server validates placement, computes hit/sunk/victory itself, authenticates a player to a room, handles reconnects, suppresses duplicate commands or synchronizes concurrent events. In particular, an event named `gameOver` is safe only if the **server derives the winner from authoritative board state**; a server that simply relays a client's “I won” message is trivially cheat-able. The available repository does not let us verify which model is used. citeturn15view0turn26view0

## Rule and data-model comparison

The implementations differ on several rules that are frequently left implicit.

| Concern | emiliayoffie | NodeBattleship | LAN Games | Calimero | Implication |
|---|---|---|---|---|---|
| Board | Flat `BoardLayout` array with explicit UI square states | Flat 100-cell shot array + flat ship-index array | Ship cell lists plus fired/received shot records; view is derived | Private placement plus shared result state | Separate authoritative domain data from UI cell-state representation |
| Fleet | Vessel objects with length/orientation/position | Sizes `[5,4,3,3,2]` | Configured five-ship fleet | 5/4/3/3/2 | Fleet configuration should be one server-side constant/contract |
| Placement | Utility-driven; client/local | Random server placement | Explicit player commands | Private player placement | Browser multiplayer requires server validation regardless of frontend previews |
| Overlap | Placement helper exists | Forbidden | Forbidden | Forbidden | Uncontroversial invariant |
| Adjacency | Not sufficiently established by inspected tests | **Forbidden, including diagonals** | **Allowed by inspected placement validator** | **Forbidden** | Must be explicitly specified; implementations disagree |
| Setup lifecycle | Local UI-oriented | No manual setup; generated immediately | `setup` barrier → `firing` | Both players privately place before play | Barrier is best model |
| Turn after hit | Local computer-game behavior | **Shooter keeps turn** | Single current-player action model | Alternating shots | Must be explicit |
| Duplicate cell shot | Local model | Rejected through target shot array | Tested as a server action family; server is authority | Shared protocol | Still separate from duplicate **network command** handling |
| Sunk | Explicit UI state / ship helper | `hits >= size` | Shot result can be `sunk`, plus sunk-ship state | Shot resolution produces shared result | Server should derive sunk atomically with hit |
| Victory | Local game | No enemy ships left | Explicit game-over transition and winner | Sink full enemy fleet | Victory must be produced by same transaction as final shot |
| Hidden fleet | Cosmetic/local against AI | Enemy receives only sunk ships | Opponent `ships` removed from projected state | Placement stays private | Projection must be an architectural boundary, not CSS |

The underlying sources support these distinctions. NodeBattleship's `Player` maintains `shots`, `shipGrid` and ship hit counts; its placement rejects adjacency as well as overlap, and its game switches players only after a miss. citeturn25view1turn25view0 LAN Games explicitly defines `setup` and `firing`, describes `Shot.result` as hit/miss/sunk, strips enemy ship data, and validates overlap in the placement operation without an adjacency perimeter test. citeturn24view0 Calimero documents non-adjacent ships and alternating fire. citeturn15view2

For this application, I would specify the rules **before** defining DTOs:

> 10×10 board; fleet lengths 5, 4, 3, 3, 2; horizontal or vertical only; no overlap; decide explicitly whether orthogonal/diagonal touching is forbidden; both players place simultaneously; after both commit, one starting player is chosen; exactly one shot per turn regardless of hit; a coordinate may be fired on only once; hit/sunk/victory are server-derived.

The “one shot per turn regardless of hit” recommendation is not because NodeBattleship's variant is wrong; it is because unconditional alternation produces a simpler and less ambiguous state machine and is consistent with Calimero's documented model. citeturn25view0turn15view2

For authoritative storage, neither a richly encoded UI board nor a fully object-per-cell model is necessary. NodeBattleship demonstrates the efficiency of dense flat boards, while LAN Games demonstrates the readability of explicit ship coordinates and shot events. citeturn25view1turn24view0 A good Java compromise is:

`BoardState` owns a fixed-size `byte[100]` or equivalent compact occupancy representation; `ShipState` owns ship ID/length plus its five-or-fewer cell indexes and hit mask; `PlayerState` owns identity/placement/ready data; `GameState` owns phase, turn, winner, monotonically increasing version and timestamps.

The API should **not expose that representation directly**. It should project it into player-specific DTOs such as `OwnBoardView`, `OpponentBoardView`, `GameView` and typed shot results. That retains NodeBattleship's density without its magic-number protocol and keeps LAN Games' critical projection boundary. citeturn25view1turn24view0

A further improvement over LAN Games would be to avoid maintaining both `shotsFired` and the opponent's `shotsReceived` as independent authoritative collections. The inspected LAN state shape stores both. citeturn24view0 In a small application, one canonical `ShotRecord[]` at game level, with shooter/target/cell/result/sequence, removes a class of “updated one side but not the other” invariants. Player-facing board views can be derived from that log plus ship state.

The canonical domain state can therefore be very small:

`GameSession → phase + two PlayerStates + fleet/board truth + shot history + currentTurn + winner + version + activity timestamps + recentCommandIds`.

There is no need for ORM entities, repositories, foreign keys or serialization-oriented domain annotations because sessions disappear after fifteen inactive minutes.

## Realtime, lifecycle, identity, and concurrency

The realtime implementations reveal a useful spectrum.

| Reference | Transport | Reconnect model | Command authority | Hidden-state delivery | Main problem for this target |
|---|---|---|---|---|---|
| NodeBattleship | Socket.IO | None; disconnect aborts game | Server checks turn and executes shot | `getGameState` filters enemy ships | Socket connection is identity; reconnect impossible |
| LAN Games | Socket.IO | Supported; AFK handling and turn skip | Server game module validates actions | Per-player `getStateForPlayer` on emissions | Database/accounts/JWT and broader framework are unnecessary |
| Calimero | P2P/CRDT/gossip | Distributed architecture | Shot resolution crosses private/shared boundary | Ship placements remain private | Operational complexity far exceeds requirement |
| Mano | Java Socket.IO according to README | Not verifiable from available source | Not verifiable | Not verifiable | Production implementation is missing from current public tree |
| Proposed target | **REST commands + SSE state/events** | Opaque player token resumes stream/state | Pure server-authoritative commands | Projection computed for authenticated player | Lowest operational complexity while retaining near-realtime delivery |

NodeBattleship demonstrates why **socket ID must not equal player identity**. Connection establishment creates `users[socket.id]`; games store the two socket IDs; and disconnect aborts the game and deletes that identity. citeturn25view3turn25view0 A transient mobile-network switch, laptop sleep, browser refresh or Socket.IO reconnect is therefore indistinguishable from abandoning the match.

For anonymous sessions, issue each participant an **unguessable opaque player secret independent of the transport connection**. A game can have:

`gameId`: public opaque identifier used to locate the session.

`playerToken`: high-entropy secret identifying one of the two seats.

The token should never appear in public state, log messages, invitation links intended for both participants, WebSocket/SSE event payloads, or URLs that may enter server/browser history. It authenticates every command and every state stream. No username/password, account or database is necessary.

This preserves the important part of LAN Games—server-authenticated player identity—without adopting its account/JWT/SQLite machinery. LAN Games currently uses JWT authentication, hashed passwords and SQLite persistence as part of its larger LAN platform. citeturn18view0

### Why REST plus SSE is preferable here

Battleship is realtime in **observation**, not in input frequency. A player produces a small number of discrete commands: join, place/move ship, commit, uncommit, fire, perhaps resign. The server primarily needs to push state changes to the other browser immediately.

That makes **HTTP command endpoints + Server-Sent Events** a particularly good fit:

```text
POST /api/games
POST /api/games/{gameId}/join
POST /api/games/{gameId}/commands
GET  /api/games/{gameId}/view
GET  /api/games/{gameId}/events
```

All mutation can go through one typed command envelope:

```text
commandId
expectedVersion
type
payload
```

The SSE stream carries `stateChanged`, `opponentConnected`, `expired` and similar notifications, preferably with the resulting version. The client can then fetch or receive a fresh projection.

Socket.IO is clearly workable—both NodeBattleship and LAN Games demonstrate it—but it invites an event-per-use-case API unless carefully disciplined. NodeBattleship, for example, has separate transport events such as `shot`, `update`, `join`, `gameover`, `leave` and `chat`, while the Mano README enumerates a similarly ad hoc family of event names. citeturn25view3turn15view0 A single command contract keeps a React frontend, a future alternate frontend and a Spring backend from developing parallel undocumented protocols.

SSE also naturally reconnects over ordinary HTTP infrastructure and is lighter conceptually than Calimero's CRDT/P2P design. Calimero's approach is appropriate when each peer must retain genuinely private state and no central server should possess all truth; this target explicitly has a backend, so server authority is simpler. citeturn15view2

WebSocket remains a reasonable second choice if the hosting platform has substantially better WebSocket than SSE support. The important recommendation is not “SSE at all costs”; it is **one transport-neutral domain command contract, with realtime merely a notification/projection channel**.

### Duplicate commands need first-class treatment

NodeBattleship prevents firing at an already-shot square, but that solves a game invariant rather than network idempotency. citeturn25view0 A browser can send command `C`, lose its response, reconnect, and legitimately retry `C`. Without an idempotency key the backend cannot distinguish the retry from a second user action.

LAN Games' Battleship test file contains extensive action tests, but a text search of that Battleship-specific suite found no test named around “duplicate” command processing. citeturn23view2 That does not prove the broader framework lacks duplicate protection, but it is enough to say the Battleship rule module is not the reference to copy for this particular requirement.

The target should keep a **bounded recent-command cache per player**, for example the last 32 or 64 `(commandId → outcome/version)` entries. Repeating a known `commandId` returns the recorded outcome without applying the transition again. A command with a new ID but stale `expectedVersion` receives a conflict response containing or pointing to the latest projected version.

This deals with both retransmission and two-tabs-at-once behavior without a database.

### Concurrency should be serialized per game, not globally

An in-memory map alone is not enough. Two HTTP requests can simultaneously observe `version=12`; both could pass “my turn” unless mutations are serialized.

Use a `ConcurrentHashMap<GameId, GameSession>`, but give each session one small critical section around:

`authenticate → check TTL/version/idempotency → validate command → calculate transition → store state/version → store command outcome → update activity → publish notification`.

A plain per-session `synchronized` section or `ReentrantLock` is adequate because a two-player turn-based game has tiny mutation frequency. Avoid one global lock: unrelated games must not block each other.

NodeBattleship largely escapes this problem because its old Node.js implementation runs mutations through a single event loop; moving the same mental model into a multi-threaded Spring application without adding per-game serialization would create races. Its source therefore should not be translated mechanically into Java. citeturn25view3

### The fifteen-minute TTL belongs in the domain repository

Keep `lastActivityAt` in each session and inject a `Clock` so expiry is deterministic under tests. A single scheduled cleanup task can periodically scan the map and remove sessions that are inactive for fifteen minutes.

Define “activity” precisely. A sound policy for the intended UX is: **an authenticated command, explicit state fetch, or lightweight browser heartbeat counts; merely having stale server state in memory does not**. A visible game can heartbeat every minute or two, so a match does not expire while both browsers remain open. Once both disappear, it vanishes naturally.

Do not create one timer/thread per game. One scheduled scavenger plus timestamps scales much better on a small free-tier VM.

Also impose a configurable hard session ceiling. TTL controls normal cleanup, but a malicious caller could create thousands of never-played games faster than fifteen minutes elapse. At the limit, reject creation or preferentially evict the oldest untouched waiting-room sessions.

## Testing, security, maintenance, and license

**LAN Games is the clear testing leader among the inspected references.** Its repository reports 625 unit tests across 11 suites and 40 integration tests across six suites, and its Docker build is documented to run both suites before producing the image. citeturn18view0 The Battleship test alone is roughly 900 source lines and exercises initialization, placement, commit/uncommit, hidden information, firing, game over, valid-action calculation, timers and action descriptors. citeturn21view1turn23view0

Several tests are particularly worth emulating. Initialization asserts `status='playing'`, `phase='setup'` and no current player. Placement tests include horizontal/vertical success, bounds and overlap rejection. Commit tests verify that incomplete fleets cannot commit and an already committed player cannot commit twice. Hidden-state tests ensure opponent ships disappear. Firing tests reject shots during setup and malformed/out-of-bounds coordinates. Game-over tests verify that no further shot is accepted and both players have no valid actions. citeturn23view0turn23view4turn23view5

Its determinism technique is mixed. Many firing tests explicitly overwrite `currentPlayerIndex` so they do not depend on random first-player selection—an excellent practice. citeturn23view0 But there is also a statistical test that runs first-player selection up to 50 times and expects to observe both players. The probability of accidental failure is tiny, yet nonzero. citeturn23view0 For CI, “nearly impossible to flake” is still weaker than an injected deterministic RNG.

emiliayoffie's utility suite demonstrates the same broader lesson from the opposite direction: random computer placement is exercised directly, while the file itself acknowledges uncovered neighbour/sinking/randomization helpers. citeturn10view1 Randomness should be moved behind an interface such as `RandomSource`, with seeded/fake implementations in tests.

The proposed Java rule engine should therefore take `Clock` and `RandomGenerator`/starter-selection strategy as explicit dependencies. There should be **no `Thread.sleep`, real-time waiting, or probabilistic success criteria in rule tests**.

A strong minimum test matrix is:

| Test family | Cases that matter |
|---|---|
| Placement | Every board edge; horizontal/vertical; negative/out-of-range/noninteger DTO rejection; duplicate ship; move ship; overlap; orthogonal and diagonal adjacency according to chosen rule; commit with missing/extra/duplicate fleet |
| Phase machine | created → waiting → setup → firing → finished; both ready simultaneously; unready before barrier; placement after firing rejected; command after finish rejected |
| Fire | hit, miss, sunk, final sunk → victory; repeat coordinate; wrong player; wrong phase; malformed coordinate |
| Privacy | Own view includes own fleet; opponent view never includes unsunk coordinates; setup events/logs/errors contain no coordinates; completed-game reveal only if intentionally specified |
| Identity | Invalid token; player A token used for B command; guessed game ID without seat token; reconnect with same token; replacement connection does not change identity |
| Idempotency | Same command ID twice has one effect; retry after response loss gets same result; same ID with altered payload rejected |
| Optimistic versioning | Stale version conflict; simultaneous commands at same version produce exactly one mutation |
| TTL | Exactly-before and exactly-at expiry; heartbeat extends life; cleanup racing a command; expired token cannot resurrect deleted session |
| Realtime | Reconnect receives current version; lost event is recovered by state fetch; slow consumer cannot grow an unbounded queue |
| Contract | Backend DTOs conform to OpenAPI/schema; generated TS client compiles; unknown enum/command is rejected, not silently ignored |

**Security comparison.** NodeBattleship correctly puts turn enforcement on the server and filters enemy fleet state, but its authorization identity is the transient socket ID and its firing payload lacks a strong schema-validation boundary. Disconnect immediately terminates an unfinished game. citeturn25view3turn25view0 These are the most important things not to reproduce.

LAN Games is materially stronger: it documents JWT/bcrypt authentication, server-side action validation and a state-emission audit intended to ensure all player state travels through the hidden-information filter. citeturn18view0 Its main mismatch is product scope rather than engineering quality: account credentials, persistent tokens, SQLite and privileged spectators do not belong in the requested anonymous ephemeral product. Its README explicitly says spectators see otherwise-hidden Battleship state. citeturn18view0

Calimero offers the strongest conceptual secret separation because fleet placement is local/private rather than simply filtered from a central state. citeturn15view2 For a central authoritative server, however, **server possession of both fleets is not itself a vulnerability**. The relevant property is that no response or event can cross the projection boundary containing the opponent's private cells.

One API endpoint should therefore never serialize raw `GameState`. Every outbound player message should originate from:

`GameState → viewFor(seat) → DTO`

not:

`GameState → generic serializer → frontend hides things`.

This is the most important security pattern in the entire reference set, and LAN Games makes the failure explicit in its source comments. citeturn24view0

## Patterns to adopt and patterns to avoid

### Good patterns to adopt

**Make the game a state machine independent of HTTP/SSE/WebSocket.** LAN Games' Battleship module is a strong example of game logic behind a generic game interface rather than rule code embedded in socket callbacks. Its setup/firing distinction and valid-action calculation are especially useful. citeturn24view0turn23view0 The target should have something conceptually equivalent to:

`TransitionResult apply(GameState before, PlayerSeat actor, Command command)`

with transport code responsible only for authentication, locking, idempotency, DTO conversion and event publication.

**Model simultaneous setup as a barrier.** LAN Games' `currentPlayerIndex=null` during setup cleanly states that neither player “owns” setup; both act until both commit. citeturn24view0 This eliminates awkward placement-turn logic and maps naturally to the browser UX.

**Use an explicit hidden-state projection.** LAN Games strips the opponent's fleet and also audits event payloads for placement leaks; Calimero goes further by structurally separating private placement from shared state. citeturn24view0turn23view0turn15view2 The new backend should make `viewFor(player)` mandatory for every snapshot and realtime update.

**Keep boards compact internally.** NodeBattleship shows that Battleship needs only fixed-size flat arrays plus small ship records. citeturn25view1 Do not build a hundred mutable Spring/JPA `Cell` entities per participant.

**Validate at the authoritative boundary.** LAN Games validates identity, phase, integer coordinates, bounds, ship type, orientation, overlap and ready state before mutating placement. citeturn24view0 The browser should perform the same validation for UX, but client validation is advisory.

**Return valid actions or phase capabilities from the server.** LAN Games exposes valid actions/action descriptors and tests them for setup, waiting-for-opponent, firing, unknown player and finished states. citeturn23view0turn23view5 A lighter target can simply expose `allowedActions`, avoiding frontend duplication of phase rules.

**Test privacy as aggressively as game rules.** The LAN test that serializes a placement/removal event and verifies it contains no positional fields is an unusually good technique. citeturn23view0 Similar tests should scan every player-facing DTO/event in setup and play phases.

### Bad patterns to avoid

**Do not bind identity to the network connection.** NodeBattleship's socket-ID player identity makes refresh/reconnect equivalent to abandoning the game. citeturn25view3 Stable ephemeral player tokens should outlive individual SSE/WebSocket connections.

**Do not place authoritative game truth in React state.** emiliayoffie's model is appropriate for a single-player local game but would expose and permit modification of the opponent's fleet in multiplayer. citeturn8view0 React should own presentation and optimistic interaction state, never victory truth or enemy placement truth.

**Do not allow a client to declare hit, sunk, turn or winner.** The server has both boards and can compute every result. Mano's README-level `gameOver` event illustrates why protocol names are not sufficient evidence of authority when implementation source is unavailable. citeturn15view0turn26view0 Commands should say only what the player is allowed to choose: principally “fire at cell C.”

**Do not let transport events become the domain API.** NodeBattleship's many Socket.IO handlers are concise, but the API contract lives implicitly inside event callbacks. citeturn25view3 A versioned command/DTO contract is easier to replace on either side.

**Do not use random behavior directly in deterministic tests.** Both the local TypeScript project and LAN Games contain tests that exercise uncontrolled or statistical randomness. citeturn10view1turn23view0 Inject a random source and test exact outcomes.

**Do not infer “standard rules.”** NodeBattleship forbids adjacency and gives another turn after a hit; LAN Games' inspected placement logic permits touching; Calimero documents non-adjacent placement and alternating shots. citeturn25view1turn25view0turn24view0turn15view2 Write these decisions into the contract and tests.

**Do not import persistence because Spring makes it convenient.** NSAI_game-server's Spring/WebFlux ecosystem includes database/security machinery appropriate to a fuller account-based service, while LAN Games uses SQLite for save/resume. citeturn28search0turn18view0 Neither is necessary for a deliberately ephemeral fifteen-minute game.

**Do not create spectators that bypass hidden-state projection unless that is an explicit feature.** LAN Games intentionally permits spectators to see full hidden state. citeturn18view0 For this application, there should simply be two authorized seat projections.

## Recommended adaptation for this application

The best adaptation is **not** to choose one reference implementation. It is to combine four ideas: NodeBattleship's compact in-memory board, LAN Games' pure server-authoritative rule module and privacy projection, Calimero's strong conceptual private/public separation, and emiliayoffie's frontend-friendly typed cell vocabulary—while rejecting their mismatched infrastructure. citeturn25view1turn24view0turn15view2turn8view0

### Proposed backend shape

Use Spring Boot with no JPA and no database:

```text
api/
  GameController
  GameEventController
  dto/

application/
  GameService
  SessionRepository
  SessionExpiryService

domain/
  GameState
  PlayerState
  BoardState
  ShipState
  ShotRecord
  GamePhase
  Command
  TransitionEngine
  GameProjector

realtime/
  EventPublisher
```

`SessionRepository` is an in-memory `ConcurrentHashMap<GameId, GameSession>`.

`GameSession` wraps immutable/replaced `GameState`, two player secrets, a per-game lock, recent command outcomes, last activity time and current realtime subscribers.

`TransitionEngine` contains no Spring types and no JSON concerns.

`GameProjector` is the only component allowed to convert raw state into player-visible state.

That follows the strongest separation seen in LAN Games while eliminating its persistent framework layer. citeturn18view0turn24view0

### Proposed lifecycle

The complete state machine should be explicit:

```text
WAITING_FOR_OPPONENT
        │
        ▼
SETUP
  player A places ┐
  player B places ├─ concurrently
  both commit     ┘
        │
        ▼
PLAYING
  turn A ↔ turn B
        │
        ▼
FINISHED
```

`EXPIRED` does not need to remain in the map as a persistent state; the repository can delete the session and make future access return an expired/not-found result.

During `SETUP`, neither player is the current player. This directly adopts LAN Games' barrier pattern. citeturn24view0

### Proposed command contract

Keep one mutation endpoint and a discriminated command schema:

```text
PlaceShip
RemoveShip
CommitFleet
UncommitFleet
Fire
Resign
Heartbeat
```

Every command envelope carries:

```text
commandId: UUID
expectedVersion: long
type: enum
payload: command-specific body
```

The server response carries:

```text
accepted
version
view
errorCode?
```

Do **not** include `Hit`, `Miss`, `SinkShip`, `ChangeTurn`, or `DeclareWinner` as client commands. Those are transition outputs.

This is a cleaner form of LAN Games' action interface and avoids NodeBattleship's transport-defined event API. citeturn24view0turn25view3

### Proposed anonymous identity and reconnect

On game creation, return:

```text
gameId
playerToken
inviteCode or join URL
```

The joiner receives a different `playerToken`.

The public invitation identifies the game but must not embed the creator's seat token.

A browser refresh restores the anonymous seat with its secret and retrieves the latest projected `GameView`. Reconnecting a realtime stream is therefore routine and does not alter game state. This directly fixes NodeBattleship's socket-ID/disconnect failure. citeturn25view3

Because sessions are temporary and anonymous, avoid the account/JWT/password system used by LAN Games. citeturn18view0 A random opaque bearer secret scoped to exactly one game seat is enough.

### Proposed hidden-information contract

During setup and play, the opponent projection should contain only:

```text
ready
connectionStatus
shots that I fired at their board
sunk ship metadata that the rules intentionally reveal
```

It must not contain ship origins, untouched ship cells, complete raw board arrays, placement-validation intermediates or logs containing coordinates.

Own projection may contain complete own placements and incoming shots.

At `FINISHED`, decide explicitly whether both fleets are revealed. LAN Games does reveal them at game over. citeturn18view0turn23view5 That is a product choice, not a necessary Battleship rule.

### Proposed realtime contract

Prefer:

`POST commands` for mutations.

`GET events` via SSE for near-realtime notification.

`GET view` for authoritative resynchronization.

Every emitted event contains at least `gameVersion`. The browser treats a version gap as “fetch the current view,” not as an instruction to replay fragile client-side state mutations.

This design survives lost notifications and reconnects much better than making the browser reconstruct truth from a sequence of imperative Socket.IO messages.

It also allows the same backend contract to support a React frontend today, a different frontend later and a bundled static frontend in the JAR without changing game semantics.

### Optional one-JAR packaging without coupling frontend and backend

Maintain frontend and backend as separate build artifacts and communicate only through the public API.

For a standalone distribution profile, copy the already-built frontend static files into Spring Boot's static resources during packaging:

```text
browser → same Spring Boot JAR
        → /         static frontend
        → /api/...  backend contract
```

For independent deployment:

```text
static host / CDN → frontend
                  → HTTPS API/SSE → Spring backend
```

No frontend source should be imported into Java domain packages, and no frontend code should call backend implementation classes. The **same API contract** must work in both modes.

That achieves the user's apparently competing requirements—“one packaged JAR option” and “independently replaceable frontend/backend”—without maintaining two application designs.

### Resource behavior

A no-database Battleship game is naturally tiny. The dominant resource risks are not board state but **unbounded session creation, retained event subscribers and command-history growth**.

Therefore:

- session map entries expire after fifteen minutes of inactivity;
- one shared scheduler performs expiry rather than a timer per session;
- recent command IDs are bounded;
- shot history is inherently bounded by board size;
- event queues are bounded or state-based rather than unlimited histories;
- completed games use the same short TTL rather than remaining forever;
- game creation has a global configurable ceiling/rate limit.

NodeBattleship validates how small the fundamental game representation can be—two 100-cell arrays per player plus five ship records are enough for its model. citeturn25view1 There is no architectural justification for a database merely to hold a fifteen-minute game.

### Recommended rule-engine invariants

The server should continuously preserve these invariants:

`players.size <= 2`.

Each player has at most one ship of each configured type.

Every ship has exactly its configured number of contiguous cells.

Every cell is within bounds.

Ships never overlap.

If no-touch rules are chosen, no cell belonging to two ships is orthogonally or diagonally adjacent across distinct ships.

No shot coordinate occurs twice.

Only the current player can fire.

Every hit corresponds to a target ship cell.

A ship is sunk exactly when every one of its cells has been hit.

A winner exists exactly when all enemy ships are sunk or the opponent resigned.

`SETUP` has no current firing player.

`PLAYING` has exactly one current player.

`FINISHED` accepts no mutating gameplay command.

Every accepted mutation increments `version` exactly once.

Every projected view satisfies the hidden-information policy.

These invariants turn Battleship from a collection of event handlers into a compact, testable state machine.
