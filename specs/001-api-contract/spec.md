# Feature Specification: Anonymous Battleship API Contract

**Feature Branch**: `feature/001-api-contract`

**Created**: 2026-08-20

**Status**: Ready for Implementation

**Input**: User description: "Specify the first rewrite change from `docs/rewrite_context_doc/Planning/03-api/specify-input.md`, validating it against the wider rewrite research and design so one authoritative backend and one independently built frontend can share a safe, stable contract."

## Clarifications

### Session 2026-08-20

- Q: How many times should `snapshotRevision` advance for one accepted transition that advances `gameVersion`? → A: Exactly once per accepted transition.
- Q: How should `GET /actuator/health` represent a process that is alive but not ready, including during startup or shutdown draining? → A: Return `200` when ready and `503` when alive but not ready; include minimal non-sensitive liveness and readiness details in the body.
- Q: Which product should localize user-facing messages derived from API problems? → A: The API returns stable language-neutral identifiers and codes only; the frontend maps them to all localized message text.
- Q: Which rate-control policy should v1 publish for snapshot reads, presence calls, and SSE connections? → A: Use bounded adjustable controls whose thresholds and scopes are not v1 compatibility guarantees.
- Q: At what moment should the invitation page request the anti-forgery token required before it can send the guest's Join request? → A: After the guest chooses Join, obtain or refresh the CSRF token through metadata and then submit the Join request.
- Q: When a browser sends an invalid or unknown session cookie to public metadata, ruleset, or health endpoints, how must those endpoints respond? → A: Ignore the cookie and return the normal public response.
- Q: What should happen when we create the first saved API baseline? → A: Validate the candidate first, create the baseline without overwrite, then require it in the final check.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Create and Join a Private Game (Priority: P1)

As an anonymous host, I can compare the two published rulesets, create a private game, and share one canonical invitation. As an anonymous guest, I can inspect the invitation landing page and explicitly join without a link preview, scanner, competing browser, or public game identifier claiming my seat.

**Why this priority**: A safe two-player membership and invitation flow is the minimum usable product and establishes the identity boundary for every later action.

**Independent Test**: Exercise metadata, ruleset discovery, creation, invitation rotation, and join using two isolated browser identities. Verify that exactly two seats are allocated, only one concurrent redemption succeeds, and neither public output nor the invitation discloses a player capability.

**Acceptance Scenarios**:

1. **Given** a browser with no anonymous identity, **When** it reads metadata and creates a game with a valid display name and either published ruleset, **Then** it receives an owner-safe version-zero snapshot, a protected browser identity, and one canonical fragment-bearing invitation URL.
2. **Given** a guest opens that invitation, **When** the landing page is rendered, **Then** the fragment has already been removed from visible history and no seat has been claimed.
3. **Given** the guest explicitly submits the invitation and a valid display name, **When** redemption succeeds, **Then** the invitation is consumed atomically, the guest membership is added to that browser identity, the game idle deadline is refreshed, and the guest receives an authoritative guest-safe snapshot.
4. **Given** multiple valid redemption requests race, **When** they are processed, **Then** exactly one claims the guest seat and every other request receives the same non-enumerating invitation-unavailable outcome.
5. **Given** the owner rotates an unused invitation, **When** rotation succeeds, **Then** the prior secret is immediately unusable and the response contains the newly versioned owner snapshot plus one replacement URL and deadline.

---

### User Story 2 - Place Fleets and Play Authoritatively (Priority: P1)

As either player, I can place and edit my own fleet, commit readiness, take legal shots, and resign when appropriate while the server remains the only authority for identity, legality, turns, shot results, victory, and the information each seat may see.

**Why this priority**: The contract must carry the complete game journey without forcing either consumer to invent rules or duplicate a game engine.

**Independent Test**: For each ruleset, use only published ruleset data, snapshots, and commands to place two legal fleets, become ready, play through a terminal result, and prove that the client never needs hidden state or locally calculated outcomes.

**Acceptance Scenarios**:

1. **Given** only the owner seat exists, **When** the owner tries to place a ship or become ready, **Then** the waiting-phase command conflicts without advancing either revision; **when** the guest joins, **Then** both seats may begin independent placement.
2. **Given** a player in placement, **When** that player places, moves, rotates, or removes a ship, **Then** only the authoritative returned snapshot changes and the opponent receives no undisclosed placement.
3. **Given** an incomplete or illegal fleet, **When** `READY` is requested, **Then** it is rejected safely; **given** a complete legal fleet, **When** `READY` succeeds, **Then** readiness is irreversible.
4. **Given** both players are ready, **When** the second readiness transition succeeds, **Then** play begins and the starting seat selected at creation is revealed for the first time.
5. **Given** a player has firing authority, **When** `FIRE` succeeds, **Then** the returned result distinguishes miss, hit, sink, and any ruleset-created automatic water disclosure, advances the proper turn policy, and decides victory atomically when applicable.
6. **Given** a target was already fired upon, **When** it is targeted again, **Then** the request conflicts without consuming a turn, changing damage, or advancing either public revision.
7. **Given** simultaneous state-changing requests use the same current game version, **When** they race, **Then** at most one advances that version and all consumers can reconcile to the one authoritative result.

---

### User Story 3 - Resume and Recover Without Guessing (Priority: P2)

As a returning or temporarily disconnected member, I can reload, reconnect, retry an unresolved command, or recover from stale data using my protected browser identity and full player-safe snapshots. I am never asked to guess whether a move succeeded or to reconstruct the game from event history.

**Why this priority**: Mobile suspension, duplicate delivery, lost responses, and server restarts are normal failure modes; ambiguous recovery would create duplicate actions or incorrect local state.

**Independent Test**: Lose command responses, reorder or omit events, replace a stream, foreground a stale tab, extend presence without changing game state, and restart the service. Verify convergence or an honest unavailable outcome in every case.

**Acceptance Scenarios**:

1. **Given** an accepted command response is lost, **When** the identical command identity and normalized content are retried, **Then** the recorded player-safe result is returned before freshness is evaluated and the transition is not repeated.
2. **Given** a command identifier is reused with different content, **When** it is submitted, **Then** it conflicts; **given** a new command based on stale game state, **When** it is submitted, **Then** it receives a stale-precondition outcome and no automatic replay occurs.
3. **Given** a member misses, duplicates, or reorders realtime updates, **When** a current full snapshot is received, **Then** the client orders it by process epoch and snapshot revision and converges without replaying an already resolved command.
4. **Given** accepted visible presence extends the idle deadline without changing game state, **When** either member performs a conditional read or reconnects, **Then** the changed snapshot is observable and is not incorrectly treated as an unchanged game-version duplicate.
5. **Given** the process epoch changes, **When** a client compares metadata with cached game evidence, **Then** it stops comparing old revisions and reports restart loss or generic unavailability without claiming recovery.

---

### User Story 4 - Finish, Leave, and View Safe Results (Priority: P2)

As a member, I can abandon a pre-play game, resign during play, view the permitted terminal result and server-calculated statistics, and revoke only my retained result access when I leave.

**Why this priority**: Terminal transitions must preserve hidden information, produce one final outcome, and define what remains available during the short retention window.

**Independent Test**: Cover abandonment before and after guest join, normal victory, resignation with and without accepted shots, terminal statistics from both caller perspectives, terminal leave, and identical leave retry after membership revocation. Prove that every result-screen value comes from one authoritative terminal snapshot rather than a browser clock, fixed fleet constant, reconstructed event history, or board inference.

**Acceptance Scenarios**:

1. **Given** the game has not started, **When** either member leaves, **Then** the whole game becomes abandoned, invitation and gameplay authority end, neither placement is disclosed, and every membership that exists at abandonment retains only the safe read view for the terminal window.
2. **Given** play is active, **When** the separate leave operation is requested, **Then** it conflicts with guidance to resign; **when** `RESIGN` succeeds, **Then** the opponent wins and the member-only final disclosure becomes available.
3. **Given** a normal finish or resignation, **When** either retained member reads the result, **Then** one terminal snapshot provides both completed boards, the winner/loser and finish reason, match and phase durations, both seats' placement and turn timing, both seats' shot/hit/accuracy and decision timing, and both fleets' final condition counts; the caller can label those seat-keyed values as “your” and “opponent” without calculating a statistic.
4. **Given** a former member leaves a terminal result, **When** the operation succeeds or is identically retried, **Then** only that game membership and stream are revoked, the other member's result and the game version are unchanged, and the replayed outcome is `204`.

### User Story 5 - Implement and Evolve One Contract (Priority: P3)

As an independent backend or frontend contributor, I can consume one language-neutral contract and determine every request, response, event, problem, security rule, lifecycle boundary, and compatibility obligation without consulting the other product's source or making a new user-visible decision.

**Why this priority**: Feature 01 exists to prevent divergent transport models and later coordinated rewrites across both consumers.

**Independent Test**: Validate all artifacts and examples in isolation, smoke-consume the contract from two independent consumer perspectives, and classify representative additive and breaking changes against the published compatibility policy.

**Acceptance Scenarios**:

1. **Given** the contract bundle alone, **When** a backend contributor implements conformance, **Then** no public path, field, status, cookie, event, retry, privacy, or lifecycle policy must be invented.
2. **Given** the same bundle, **When** a frontend contributor models every named journey, **Then** no server state transition, hidden-state inference, or handwritten transport shape is required.
3. **Given** an optional response field is added, **When** compatibility is evaluated, **Then** it is treated as additive and old consumers tolerate it; **given** a closed discriminator, required field, security rule, or existing meaning changes, **Then** it is classified as breaking.

### Edge Cases

- A create response is lost before the client learns `gameId`; the v1 route surface cannot discover that orphan, so the client explains the uncertainty and requires explicit confirmation before another creation.
- A join response is lost after the one-time invitation is consumed. If the browser identity received the membership, an authenticated snapshot for the known `gameId` recovers it; if membership cannot be proven, v1 cannot recover that claimed seat.
- Invitation rotation and redemption race. Exactly one serialized outcome wins: either the old invitation is consumed by one guest or it is revoked and replaced; no second guest is allocated.
- A valid browser identity already owns one seat and attempts to redeem the other seat's invitation in the same game. The attempt fails without replacing or weakening the existing membership.
- The same browser identity participates in several games. Leaving or expiring one game does not revoke its memberships in the others.
- A display name is empty after trimming, exceeds its limit, contains control characters, or contains markup-like text. Invalid names are rejected; accepted names remain plain text and confer no authority.
- Both players send `READY` concurrently, or a final `FIRE` races with `RESIGN`. One serialized transition determines the next or terminal snapshot; no intermediate winner or extra turn is exposed.
- A command is retried after its bounded receipt is no longer guaranteed. It must fail safely under its stale game-state precondition rather than reapply against current state.
- A presence extension changes an idle deadline while `gameVersion` remains unchanged. `snapshotRevision`, snapshot ETag, and realtime ordering still advance consistently.
- A request arrives exactly at an idle, absolute, invitation, or terminal-retention deadline. At or after the deadline is expired/unavailable; an earlier qualifying action may extend only the idle deadline and never the absolute deadline.
- A normal or resigned game has zero shots or no timing samples. Counts remain zero and derived ratios or minimum/average/maximum values with no denominator are `null`, never fabricated.
- A player retains firing authority after a hit. The accepted `FIRE` ends one shot-decision sample and immediately begins another for that seat, while both samples remain inside one logical-turn interval.
- Play ends by resignation before the current player fires. The open logical turn ends at resignation, but the unfinished shot-decision interval produces no accepted decision sample.
- Terminal statistics are read from the owner and guest perspectives. The same seat-keyed values and outcome are returned to both authorized former members; only presentation labels such as “your” and “opponent” change locally.
- An SSE replay cursor is stale, outside retained history, or presented while reconnecting to a different game or process epoch. The cursor is treated only as a hint within the currently authorized game and process; the response never discloses cursor provenance and falls back to the current authorized full snapshot when no retained match exists.
- A newer stream for one seat replaces its older stream; a slow or superseded stream is closed without delaying commands or retaining unbounded output.
- A hidden opponent board differs internally while everything legally disclosed is the same. The caller-facing snapshots, events, command results, and problems remain equivalent except for non-sensitive request correlation values.
- Capacity, rate limiting, or shutdown draining rejects new work. Existing live games are not evicted to admit it and the problem reveals no game, invitation, membership, or secret state.

## Requirements *(mandatory)*

### Functional Requirements

#### Contract Product and Compatibility

- **FR-001**: The feature MUST publish one authoritative, language-neutral contract bundle under `contracts/` containing the canonical HTTP description, reusable machine-readable schemas, validated redacted examples, an API guide, a realtime protocol guide, a compatibility policy, a changelog, and independent validation instructions.
- **FR-002**: The contract bundle MUST NOT contain backend or frontend application code, controllers, framework classes, generated consumer source, runtime server configuration, persistence, frontend assets, or any implementation of game rules.
- **FR-003**: The v1 contract MUST define exactly these public application methods and paths, with no alternate v1 aliases: `GET /api/v1/meta`, `GET /api/v1/rulesets`, `POST /api/v1/games`, `POST /api/v1/games/{gameId}/join`, `GET /api/v1/games/{gameId}/snapshot`, `POST /api/v1/games/{gameId}/commands`, `GET /api/v1/games/{gameId}/events`, `POST /api/v1/games/{gameId}/invite/rotate`, `POST /api/v1/games/{gameId}/presence`, `POST /api/v1/games/{gameId}/leave`, and public `GET /actuator/health`. Automatic `OPTIONS` handling used only for CORS preflight is protocol support, not another application operation or alias.
- **FR-004**: The canonical description and companion artifacts MUST agree on every request and response body, path and query value, header, cookie, entity tag, event frame, status, media type, security rule, example, and problem code they publish.
- **FR-005**: The contract MUST use one RFC 9457-compatible problem representation and an OpenAPI 3.1-compatible canonical description. Exact specification patch and validation tooling are planning decisions and MUST NOT create a second contract source.
- **FR-006**: The initial semantic contract release MUST be identified as `1.0.0`; semantic contract version, `/api/v1` major, `gameVersion`, `snapshotRevision`, and per-process `serverEpoch` MUST be documented as distinct concepts.
- **FR-007**: Optional response fields MAY evolve additively when old consumers are required to tolerate them. Removal, incompatible type or meaning changes, newly required data, security weakening, changed status or event semantics, and additions to closed enums or discriminated unions MUST be classified as breaking unless the contract explicitly defines a safe fallback. A breaking wire change MUST use a new API major and a documented migration window; it MUST NOT silently change v1 in place.
- **FR-008**: Request objects MUST reject unknown fields, including client-supplied seat, role, ownership, turn, winner, score, or authorization claims. Response and event objects MUST tolerate documented unknown optional fields. Every release MUST record its compatibility classification; after `1.0.0`, compatibility MUST be compared with an immutable prior released baseline rather than with the release itself. Initial `1.0.0` publication MUST use a candidate gate that does not require the not-yet-created baseline, a baseline-creation command that accepts only that passing candidate and refuses to overwrite an existing release baseline, and a final gate that requires and validates the immutable baseline. The created `1.0.0` baseline MUST NOT count as compatibility evidence against itself.

#### Metadata, Rulesets, and Names

- **FR-009**: `GET /api/v1/meta` MUST create no game membership, MUST use `Cache-Control: no-store`, MUST establish or refresh the browser-readable CSRF cookie, and MUST return current `serverEpoch`, server time, contract/API identity, lifecycle bounds, and only non-sensitive service availability metadata.
- **FR-010**: `GET /api/v1/rulesets` MUST initially publish exactly `sea-battle-10-ship.v1` and `hasbro-classic-2002.v1`.
- **FR-011**: Each ruleset summary MUST provide stable machine identifiers and the complete data needed to present and validate its board dimensions and coordinate labels, fleet entries and counts, ship geometry and orientations, overlap and contact policy, shot allocation, repeat-target policy, turn-retention policy, starting-seat policy, victory rule, per-cell disclosure, automatic water disclosure, and terminal reveal policy without hard-coding those mechanics in a consumer.
- **FR-012**: `sea-battle-10-ship.v1` MUST describe a 10 by 10 board; lengths 4 once, 3 twice, 2 three times, and 1 four times; horizontal or vertical placement; no overlap or orthogonal/diagonal contact; one shot per decision; retained turn after hit or sink; and automatic water around a sunk ship as distinct from a fired shot. `hasbro-classic-2002.v1` MUST describe a 10 by 10 board; Carrier 5, Battleship 4, Destroyer 3, Submarine 3, and Patrol Boat 2; horizontal or vertical non-overlapping placement with contact allowed; one shot; and turn transfer after hit or miss.
- **FR-013**: Published rulesets MUST be immutable for an in-progress game. Any mechanical correction MUST receive a new identifier; broad labels such as `UKRAINIAN` or `MILTON_BRADLEY` MUST NOT identify a ruleset.
- **FR-014**: Creation and join MUST accept a presentation-only display name that, after Unicode NFC normalization and removal of leading and trailing Unicode whitespace, contains 1 to 32 Unicode code points, contains no Unicode control characters, and is treated as plain text. The accepted name is immutable for that membership and visible to both members; a vacant seat has no name, names need not be unique, and a display name MUST NOT authenticate or authorize a player. Display names MUST NOT be used as metric labels or written to operational logs; every output context MUST encode them as untrusted plain text.

#### Anonymous Browser Identity and Invitations

- **FR-015**: A public `gameId` MUST locate a game only. It MUST NOT authenticate, authorize, identify a seat, or reveal protected game state.
- **FR-016**: One uniformly random anonymous browser capability with at least 256 bits of entropy MUST identify a browser profile with zero or more per-game memberships, and the server MUST retain only a cryptographic digest of that capability. A valid capability MUST be reused when that identity creates or joins another game; one identity MUST NOT occupy both seats of the same game, and revoking one membership MUST NOT revoke its other memberships.
- **FR-017**: The browser capability MUST be carried only by a host-only session cookie named `__Host-battleship_session` with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, and no `Domain` attribute. Issuance and normal refresh MUST omit `Max-Age` and `Expires`; the sole exception is an invalid-cookie clearing response, which MUST expire that same cookie using deletion attributes. The capability MUST never appear in a URL, request or response schema field, browser-readable storage, event URL, log, metric, problem, invitation, or shareable representation. Public safe reads `GET /api/v1/meta`, `GET /api/v1/rulesets`, and `GET /actuator/health` MUST ignore any presented session cookie for both authority and validation, MUST NOT reject the request or issue, refresh, or clear the session cookie, and MUST return their normal public response subject to their non-session request-security and availability rules; metadata may independently issue or refresh only the CSRF cookie. Authenticated routes presented with no valid capability MUST return `401`, and lost membership is unrecoverable in v1. Public creation and join MUST reuse a valid presented capability, issue one on success when none is presented, and reject and clear a malformed or unknown presented capability so a later explicit attempt can begin without it; issuing or reusing a capability for another game MUST preserve its other memberships.
- **FR-018**: The separate CSRF value MUST use a host-only `BATTLESHIP-XSRF-TOKEN` cookie with `Secure`, `SameSite=Strict`, and `Path=/`, without `HttpOnly`, and MUST be echoed only in `X-Battleship-CSRF` for unsafe requests.
- **FR-019**: Creation MUST accept exactly one published ruleset identifier and the owner display name, establish or reuse the anonymous browser identity, create only the owner membership, select and conceal the random starting seat, start with `gameVersion: 0` and `snapshotRevision: 0`, and return the owner snapshot plus one canonical invitation URL and its deadline.
- **FR-020**: Creation MUST be one deliberate non-idempotent request. If its result is unknown, the client MUST NOT replay it automatically. A known `gameId` MAY be reconciled with an authenticated snapshot; if no `gameId` was received, v1 MUST state that the orphan cannot be discovered and will expire normally.
- **FR-021**: A canonical invitation MUST have the validated public frontend base, including any application subpath, and the shape `{publicBase}/join/{gameId}#invite={oneTimeSecret}`. The secret MUST be uniformly random with at least 128 bits of entropy, and the server MUST retain only its cryptographic digest. Only creation and successful rotation may return the URL. The owner capability MUST never be included, and the client MUST share the exact returned URL rather than reconstructing it.
- **FR-022**: Opening an invitation MUST have no server-side effect. The client contract MUST require reading the fragment locally, removing it from visible/history state before rendering shareable navigation, and holding it only in transient memory. Only after the guest explicitly chooses Join MAY the client call `GET /api/v1/meta` to obtain or refresh the CSRF cookie, after which it MUST echo that value in the protected explicit join POST. This metadata bootstrap MUST create no membership, consume no invitation, and send no invitation secret; the secret MUST be sent only in the subsequent explicit join body. Automatic redemption, query transport, token-only copy/paste, persistence, logs, analytics, and referrers are outside the authorized flow.
- **FR-023**: Successful join MUST atomically consume the invitation, establish or reuse the guest browser identity, reject an identity already controlling the owner seat, allocate exactly one guest membership, refresh the game's idle deadline subject to the absolute deadline, increment both public revisions, and return the guest snapshot.
- **FR-024**: Transport, media-type, body-size, CSRF, Origin, Fetch Metadata, session, source-rate, and capacity gates MUST be resolved without examining invitation validity. An invalid presented capability MUST return `401` with `invalid-session`, clear the cookie, and consume no invitation; a security-gate rejection MUST follow FR-027; the source-wide invitation limiter MUST return `429` with `rate-limit-exceeded` before game or invitation lookup; and capacity rejection MUST return `503` with `service-unavailable`. Only after those gates admit a syntactically valid redemption request, every unsuccessful redemption—including missing game, wrong, expired, revoked or consumed secret, occupied seat, same-identity second-seat claim, or losing a race—MUST return the same `409` invitation-unavailable problem with equivalent public status, code, body shape, and headers.
- **FR-025**: After an unknown join result, the client MUST first request the authenticated snapshot for the known `gameId`. If membership exists, that snapshot completes recovery. The invitation MUST never create another membership; if the response and membership credential were both lost, v1 MUST make no recovery promise for that seat.
- **FR-026**: The owner MAY rotate an unused invitation only while the guest seat is vacant. Success MUST revoke the old invitation atomically, advance both revisions once, and return the current owner snapshot plus one new canonical URL and invitation deadline. A lost URL or unknown rotation result MUST require reconciliation followed by an explicit replacement action, never blind replay.
- **FR-027**: Every credentialed cross-origin API response, including authenticated safe reads and SSE, MUST allow only the exact configured frontend Origin, allow credentials, use no wildcard origin, and vary by Origin. Every unsafe operation additionally MUST require the CSRF header, an exact configured frontend Origin, compatible Fetch Metadata, and the contract's content constraints. A missing or mismatched CSRF value, disallowed Origin, browser request identified as cross-site, or incompatible mode or destination MUST return `403` with the stable `request-security-rejected` code without resource-state disclosure; an absent Fetch Metadata header is permitted only for a non-browser client that still passes the same CSRF and exact-Origin checks. Preflight behavior MUST enumerate only the allowed origin, methods, and headers and set credential allowance. Cross-origin SSE opens MUST validate the exact frontend Origin and membership before allocating or replacing a stream; safe reads and SSE MUST NOT require the CSRF header but remain subject to the Origin and credentialed-CORS rules.

#### Authoritative Snapshots and Privacy

- **FR-028**: A full player-safe snapshot MUST be the authoritative representation returned by successful creation, join, snapshot reads, accepted game commands, successful rotation, pre-play abandonment, terminal reads, and realtime snapshot events. Every game-specific authenticated or secret-bearing response—including creation, join, snapshots, commands, rotation, presence, leave results, problems, and SSE—MUST use `Cache-Control: no-store`; a `304` snapshot response MUST repeat the same cache policy.
- **FR-029**: Every snapshot MUST include contract/API major, `serverEpoch`, an observation time fixed for that `snapshotRevision`, `gameId`, `gameVersion`, `snapshotRevision`, a game-state tag, selected ruleset summary, phase, caller-derived seat and display names, readiness, `allowedGameCommands`, `allowedOperations`, applicable turn and terminal outcome, distinct lifecycle deadlines, the caller's complete board, and only opponent information the ruleset and phase permit. A snapshot for a normal victory or resignation MUST additionally contain the `terminalStatistics` projection defined by FR-048 through FR-051. Re-reading an unchanged revision MUST NOT generate a new observation time that invalidates conditional-read semantics.
- **FR-030**: Snapshot deadlines MUST distinguish current idle deadline, absolute deadline, invitation deadline when the caller may manage it, effective active-game deadline, and terminal `readableUntil` when applicable. Consumers MUST NOT infer expiry solely from an old local countdown after a foreground or epoch change.
- **FR-031**: Own-fleet projections MUST give each ship a stable opaque `shipId`, stable ship-type identity, occupied coordinates, orientation where applicable, and known damage state so same-length ships can be addressed unambiguously. Board cells MUST distinguish unknown, known water, own ship, miss, hit, sunk, and automatically revealed water; one overloaded shot flag is prohibited.
- **FR-032**: `allowedGameCommands` MUST cover only the game command union, while `allowedOperations` MUST separately state endpoint actions such as rotate invitation, presence, pre-play leave, terminal leave, snapshot refresh, and stream use. Consumers MUST NOT derive either set from phase or seat assumptions.
- **FR-033**: Before normal finish or resignation, no snapshot, response, event, or problem may expose raw opponent placement, concealed starting seat, internal command history beyond the revision timing and count explicitly permitted by FR-038, invitation or capability material, subscriber/lock state, or abuse-control state. Two internal games differing only in undisclosed opponent placement MUST produce equivalent caller-facing data.
- **FR-034**: Normal finish or resignation MUST disclose both completed boards and terminal statistics only to the two retained former memberships. Pre-play abandonment MUST disclose neither placement nor fleet-derived statistics. No public, invitation-based, or non-member terminal disclosure is permitted.

#### Revision, Conditional Request, and Command Semantics

- **FR-035**: Each game MUST have monotonic `gameVersion` for game-state concurrency and monotonic `snapshotRevision` for player-visible representation ordering. Any accepted transition that advances `gameVersion` MUST advance `snapshotRevision` exactly once; an accepted presence that changes a deadline MUST advance only `snapshotRevision`.
- **FR-036**: Snapshot HTTP ETags MUST be strong, caller-specific validators for the complete authorized representation and therefore differ across seats when their representations differ. They MUST bind to process epoch, game, caller projection, and snapshot revision. Snapshot `If-None-Match` may return `304` only when that caller's complete representation is unchanged.
- **FR-037**: The snapshot's separate game-state tag MUST use entity-tag syntax and be bound to the current game and `gameVersion`, not lifecycle-only snapshot changes. Commands and leave MUST send that value in `If-Match` plus the identical numeric `expectedVersion`; presence-only changes MUST NOT make an otherwise current game-state precondition stale.
- **FR-038**: A newly created game MUST start both revisions at zero. Guest join, invitation rotation, pre-play abandonment, and every accepted game command MUST advance both `gameVersion` and `snapshotRevision` exactly once. During concurrent private placement, every accepted edit MUST publish the resulting higher safe snapshot to both members so either can obtain the current precondition; the non-acting member may observe revision timing and count but MUST receive no command type, ship identity, coordinate, orientation, or other placement fact. Reads, failures, repeated targets, non-extending presence, heartbeats, reconnects, and terminal membership revocation MUST advance neither revision.
- **FR-039**: The v1 game command union MUST contain only `PLACE_SHIP`, `MOVE_SHIP`, `ROTATE_SHIP`, `REMOVE_SHIP`, `READY`, `FIRE`, and `RESIGN`, each with complete command-specific schemas, coordinate conventions, field bounds, and phase/ruleset validation. `FIRE_SALVO` and client-supplied actor or outcome data are excluded.
- **FR-040**: Every game command and leave request MUST use a client-generated command identifier whose uniqueness scope is `(game, membership, commandId)`, the current `expectedVersion`, and matching game-state `If-Match`. Missing preconditions MUST return `428`; header/body disagreement or invalid values MUST return a validation problem; a new stale precondition MUST return `412` and direct snapshot reconciliation.
- **FR-041**: Duplicate processing MUST occur before freshness and domain validation. The same retained identifier with the same normalized semantic content MUST return the recorded player-safe result without another transition; reuse with different normalized content MUST return `409`. At minimum, each membership's latest accepted game-command receipt MUST remain available until that membership's next game command is accepted or the game is removed; earlier game-command receipts are not promised. Separately, up to two leave receipts per seat MUST remain until game removal so both an earlier pre-play abandonment and a later terminal revocation can be retried. After browser-identity authentication, an identical leave receipt MUST be looked up before ordinary current-membership and version checks, including after terminal revocation. A leave receipt authorizes only replay of its recorded safe snapshot or `204`, restores no membership, and conflicts on changed normalized content. No receipt is promised across process restart.
- **FR-042**: Requests that change state for one game MUST have one authoritative serial order. If requests race from the same version, at most one may advance that version. Commands for different games MUST remain independent from this ordering guarantee.
- **FR-043**: A repeated fire target MUST return a stable `409` conflict, consume no turn, change no damage or timing statistic, and advance neither revision.

#### Game and Terminal Behavior

- **FR-044**: Before guest join, the game MUST remain waiting and MUST reject placement and `READY` without advancing either revision. Guest join MUST begin placement for both seats. During placement and until a seat becomes ready, only that seat may place, move, rotate, or remove its ships. `READY` MUST require a complete legal ruleset fleet and be irreversible. The starting seat MUST be selected at creation, concealed throughout waiting and placement, and revealed only in the first playing snapshot after both seats are ready.
- **FR-045**: The server-defined outcome of `FIRE` MUST atomically validate membership, phase, turn, and target; calculate miss, hit, sink, ruleset-specific automatic disclosure and turn retention; update statistics; and produce exactly one winner when the victory condition is met. A terminal outcome MUST be a closed server-defined discriminator: normal fleet destruction identifies `winnerSeat`, `loserSeat`, and `ALL_SHIPS_DESTROYED`, while resignation identifies those seats and `RESIGNATION`; pre-play abandonment identifies `ABANDONED` and has no winner or loser. Consumers submit intent and MUST NOT calculate these authoritative results or infer the finish reason from final boards.
- **FR-046**: Pre-play `LEAVE` MUST use the versioned leave envelope, abandon the whole game, revoke the invitation and gameplay authority, advance both revisions once, and retain a safe read-only abandoned snapshot for every membership that exists at abandonment without placement disclosure. During play it MUST return a `409` resign-required problem. After any terminal result it MUST revoke only the caller's game membership, close that stream, return or identically replay `204`, and change neither revision nor the other member's access.
- **FR-047**: `RESIGN` MUST be irreversible, be available only during play, award the game to the other seat, and provide the same member-only final-board disclosure as normal victory.
- **FR-048**: Every normal-victory or resignation snapshot MUST contain exactly one server-calculated `terminalStatistics` object and MUST omit that object from waiting, placement, playing, expired, and pre-play-abandoned snapshots. `terminalStatistics` MUST contain a `match` section and a `bySeat` section with exactly the stable `owner` and `guest` entries, independent of the caller. `match` MUST contain `totalDurationMs`, `placementPhaseDurationMs`, and `gameplayDurationMs`. Each seat entry MUST contain `placementDurationMs`; `logicalTurns`; `shots`; `hits`; `accuracy`; `shotDecisions`; and `fleetCondition`. `logicalTurns` and `shotDecisions` MUST each contain `sampleCount`, `totalDurationMs`, `averageDurationMs`, `fastestDurationMs`, and `slowestDurationMs`. `accuracy` MUST contain `numerator`, `denominator`, and a server-calculated `ratio`; its numerator MUST equal `hits` and its denominator MUST equal `shots`. `fleetCondition` MUST contain `totalShips`, `untouchedShips`, `damagedShips`, and `destroyedShips`.
- **FR-049**: All terminal-statistics durations MUST be non-negative integer milliseconds measured by the server's authoritative elapsed-time source; browser clocks, event arrival times, and client reconstruction MUST NOT contribute. Match timing MUST run from successful guest join to terminal transition; placement phase from join to both-ready; each seat's placement from join to that seat's accepted `READY`; and gameplay from both-ready to terminal transition. A logical-turn sample MUST begin when a seat first gains firing authority, including the initial playing transition and every later transfer, and MUST end when authority transfers or play becomes terminal. A shot-decision sample MUST begin at that same grant of firing authority, end only when that seat's `FIRE` is accepted, and restart immediately after acceptance only when the same seat retains firing authority. A terminal transition without an accepted `FIRE` MUST close the logical-turn sample but MUST discard the open shot-decision interval. Rejected, stale, repeated, invalid, or duplicate commands and all presence/lifecycle operations MUST affect no statistics sample.
- **FR-050**: `match.totalDurationMs` MUST equal `match.placementPhaseDurationMs + match.gameplayDurationMs`, and `match.placementPhaseDurationMs` MUST equal the greater of the two seat placement durations. For each non-empty duration aggregate, `sampleCount` MUST be positive; `totalDurationMs` MUST equal the sum of its accepted samples; average, fastest, and slowest MUST be non-null; fastest MUST be no greater than average and average no greater than slowest; and the average MUST be rounded to the nearest whole millisecond using half-up rounding. For an empty aggregate, `sampleCount` and `totalDurationMs` MUST be zero and average, fastest, and slowest MUST be `null`. `shots` and `hits` MUST be non-negative integers, `hits` MUST NOT exceed `shots`, and `shotDecisions.sampleCount` MUST equal `shots`. `accuracy.ratio` MUST be `null` exactly when `shots` is zero and otherwise MUST be the contract-encoded server result of `hits / shots`; the contract artifacts MUST fix its precision and rounding. An accepted fire that strikes any previously unhit ship cell, including the final cell that sinks a ship, MUST add one shot and one hit. A miss adds one shot only. Automatically revealed water adds neither, and rejected or duplicate fire adds neither. `untouchedShips`, `damagedShips`, and `destroyedShips` MUST be mutually exclusive ship counts whose sum equals `totalShips` and the selected ruleset's fleet count; a damaged ship has at least one hit but is not sunk. Across both seat entries, logical-turn total durations MUST partition `gameplayDurationMs` without overlap.
- **FR-051**: The owner and guest projections of the same terminal revision MUST carry identical `terminalStatistics.match` and `terminalStatistics.bySeat` values. A consumer MUST treat `terminalStatistics.bySeat` as authoritative seat-labelled facts and map the snapshot's caller seat to presentation labels such as “your” and “opponent”; it MUST NOT reorder facts by winner, recompute accuracy or aggregates, derive fleet condition from boards, or use a fixed ruleset fleet constant. The result screen's turn count and “turn timing” values MUST consume `logicalTurns.sampleCount` and the corresponding `logicalTurns` duration aggregate; `shotDecisions` is a separate accepted-fire timing aggregate and MUST NOT be substituted for logical-turn timing. Result title and explanatory copy MAY be localized and phrased by the frontend only from the caller seat, display names, and authoritative terminal outcome; they MUST NOT infer the winner or finish reason from boards. Formatting milliseconds as localized clock text and formatting the supplied accuracy ratio as a localized percentage are presentation decisions and MUST NOT change the underlying values. Rich pre-terminal statistics are not part of v1. The mockup's generic pre-terminal `Ships x/total` and `Cells x/100` indicators have no approved API semantics in v1 and MUST NOT be inferred from hidden or player-safe boards.

#### Realtime Recovery and Lifecycle

- **FR-052**: The authenticated realtime wire shape MUST be one `snapshot` event whose SSE `id` is decimal `snapshotRevision` and whose `data` is the full player-safe snapshot JSON; transport framing MUST NOT be duplicated as a second nested event envelope. Every connection MUST atomically register the seat and send the current full snapshot before relying on later delivery.
- **FR-053**: One active stream per game membership is allowed; a newer stream replaces the older one. The initial policy MUST document heartbeat comments every 15 seconds and a 20-minute maximum stream lifetime. Replay and outbound buffering MUST be bounded, and a slow or superseded client MUST be disconnected rather than accumulating work. After an SSE response is committed, replacement, overflow, lifetime, or transport failure MUST close the stream without attempting an HTTP Problem Details body; the client then reconnects or retrieves a snapshot under FR-054.
- **FR-054**: `Last-Event-ID` MAY recover retained contiguous caller-safe snapshots, but complete replay MUST remain optional. Its decimal value MUST be treated only as a replay hint scoped to the requested authorized game and current process; it MUST NOT be trusted to identify or disclose the cursor's originating game or epoch. When no retained caller-safe snapshot matches in that scope, the server MUST send the current full snapshot. Clients MUST order state by `(serverEpoch, snapshotRevision)`, reject rollback, and use full conditional snapshots as the correctness fallback for gaps, foregrounding, stream failure, or degraded polling.
- **FR-055**: While the preceding game-command or leave outcome is unknown, the client MUST NOT issue any different game command or leave request for that same game and membership. It may retry only the same retained identity or reconcile through a newer authoritative snapshot; creation and secret-bearing rotation follow their explicit non-replay recovery rules.
- **FR-056**: Creation MUST establish the initial 15-minute idle deadline. Successful guest join, an accepted game command that leaves the game active, or eligible visible-tab presence accepted as an extension MUST refresh idle lifetime, capped by the two-hour absolute deadline. An accepted command that ends the game MUST establish terminal retention instead of refreshing an obsolete idle deadline. Reads, snapshot polling, invitation rotation, stream activity, reconnects, heartbeats, failed or duplicate operations, invalid invitations, and rejected or non-extending presence MUST NOT refresh idle lifetime.
- **FR-057**: A visible authenticated non-terminal member MAY submit presence, but the server MUST permit at most one deadline extension per membership in any five-minute interval. An eligible call that actually extends the deadline MUST return `extended: true`, current server time and deadlines, advance `snapshotRevision` once without changing `gameVersion`, and make the updated snapshot available to both member streams. An earlier well-formed call MUST return `extended: false` with current deadlines and advance neither revision; abusive traffic MUST return `429`.
- **FR-058**: Active games MUST expire at 15 minutes of non-qualifying activity and no later than two hours after creation. Invitations MUST expire 15 minutes after issuance or at game expiry, whichever is earlier. Finished and abandoned views MUST remain member-readable until five minutes after terminal transition or the absolute deadline, whichever is earlier. Every access MUST linearize its deadline decision before receipt lookup, command validation, or activity refresh: an operation that wins that ordering before the deadline may proceed, while a request at or after the deadline MUST observe expiry. Cleanup MUST not remove a game whose earlier qualifying operation won that ordering, and no later request may resurrect an expired game.
- **FR-059**: A current-process expiry that remains provable MUST return `410` with the current epoch. A game missing after cleanup or process restart MUST return a generic `404`; a new process MUST publish a new `serverEpoch` and MUST NOT imply that any prior game, receipt, stream, or rate-limit state survived.
- **FR-060**: The initial public rate policy MUST document no more than five creations per minute per bounded source key, twenty invitation attempts per minute per bounded source key, and sixty game commands per minute per capability as fixed public limits. Snapshot reads, presence calls, and stream establishment MUST remain subject to bounded adjustable admission controls that may return `429` with bounded machine-readable retry fields, but their exact thresholds and scopes MUST NOT be v1 compatibility guarantees. Rate limiting MUST not reveal resource, invitation, or membership existence.
- **FR-061**: Capacity exhaustion and shutdown draining MUST reject new work with `503` and bounded retry guidance without evicting a live game. Rate limits MUST use `429`. Heartbeat, replay, queue, request body, game, stream, and attacker-keyed resources MUST be bounded without exposing their internal structures as compatibility guarantees.

#### Problems and Health

- **FR-062**: Every application HTTP failure that occurs before its response or SSE stream is committed MUST use the one RFC 9457-compatible schema with stable machine-readable `type`, HTTP `status`, stable application `code`, opaque bounded `correlationId`, current `serverEpoch` when it helps recovery, and bounded machine-readable recovery or retry fields only when meaningful. Validation violations and corrective guidance MUST use stable identifiers or structured values rather than prose. The server-side problem representation MUST remain natural-language-neutral and MUST NOT provide localized or user-facing `title`, `detail`, or message text; the frontend exclusively maps the stable problem code and structured fields to English and Ukrainian copy. Post-commit SSE closure follows FR-053 and cannot be replaced by an HTTP problem body. Problems MUST contain no stack trace, exception text, secret, cookie, invitation fragment, board, raw command body, internal state, or existence oracle.
- **FR-063**: The contract MUST distinguish malformed syntax (`400`), invalid size (`413`), unsupported media type (`415`), invalid well-formed values (`422`), missing/invalid authentication (`401`), request-security rejection or proven-member role denial (`403`), generic unavailable or unprovable membership (`404`), domain/workflow or identifier-reuse conflict (`409`), membership-proven in-process expiry (`410`), stale precondition (`412`), missing precondition (`428`), rate limit (`429`), safe unexpected failure (`500`), and capacity/draining (`503`). FR-024's uniform invitation-unavailable `409` overrides ordinary missing-game, membership, and expiry classification for every syntactically valid failed join redemption. A member action incompatible with current phase, turn, target, or lifecycle is a `409`, not a client-chosen authorization fact.
- **FR-064**: Public `GET /actuator/health` MUST define one minimal project-owned body that reports liveness and readiness separately without importing framework component schemas. It MUST return `200` when the process is live and ready and `503` when the process is alive but not ready, including during startup or shutdown draining. The body MUST include bounded non-sensitive state details and a safe readiness reason when readiness is false. It MUST expose no configuration, active-game or capacity counts, metrics, secrets, player data, or implementation internals, and full game capacity alone MUST NOT report the process as unhealthy or unready.

#### Client Continuity Boundaries

- **FR-065**: The contract guide MUST limit durable browser storage to public game locators, non-secret epoch/revision recovery metadata, user-authored drafts, and presentation preferences. Invitation secrets and authenticated snapshots MUST never be placed in durable storage, and gameplay commands MUST never be queued for offline or background replay. The HttpOnly browser capability is the only credential used to resume a known game after reload.

### Scope Boundaries

- This feature owns the published v1 HTTP, schema, event, example, error, security, and compatibility boundary only.
- `/api/v2/game` compatibility is intentionally not retained.
- Accounts, registration, recovery identities, spectators, chat, matchmaking, bots, rankings, payments, analytics, advertisements, social sharing, durable history, offline gameplay or command queues, databases, brokers, multiple backend replicas, horizontal scaling, and recovery after process loss are out of scope.
- Durable SSE replay, durable idempotency, exactly-once processing across a process crash, and a durable distinction between expiry and loss after restart are not promised.
- Concrete locks, maps, subscriber implementations, replay-ring sizes, command-receipt structures, generation tools, language bindings, and hosting/deployment mechanisms belong to later planning or implementation and are not public contract policy.

### Key Entities

- **Anonymous Browser Identity**: An opaque protected browser-session capability with zero or more per-game memberships; it is not an account, seat identifier, or game locator.
- **Game Membership**: Server-derived authorization connecting one anonymous browser identity to exactly one owner or guest seat in one game, including retained terminal read authority.
- **Game**: One ephemeral two-seat match with a public locator, selected immutable ruleset, phases, revisions, deadlines, memberships, concealed starting-seat choice, and terminal outcome.
- **Ruleset Summary**: Immutable machine-readable board, fleet, placement, firing, turn, disclosure, and victory policy identified by a stable versioned ID.
- **Invitation**: A one-time guest-seat grant represented by a canonical frontend URL with a fragment secret, expiry, and unused/consumed/revoked state; it is not a player capability.
- **Game Snapshot**: Complete authoritative representation projected for one membership, including both revisions, allowed actions, deadlines, own board, and only legally disclosed opponent knowledge.
- **Game-State Tag**: Entity-tag-form token bound to a game and `gameVersion`, used only for state-changing preconditions.
- **Snapshot Validator**: Caller-specific strong entity tag for the complete snapshot representation and `snapshotRevision`, used for conditional reads.
- **Game Command**: One server-authorized placement, readiness, fire, or resignation intent with membership-scoped identity and game-state precondition.
- **Leave Request**: Separately versioned membership/lifecycle intent that abandons before play, redirects to resignation during play, or revokes only terminal read membership.
- **Command Receipt**: Bounded player-safe record used to resolve an identical uncertain retry without repeating a transition.
- **Problem Detail**: Stable, safe, machine-actionable failure representation with correlation and optional recovery guidance.
- **Realtime Snapshot Event**: SSE framing around one full player-safe snapshot, ordered by process epoch and snapshot revision.
- **Terminal Statistics**: One server-calculated normal-victory or resignation projection containing match-wide durations and stable owner/guest seat statistics for placement, logical turns, shots, hits, accuracy, accepted shot decisions, and mutually exclusive fleet-condition counts. Consumers relabel its seat entries for presentation but do not calculate its facts.

## Assumptions

- The project constitution and this active feature specification outrank historical implementation and generic recommendation files when they conflict.
- The frontend and API use the exact same hostname in v1; ports may differ in local operation. Split hosting therefore requires a same-host public routing arrangement rather than a parent-domain credential cookie.
- One anonymous browser profile is one identity across its normal tabs and may join multiple games, but two players in one profile for the same game are outside v1; a second profile, private context, or device is required.
- The browser may persist the current public `gameId`, non-secret presentation preferences, and other non-authoritative continuation hints. The capability remains only in its HttpOnly cookie; invitation secrets and authenticated snapshots are not placed in durable browser storage, and reload recovers from the server.
- The backend is one bounded in-memory process. Restart, deployment, or process loss destroys all games and recovery records; preserving them would require a different architecture and feature scope.
- Full current snapshots are mandatory recovery truth. Replaying intermediate realtime snapshots is an optional optimization and never a correctness dependency.
- The separate `snapshotRevision` is deliberate: lifecycle deadlines can change without a game-state transition, so `gameVersion` alone cannot safely serve as the complete snapshot validator or realtime recovery cursor.
- The HTML mockup defines UX direction and the statistics that the result surface must be able to render, but its hard-coded demonstration numbers are not normative API fixtures. Contract examples must satisfy the arithmetic invariants in this specification even when a mockup placeholder does not.
- Initial rate, heartbeat, and stream-lifetime values are documented operational defaults. Changes require evidence and changelog review but are not presented as universal capacity guarantees.
- All statistics durations use integer milliseconds; presentation may localize those values into clocks or decimal seconds without changing them. Exact timestamp encoding, accuracy-ratio precision, coordinate base, entity-tag syntax, and problem-code catalog will be fixed during planning inside the contract artifacts without changing the behavior stated here.
