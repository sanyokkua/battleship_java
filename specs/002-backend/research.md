## Decisions

| D1 | How do wire types reach the backend? | **Generated** from `contracts/openapi.yaml` — `openapi-generator-maven-plugin`, models only, into `app/target/generated-sources/openapi`, package `ua.kostenko.battleship.app.web.dto`. Configuration is D28 | Reverses the earlier "hand-written records; no codegen". It was always this feature's call: `specs/001-api-contract/tasks.md:117` records *"Java code generation from the contract is not part of this gate; feature 002 proves it."* Generation is what **retires** wire drift instead of mitigating it — a contract change regenerates the DTOs and breaks compilation of the assembler that fills them. The three things that made codegen look hostile are handled, not avoided: five lines of 3.1-only syntax are normalized in the contract (`const` → single-value `enum`, `examples: [x]` → `example: x` — wire-identical, `001-api-contract` R24-additive, and `enum` is already what `SimpleCommand` uses); the `Command` discriminator is left exactly as it is (D30); and the `text/event-stream` body is not a generated type at all, because SSE carries the same `GameSnapshot` (R17, D11). The one-element `allOf` description wrappers and the plugin's behaviour on JDK 25 are unverified until the build exists, which is why this is Task 1 with an abort condition (plan.md § *Forecast*) | Hand-written records — a second hand-maintained copy of 39 component schemas with nothing mechanically checking it against the contract; kept only as the named fallback if Task 1 fails. Generating API interfaces as well (D28). Normalizing the 13 `allOf` wrappers too (offered and declined; the spike must confirm they inline). A `json-schema-validator` conformance test (extra dependency — proof area 10 asserts the wire boundary instead) |
| D2 | What decides the first turn? | The ready order: the player who declared `READY` first fires first, an exact tie broken from `RandomSource` (R11) | Overrides the seed document's "secure unbiased random choice at game creation … readiness timing cannot bias the choice". Accepted consequence: declaring ready first *is* an advantage, so the rule rewards placing quickly; that is preferred to a coin flip because it is observable and explicable to a player | Random at game creation (the seed document's rule, and the contract's before its amendment) |
| D3 | How is request security built? | Spring Security, one minimal `SecurityFilterChain`, plus three own filters | `CookieCsrfTokenRepository` emits `XSRF-TOKEN` and reads `X-XSRF-TOKEN` exactly as the contract specifies; hand-rolling CSRF is a classic defect | — |

| D14 | Randomness | `RandomSource` (arrangement, R11 tie-break, seedable) separate from `SecretGenerator` (`SecureRandom`) | R26 needs reproducible arrangements in proofs; secrets must never be reproducible | One source for both; `SecureRandom` everywhere (unprovable arrangements); `Math.random`/`UUID.randomUUID` inside the domain |
| D15 | Bounding sessions and rate-limit keys | Plain concurrent maps pruned by the one sweeper, plus a hard cap that drops least-recently-used | R41 requires drop-LRU rather than refusing unseen callers; the sweeper already exists for game expiry | — |

| D17 | "Bounded caller-address key" (R38, spec assumption 4) | `request.getRemoteAddr()` as the key, used only for rate limiting and never written to a log record | No proxy in the local baseline; the requirement is that the keyed structure is bounded, which D15 gives | — |
| D18 | Structured logging | Spring Boot 4's built-in structured logging | No extra dependency for exactly the required output | — |
| D19 | Problem document | The **generated `Problem`** from `contracts/openapi.yaml` | D1 reverses this decision's premise: every component model is generated, and the contract's schema is named **`Problem`** — there is no `ProblemDto` in it. The contract still fixes the field set and still forbids extras; the generated type **is** that shape, mechanically rather than by hand | A hand-written `ProblemDto` record — the pre-D1 answer, a second copy of a wire type with nothing checking it against the contract. | D24 | The generic `Standards_and_recommendations/` material | Superseded wherever it conflicts; the constitution and the contract govern | Its version pins (JDK 21, Spring Boot 3.x, Gradle) contradict the constitution's baseline, which as of v1.2.1 is Java 25 LTS at patch 25.0.4 with Spring Boot 4.1.1 — an Enforcer `requireJavaVersion [21,22)` from them would fail this build. | D25 | Configuration key shape | One `BattleshipProperties` record with a single nested `RateLimits` record; keys enumerated in plan.md § *Configuration* | Keeps top-level limits at `BATTLESHIP_IDLETIMEOUTSECONDS`, which is what an operator will reach for, while grouping the rate limits | — |
| D26 | CSRF token handler | Plain `CsrfTokenRequestAttributeHandler` with `csrfRequestAttributeName = null`, and a cookie customised to `Secure; SameSite=Strict; Path=/` | Spring's default `XorCsrfTokenRequestAttributeHandler` masks the token per response, so echoing the raw cookie value — exactly what the contract prescribes — would be refused; `withHttpOnlyFalse()` alone sets neither `Secure` nor `SameSite` | Accepting Spring's defaults (breaks the contract); hand-rolled CSRF (rejected as D3) |
| D27 | How the projector reaches data outside the aggregate | `SnapshotContext`, an `application` record built by `app/registry` from the slot | `expiresAt`, `invitationUrl`, `invitationExpiresAt` and `connected` live on the slot, but `application` must not reference an `app` type or the ArchUnit rule fails | — |
| D28 | Generator configuration | `openapi-generator-maven-plugin` 7.25.0 in the `app` module only, bound to `generate-sources`: `generatorName=java`, `library=native`, `generateModels=true`, `generateApis=false`, `generateModelTests=false`, `generateSupportingFiles=false`, `useJakartaEe=true`, `serializationLibrary=jackson`, `dateLibrary=java8`, `enumPropertyNaming=UPPERCASE`, `disallowAdditionalPropertiesIfNotPresent=false`, and `typeMappings`/`importMappings` sending `Instant` to `java.time.OffsetDateTime` | Each setting earns its place. **Models only** — the controllers are hand-written (plan.md § *Adapters*) and generated Spring interfaces would dictate the adapter shape; `library=native` keeps an HTTP client out of the JAR, and with no APIs and no supporting files there is nothing to configure a client with. The `typeMappings` entry is not optional: the contract has a **schema named `Instant`**, which would otherwise shadow `java.time.Instant`. `enumPropertyNaming=UPPERCASE` (to verify in Task 1) is needed because `ProblemCode`'s 17 values are kebab-case (`malformed-request`) and must round-trip through `@JsonProperty`. `useJakartaEe` + `serializationLibrary=jackson` + `dateLibrary=java8` match the Spring Boot 4 baseline and `Instant`'s `string`/`date-time` with milliseconds and `Z`. `disallowAdditionalPropertiesIfNotPresent=false` keeps the generator from inventing an `additionalProperties` map on the schemas that do **not** declare one, while the eight that set `additionalProperties: false` deliberately — the seven request bodies and command variants plus the shared `Coordinate` — are enforced at runtime by Jackson `FAIL_ON_UNKNOWN_PROPERTIES=true`, which is what R37 actually requires. Open questions the Task 1 spike settles: whether `StreamClosed` is emitted at all (nothing `$ref`s it — it is the SSE `closed` payload, which is why `redocly.yaml` turns `no-unused-components` off); whether the 13 one-element `allOf` wrappers inline or mint wrapper classes; whether `Ruleset.board`'s inline object yields a usable `RulesetBoard`; and whether the plugin runs clean on JDK 25 | Generating APIs as well; `library=resttemplate`/`webclient` (pulls a client in); `spring` generator with `interfaceOnly` (dictates the adapter shape); committing the generated sources (Constitution VI); `openapi-generator` CLI outside Maven (a second toolchain to pin) |
| D29 | Open contract enums vs closed Java enums | Closed Java enums for all six | The contract marks `ProblemCode`, `Action`, `Violation.rule`, `Outcome.reason`, `Health.reason` and `StreamClosed.reason` open (`info.description` § *Compatibility*), but that is a rule for **clients**. This is the server: it authors every one of those values itself, and an unknown value arriving on a *request* must be refused `422 validation-failed` (R37) — which a closed Java enum does natively, with no extra code. Recorded so it is not re-litigated as a risk | An `UNKNOWN` sentinel constant per enum (dead code on the server, YAGNI); `String` fields (loses exhaustiveness on `switch`) |
| D30 | The `Command` `oneOf` whose discriminator maps 4 of 7 `type` values to `SimpleCommand` | Left exactly as it is | It looks codegen-hostile, but `Command` is **inbound only** — the server deserializes it and never writes one back — and Jackson handles many-names-to-one-class on the read side. Splitting `SimpleCommand` into four tagged schemas would be a contract change with no runtime benefit. A decision, not an open unknown; Task 1 proves the four variants deserialize by their `type` tag | Splitting `SimpleCommand` into `PlaceFleetRandomlyCommand`/`ClearFleetCommand`/`ReadyCommand`/`ResignCommand`; dropping the discriminator and letting the generator guess |
| D31 | What the projector returns, now the DTOs are generated | `SnapshotView` — framework-free `application` records (`SnapshotView`, `BoardView`, `PlayerView`, `ShotView`, `StatisticsView`) — which `SnapshotDtoAssembler` in `app/web` copies 1:1 into the generated `GameSnapshot` | Generated DTOs carry Jackson annotations, so they may live in neither `domain` (Constitution III) nor `application` (plan.md module table: no framework types). The previous plan had `SnapshotProjector` in `application/projection` producing a DTO from `app/web/dto` — a module-direction violation that could not have compiled, and the same rule D27 invokes. `SnapshotView` removes it while keeping the projector the **sole** place that decides disclosure, so proof area 3 stays an `application` test. R17 still holds: `SnapshotView` never leaves the server, so exactly one document goes on the wire for HTTP and SSE alike | A fourth Maven module for the DTOs (AGENTS.md forbids inventing module boundaries; the constitution mandates three); putting the projector in `app` (moves the privacy decision out of `application` and proof area 3 with it); hand-written DTOs kept solely to avoid the split (D1) |
