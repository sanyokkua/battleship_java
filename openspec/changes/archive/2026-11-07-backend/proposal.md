## Why

Feature `002-backend` of the greenfield Battleship rewrite needs one server-authoritative, ephemeral backend that conforms to the published `001-api-contract` (`contracts/openapi.yaml`). The backend has no database, no durable state, no frontend assets and no alternate public API. This change records the delivered the original workflow feature `the original 002-backend artifacts` (spec.md, plan.md, tasks.md, data-model.md, research.md, quickstart.md, checklists/requirements.md) in OpenSpec form so its requirements, design and task evidence remain greppable by their original IDs (R01-R64, S1-S12, US1-US7, the ten proof areas). Status at conversion: Delivered; T001-T038 complete. the original workflow `the original 002-backend artifacts` remains the historical source.

Provenance: requirements are `[user]` unless tagged `[agent]`, meaning proposed by the agent and approved by the owner. The `[agent]` set is R21 (server-generated ship ids), R26 (injectable randomness and attempt bound), R40 (body ceiling and content-type refusal), R52 defaults for the five unpinned rate limits, body ceiling, attempt limit, sweep interval and drain window, R61 (limits on unpinned operations) and R62 (per-browser live game cap). R26 also carries a `[user]` clarification of 2026-09-29 (`random-arrangement-failed`, HTTP 409). Owner-approved decisions: A1 (superseded 2026-09-29: application owns the in-memory registries), A2 (38 tasks over 7 phases, approved 2026-09-21), A3 (generated `Problem`, not a hand-written `ProblemDto`).

## What Changes

- Add a three-module Maven reactor `backend/` (`domain`, `application`, `app`) on Java 25, Spring Boot 4.1.1 and the Maven Wrapper, producing one executable backend-only JAR `battleship-app-1.0.0-SNAPSHOT.jar`.
- Implement all eleven contract operations under `/api/v1` and no other public surface; wire DTOs are generated from `contracts/openapi.yaml`.
- Implement the two rulesets (`sea-battle-10-ship.v1`, `hasbro-classic-2002.v1`), the phase machine, the allowed-action table, repeat-safe serialized actions, the caller-relative snapshot projector, statistics, anonymous sessions and invitations, request security, SSE live updates, rate limits and capacity ceilings, lifetimes and expiry, validated external configuration, redacted structured logging and graceful shutdown.
- Capabilities (delta specs under `specs/`): `backend-game-rules`, `backend-actions`, `backend-snapshots`, `backend-statistics`, `backend-sessions`, `backend-realtime`, `backend-limits`, `backend-lifetimes`, `backend-service-surface`, `backend-operations`.
- Contract amendments authorised under `001-api-contract` R24 (additive, within v1) and already applied: `Phase.PLAYING` first-turn wording (ready order), `GameSnapshot.version` wording (view rule R18), five lines of OpenAPI-3.1-only syntax normalised (`const` to single-value `enum`, `examples: [x]` to `example: x`) so wire types generate, and the owner-approved `joinGame` 410 response for an existing guest of a retained expired game (R34, R63). The first three are wire-JSON byte-identical.
- Out of scope: a database, durable session or result store, cache or broker as authority, accounts, chat, spectators, matchmaking, bots, rankings, history, payments, analytics, advertisements, offline play, command queues, horizontal scaling, CI workflows, deployment manifests and hosting automation; any user interface (`003-frontend`); the repository-wide gate and browser journeys (now owned by `003-frontend`); contract changes beyond the four amendments; the capabilities the contract defers (claiming a win against a vanished opponent, rematch, recovering a lost-answer join, conditional reads, salvo rules).

## Impact

- New code under `backend/` (about 95 files: roughly 60 main, 25 test, 10 build; generated sources are build output and not committed).
- `contracts/openapi.yaml` amended as listed above; `cd contracts && npm ci && npm run check` must stay green.
- Assurance level: Standard. Evidence is the ten proof areas only; JaCoCo or coverage gates, mutation scores, soak runs and generative testing are explicitly not completion criteria.
- Gate: `cd backend && ./mvnw -q verify && ./mvnw spotless:check`, with the repository-wide product gate later owned by `003-frontend` (`./scripts/local-build.sh`).
- Assumptions: the contract is complete enough to implement (gaps are fixed in the contract with dependents updated); the default base URL `http://localhost:5173` is configuration; the `[agent]` defaults are conservative starting configuration, not measured capacity; "bounded caller-address key" is decided by the plan (remote address).
- Checklist `checklists/requirements.md`: all items checked (content quality, requirement completeness, feature readiness, cross-artifact consistency); accepted deviation: the spec uses the contract's published vocabulary because the contract is the behavioural boundary.
